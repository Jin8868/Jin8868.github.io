视频从 MP4 到 Unity 屏幕显示的流程与原理

把一个 MP4 文件交给播放器，等待片刻，Unity 界面上就出现了连续画面。看起来像是在不断切换图片，背后却涉及文件读取、媒体容器解析、视频解码、时间调度、GPU 资源共享和图形渲染。

这是 PulseVideoPlayer 系列的第一篇。本文只讨论视频播放的通用步骤与原理，不涉及具体项目代码，也不限定某一种播放器实现。不同平台使用的接口和数据通道有所不同，但都需要解决同一组问题：画面在哪里、怎样还原、何时展示，以及怎样交给屏幕。

二、MP4 文件里装的是什么

1. MP4 是容器，H.264 才是一种编码格式

MP4 规定如何组织媒体数据与描述信息。视频编码则规定如何压缩和还原画面，例如 H.264、H.265 和 AV1。

同样以 .mp4 结尾的文件，内部可能使用不同的视频编码。因此，能够识别 MP4，不代表一定能够播放其中的内容。播放器还需要支持对应编码、Profile、位深、分辨率等参数。

一个 MP4 中可以同时存在视频轨道、音频轨道和其他轨道。各轨道拥有自己的样本、时间信息和描述数据。

2. 文件中并不是一张张完整图片

视频利用两类冗余进行压缩：

  • 空间冗余：同一幅画面中的相邻区域经常相似。
  • 时间冗余：相邻画面中的背景和物体经常只发生少量变化。

例如，一个人在固定背景前走动，没有必要为每一帧都完整存储整幅背景。编码器可以记录预测方式、运动信息和预测误差，由解码器重建画面。

以常见的 H.264、H.265 为例，人们通常用 I、P、B 来概括不同的帧间依赖方式：I 类画面主要使用帧内预测，P 类画面使用参考画面预测，B 类画面可以使用更灵活的参考关系。实际码流的细节比这个分类更复杂，但理解“部分画面需要依赖其他画面才能还原”就足够了。

3. MP4 还保存了寻找和解释数据的信息

MP4 使用称为 Box 的结构组织内容。常见结构包括：

结构 主要作用
ftyp 标识文件所兼容的格式品牌
moov 保存轨道描述、时间信息及样本组织信息
mdat 保存实际媒体数据
moof 在分片 MP4 中描述一个片段内的媒体样本

普通 MP4 中的样本表帮助播放器回答：某段数据在文件什么位置、长度多少、何时播放、哪些样本适合随机访问。分片 MP4 则会把相关信息分布到片段结构中。

这里的“样本”是容器组织媒体数据的单位，不能直接理解为已经解码完成的像素图片。

三、读取：先把正确的字节送进来

本地播放从文件系统读取数据，在线播放则从网络获得数据。读取阶段只负责提供字节，还没有把它们变成画面。

播放器通常先获得必要的描述信息，再持续读取后续数据，并使用缓冲区吸收磁盘或网络速度的波动。完整视频不必全部进入内存才能播放，是否能够边下载边播取决于容器布局、服务器能力和播放器实现。

例如，普通 MP4 的 moov 如果位于文件末尾，顺序下载时可能很晚才能得到播放所需的信息。将它移到前面，也就是常说的 Fast Start，可以改善渐进式播放的启动条件。支持 HTTP Range 的播放器还可以按需请求文件尾部或其他区间。

Fast Start 只是调整容器布局，不会让视频解码计算本身变快。

四、解封装：从容器中取出压缩视频

拿到文件字节后，解封装器会解析 MP4，选择需要播放的轨道，读取编码参数，并按需要取出媒体样本。

这一阶段的输出仍然是压缩数据。例如，视频轨道可能输出 H.264 码流，音频轨道可能输出 AAC 码流。解封装没有把视频还原成 RGB，也没有把音频还原成可以直接送到扬声器的 PCM。

对于视频样本，除了压缩数据本身，还需要保留时间信息：

时间信息 含义
DTS，解码时间戳 描述解码顺序对应的时间
PTS，显示时间戳 描述画面应该出现在时间轴上的位置
Duration 描述样本持续的时间

这些值通常以轨道时间基的整数刻度表示，需要换算后才能和播放时钟比较。

五、解码：把压缩码流还原成图像

解码器读取编码参数与压缩数据，重建图像。以常见块编码视频为例，这个过程包括解析压缩语法、反量化、反变换、生成预测结果、叠加残差，以及执行相应的滤波处理。

软件解码与硬件解码

软件解码主要由 CPU 执行算法，方便实现较广泛的格式兼容，但高分辨率、高帧率视频可能带来明显的 CPU 与功耗压力。

硬件解码使用设备上的专用视频解码单元。它通常有更好的能效，但支持范围受硬件、驱动、操作系统和编码参数限制。

硬件解码不等于“Unity 用一个 Shader 解开视频”，也不等于整条播放链完全没有 CPU 工作。文件读取、解封装、命令提交和时间调度依然需要处理。

解码结果通常不是普通 RGBA 图片

常见视频解码输出使用 Y′CbCr 表示，工程中经常统称为 YUV。它把亮度相关信息与色度信息分开存放。

以常见的 8 位 4:2:0 格式为例，每个像素都有亮度样本，而色度分辨率在水平、垂直方向各减半。NV12 通常包含一个 Y 平面，以及一个交错保存 U、V 的平面。

1920 × 1080 的一帧，忽略对齐与额外开销时：

  • 8 位 YUV 4:2:0：约 1920 × 1080 × 1.5 = 3.11 MB。
  • RGBA32：约 1920 × 1080 × 4 = 8.29 MB。

这里使用十进制 MB。实际内存还受行跨度、对齐方式、参考帧数量和输出缓冲数量影响，不能用“一帧大小”代表整个播放器的内存占用。

六、帧调度：画面解出来以后，什么时候显示

解码速度与播放速度是两个不同的概念。

一个解码器可能用 5 毫秒还原一帧，但 30 FPS 视频的相邻画面通常间隔约 33.3 毫秒。如果解完就显示，视频就会被加速播放。

播放器因此需要一个播放时钟，并根据每帧的 PTS 决定如何处理：

  • 画面还没到显示时间，暂时保留。
  • 画面到了合适的时间，交给呈现端。
  • 画面已经明显过期，可能丢弃它并追赶当前进度。

丢弃过期的显示输出，不代表可以随意跳过压缩码流中的参考画面。后续画面如果依赖它，解码器仍然可能需要完成相应解码。

视频时钟可以以音频播放进度为基准，也可以以系统单调时钟或外部时钟为基准。带声音的播放器常使用音频时钟，但这不是所有实现的固定规则。

视频帧率与 Unity 帧率互不相同

当视频为 30 FPS、Unity 以 60 FPS 渲染时，同一张视频画面可能被连续渲染两次；它不需要因此被解码两遍。

当视频为 60 FPS、Unity 实际只能以 30 FPS 呈现时，最终屏幕不可能逐一展示全部视频画面。播放器需要结合缓冲与丢帧策略维持时间轴。

对于可变帧率视频，相邻画面的时间间隔还可能变化，因此应依据时间戳调度，不能只靠固定的帧间隔累加。

七、图形接入：让 GPU 能采样解码结果

Unity 绘制 UI 或模型时，最终需要图形系统能够访问的视频资源。解码器输出的缓冲区，不一定能直接作为普通 Unity 纹理使用。

常见接入方式有两类。

1. CPU 图像上传到 GPU

软件解码或某些回退路径会在 CPU 内存中提供图像，然后上传为 GPU 纹理。

可以先在 CPU 转成 RGB 再上传，也可以分别上传 YUV 平面，在 GPU 中转换颜色。前者增加 CPU 颜色转换工作与上传数据量，后者需要相应的纹理布局和 Shader 支持。

仅以 1080p、60 FPS 的 RGBA32 完整帧上传估算，数据量就接近每秒 498 MB，还未计算额外复制与同步开销。这也是视频链路通常需要避免无意义的逐帧复制的原因。

2. 共享硬件解码表面

某些平台允许把解码输出表面，通过共享纹理、外部纹理或平台图形接口提供给渲染端。

这可以避免“先把图像读回 CPU，再上传 GPU”的往返，但是否能够直接共享，取决于解码器、图形 API、纹理格式及平台互操作能力。部分路径仍然需要 GPU 内部复制或颜色转换。

所谓“零拷贝”需要说明省掉的是哪一次复制，它并不自动意味着完全没有数据移动、转换和同步成本。

3. 共享资源还要共享正确的使用时序

解码器可能正在写入某个表面，而 Unity 正准备读取它。两边必须通过队列、栅栏或其他平台同步机制协调。

必须满足的条件是：写入完成后才能采样，采样结束后才能安全复用对应缓冲区。

如果只传递纹理句柄而忽略同步，即使纹理尺寸和格式都正确，也可能出现旧帧、闪烁、花屏或资源访问错误。

八、颜色转换：把视频颜色正确地显示出来

GPU 能读取视频资源，并不代表最终颜色已经正确。

从 YUV 到 RGB 的转换，需要结合色彩矩阵、量化范围和色度采样方式。BT.601、BT.709、BT.2020 使用的颜色定义并不完全相同；有限范围与全范围的数值解释也不同。

如果这些参数不匹配，就可能出现颜色偏移、黑色发灰、暗部压黑或亮部截断。

转换后还需要考虑视频的传递函数、Unity 的 Gamma 或 Linear 工作流，以及目标显示设备。不能只根据“视频已经是 RGB”就认为后续采样与输出一定正确，否则容易重复转换或漏掉转换。

HDR 视频还涉及更高位深、PQ 或 HLG 等传递函数，以及在 SDR 目标上的色调映射。它不是简单地把亮度乘大，而是一条需要端到端配合的显示流程。

九、Unity 渲染：把视频画面放进最终场景

拿到可采样的视频资源以后，Unity 才进入熟悉的绘制流程。

视频可以显示在 UI 矩形上，也可以作为场景中某个模型的材质输入。例如，一个游戏内电视机的屏幕可以用视频作为纹理，而电视机外壳仍然走普通模型渲染。

Unity 会根据几何形状、UV、材质和渲染状态生成绘制命令。GPU 执行这些命令，采样视频资源，将结果写入当前渲染目标，并与其他 UI 或场景内容合成。

在这一步，还需要处理几个独立于视频解码的问题：

  • 宽高比：完整显示时可能留黑边，铺满区域时可能裁切，直接拉伸则可能变形。
  • 方向与坐标：视频旋转信息及平台纹理坐标约定可能需要转换。
  • 遮挡与透明度：UI 层级、裁剪、混合和模型深度关系都会影响最终可见结果。

RenderTexture 可以作为中间渲染目标，但不是所有路径的必需步骤。有些实现直接采样外部视频纹理，有些实现先把视频转换或绘制到 RenderTexture，再供 UI 或材质使用。

十、屏幕显示：提交画面之后还有最后一段路

Unity 完成一帧渲染后，结果仍然位于图形系统管理的缓冲区中。

应用通过交换链或平台对应机制提交画面，随后可能经过操作系统窗口合成器，再由显示系统按照刷新节奏扫描输出。独占显示、窗口显示与不同平台的具体流程有所区别。

因此，至少要区分三个时刻：

  1. 视频帧解码完成。
  2. Unity 已经使用该视频帧完成渲染并提交。
  3. 显示器实际扫描到对应区域，像素开始呈现新内容。

这三个时刻之间存在队列、同步和刷新等待。播放器报告“首帧准备完成”，通常只说明链路中的某个准备条件已满足，不能直接等同于用户已经看到画面。

显示刷新率同样会影响观感。例如，24 FPS 内容放到固定 60 Hz 输出中，如果没有自适应刷新或其他处理，画面持续的刷新次数可能不均匀，即使没有解码丢帧，也可能产生节奏不均匀的顿挫感。

十一、声音、暂停和拖动进度为什么需要额外协调

声音走另一条处理链

MP4 中的音频通常经过独立的解封装输出、音频解码、PCM 缓冲、混音和音频设备输出。

声音与画面不需要经过完全相同的处理时间，但需要对齐到同一条媒体时间轴。音频设备还可能缓存尚未真正播放的样本，因此“提交了多少声音”不等于“用户已经听到了哪里”。

音画同步需要考虑这些缓冲与时钟差异。具体播放器可以选择等待画面、丢弃过期画面，或者在合适的策略下调整音频推进方式。

暂停需要冻结媒体时间的推进

暂停并不一定意味着立即销毁解码器，也不一定要求所有后台工作瞬间停止。播放器可以保留当前画面和已缓冲的数据，但必须协调视频时钟与音频输出，使恢复后仍然处于一致的媒体位置。

Seek 通常要从可随机访问的位置重新解码

用户拖动到第 10 秒，不代表文件里存在一张可以直接读取的“第 10 秒完整图片”。

播放器通常先通过索引寻找合适的随机访问点，再从那里向前解码，跳过目标时间之前的输出，直到得到目标附近可呈现的画面。

这里不能把任意 I 帧都等同于可以独立开始播放的完整随机访问点；具体能力还取决于编码结构和参考关系，例如 IDR 等随机访问语义。

Seek 还需要丢弃或失效化旧队列中的数据、重新对齐音频，并更新时钟基准。因此，拖动进度不是单纯修改一个浮点数。

十二、用一帧画面串起全过程

假设一个 MP4 中有一帧画面的显示时间戳为 2.000 秒。

播放器先从文件中读取相关字节，解封装器根据轨道信息找到压缩样本，并保留它的显示时间。解码器获取必要的参考画面后，将它还原为图像，并通过重排序使其进入正确的显示序列。

图像可能保存在 CPU 内存，也可能已经位于硬件解码表面。播放器通过上传、复制或共享方式，使它成为 Unity 可以使用的图形资源。

帧调度器依据播放时钟与呈现策略，在合适的渲染时机提交这张画面。Unity 采样视频资源，完成必要的颜色处理，将其画到 UI 或场景物体上，再提交包含该视频的完整游戏画面。

最后，显示系统在后续刷新中扫描输出，用户才真正看到这张画面。这个时刻还包含呈现队列和显示刷新带来的延迟，并不保证恰好发生在应用时钟的 2.000 秒。

MP4 负责组织数据，解封装负责取出压缩样本，解码负责还原图像，时钟负责安排呈现，图形接入负责让 GPU 访问图像，Unity 负责把它合成进游戏画面，显示系统负责最终输出。理解这些环节的职责，就能进一步讨论首帧耗时、播放卡顿、颜色异常、音画不同步和资源释放等具体问题。

Unity 异步等待方案选型：Mono 轮询 vs 协程 vs UniTask 在 Unity 项目里，”等一段时间再做某件事”、”等加载完再回调”、”等动画播完再切场景” 这类需求几乎天天遇到。选型不当，轻则代码难读，重则 GC 卡顿、生命周期错乱、回调地狱。本文把目前主流的三种方案放在一起做一次彻底的对比。 引子：我们到底在解决什么问题Unity 的核心循环是单线程帧驱动的：所有游戏逻辑都跑在主线程，按 PlayerLoop 的节拍一帧一帧推进。这就意味着 “异步等待” 在 Unity 里本质上是一个时间/事件维度的问题，而不是一个 “线程切换” 的问题。 我们需要解决的典型场景有： 等待 N 秒后执行某件事（技能 CD、UI 提示自动消失） 等待某个资源加载完成（AssetBundle、Addressables、网络请求） 等待某个条件成立（敌人进入视野、玩家按下按键、动画播放到某一帧） 串行/并行编排多个上述等待（连招、剧情演出、新手引导） 围绕这些需求，社区演化出了三种主流方案，下面逐一拆解。 方案一：自己编写基于 Mono 的管理器，在 ...
