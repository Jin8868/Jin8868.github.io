AlloyFramework的实现(九) - UIView的预制体结构、创建和加载

发表于2026-11-19|更新于2026-11-19
|总字数:2k|阅读时长:6分钟

一、一个根节点，两种布局边界

在不同比例的手机屏幕上，背景图既要铺到屏幕边缘，又要保持原始宽高比，避免拉伸变形。同时，交互组件要避开刘海和挖孔。为此，框架在 UIView 根节点下预留两个同级容器。背景图放在全屏容器 Background 下，等比缩放到铺满屏幕，允许边缘裁切。交互组件放在 SafeAreaContent 下，在安全区内布局。

横屏界面统一以 1920 × 1080 为参考分辨率，按宽度适配。 每个业务界面根节点的 CanvasScaler 都使用 Scale With Screen Size，匹配方式为 Match Width Or Height，横屏时 Match = 0（Width）。换设备时，设计稿的参考宽度仍是 1920，实际缩放倍率等于画布显示宽度除以 1920。例如在 2400 × 1080 的全屏画布上，倍率是 1.25，设计稿中宽 100 单位的组件会显示为 125 像素。此时画布可用高度是 1080 / 1.25 = 864 个设计单位，上下贴边的内容仍要通过锚点布局。当前项目的 UIRoot 配置为 AutoRotate，切到竖屏时会使用另一组参数：1080 × 1920，按高度适配。

Background 用来存放需要覆盖全屏的节点。 背景图、全屏遮罩都放在这个容器下。遮罩通常随容器拉伸到屏幕四边，背景图还需要保持素材的宽高比。

全屏背景图片的适配。 先比较屏幕和背景图的宽高比（宽 ÷ 高），再决定按哪条边铺满。缩放时，图片的宽和高始终使用同一倍率，画面就能保持原有比例。这个做法参考了《Unity UGUI 手机屏幕适配方案》中的“全屏背景图片的处理”一节。

  1. 屏幕宽高比等于图片宽高比。 按宽或按高等比缩放都能刚好铺满屏幕，整张图完整显示。
  2. 屏幕宽高比大于图片宽高比。 屏幕相对更宽，按屏幕宽度等比缩放，让图片左右铺满。此时图片高度超出屏幕，居中显示时裁掉上下边缘。
  3. 屏幕宽高比小于图片宽高比。 屏幕相对更窄，按屏幕高度等比缩放，让图片上下铺满。此时图片宽度超出屏幕，居中显示时裁掉左右边缘。

SafeAreaContent 让交互组件避开刘海和挖孔。 这个节点在编辑时铺满父节点。运行时，UISafeAreaFitter 根据 Unity 通过 Screen.safeArea 返回的安全区域调整容器边界。子节点的锚点相对于容器生效，因此交互组件可以按设计稿在安全区内排列。

两个容器互为同级。安全区收缩时，背景仍然铺到屏幕边缘，交互组件则随 SafeAreaContent 调整布局，避开遮挡。

二、用菜单一次创建标准层级

手工搭一个界面时，最容易漏掉的是刚好看不出差别的设置。例如，普通矩形屏幕上，即使忘了挂 UISafeAreaFitter，交互组件的位置也可能看不出异常。框架把这些固定操作集中在 UICreationMenu 里，每个新界面都从同一套设置开始。

  1. 在 Unity 的 GameObject → ★AlloyFramework★ → UI → 创建界面 执行菜单命令。工具创建并选中 NewUI，根节点带有 RectTransform、CanvasGroup、UIAnimationPlayer，并通过 EnsureRootCanvas 补齐 Canvas、CanvasScaler 和 GraphicRaycaster。
  2. 根节点下会按顺序出现 Background 和 SafeAreaContent。工具统一设置拉伸锚点、零偏移和单位缩放，再为 SafeAreaContent 添加适配组件。核心代码只有三行：
  1. 将 NewUI 改为业务界面的名字，放好背景和交互组件，把它保存为 Assets/Res/Prefabs/UI/ 下的业务 Prefab。创建菜单只在当前层级创建对象，到这一步才有可供加载的资源。
  2. 打开 ★AlloyFramework★ → UI → 打开界面生成器，选中该 Prefab，核对界面名、资源地址和显示层等设置，点击 生成界面代码并绑定预制体。

点击后，工具先生成三类代码：

  • View：工具按节点命名前缀扫描预制体，为匹配的组件生成序列化字段和强类型属性。脚本编译成功后，工具会自动把生成的 View 作为组件挂到该界面预制体的根节点上；如果根节点已有同类型的 View，就复用它。
  • Controller：首次生成时创建继承自 UIController<具体View类型> 的业务脚本骨架，包含生命周期回调。再次生成时会保留已有的 Controller 文件。
  • 界面定义：更新 GameUI 的定义表和强类型属性，将该界面的 View、Controller、资源地址和显示层等设置关联起来，供运行时打开界面使用。

根节点上的 View 就位后，工具将匹配节点的组件引用写入这个 View 的序列化字段，并保存预制体。之后新增或重命名控件时，再次执行同一命令即可更新字段和引用。

三、调用 Open 接口，从预制体加载到 Controller

至此，打开界面的准备工作已经完成：预制体根节点挂好了 View，节点引用已绑定，Controller 和界面定义也已生成。现在可以调用 UIManager.Instance.Open(definition) 打开界面，其中 definition 取自生成器在 GameUI 上生成的对应属性。

业务可以根据界面是否需要打开参数，以及是否需要 await，选择对应的接口。下表中的方法都通过 UIManager.Instance 调用。

调用方式 无打开参数的界面 需要打开参数的界面
直接打开，可选完成回调 Open(definition) Open(definition, data)
等待打开完成并取得句柄 await OpenAsync(definition) await OpenAsync(definition, data)

data 的类型由界面定义指定。Open 内部调用 OpenAsync，需要回调时可传入 onCompleted 接收界面句柄和异常。两种入口都支持可选的 cancellationToken。

UIManager 先按界面定义处理重复打开和实例复用。首次打开、需要创建实例时，内部流程可以分为三步：

  1. 加载预制体。 根据定义中的资源地址和包名调用 ResourceManager.Instance.InstantiateAsync，将界面实例挂到指定的 UI 层。
  2. 取得 View。 在实例根节点上按定义中的 View 类型调用 GetComponent。框架暂时隐藏界面、关闭输入，并配置 Canvas。这也是生成器要把具体 View 挂在预制体根节点上的原因。
  3. 交给 Controller。 框架通过界面定义创建对应的 Controller，调用 AttachView 将 View 交给它，再设置界面句柄并触发首次创建回调 OnCreate。从这里开始，业务代码就能通过 Controller 的 View 属性访问已绑定的组件。

四、总结

制作一个新 UIView 时，先按布局边界放控件：需要延伸到屏幕边缘的内容放在 Background，需要避让缺口和系统手势区的内容放在 SafeAreaContent。菜单固定了两者的层级、锚点和适配组件；业务只需决定每个控件应该跟随哪条边。保存预制体并生成具体 View 后，UIManager 就能根据界面定义找到资源、取得根 View，并把已经准备好的界面交给玩家。
