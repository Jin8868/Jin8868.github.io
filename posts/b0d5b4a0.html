YooAssets 的 AB 资源分类：如何抽象不同项目的分包需求

前三篇分别讨论了 AssetBundle 的结构、加载与卸载，以及分包策略。到了具体项目里，我们已经可以根据资源的使用范围、生命周期和更新节奏，决定哪些内容适合放进同一个包。

但对于 YooAssets，问题还要再往前走一步。

有的项目按角色和关卡管理资源，有的按玩法和活动组织内容；有的保留贴图、材质、预制体等类型目录，有的直接按功能划分文件夹。同样一个角色，在小项目中可能整体打包，在大项目中却需要拆出皮肤、语音和高清贴图。

YooAssets 作为一个面向不同项目的通用资源管理器，要适配这些差异，它应该如何抽象资源分类和分包管理？

如果直接规定“每个文件夹打成一个 AB”，就会把项目的目录结构与打包结构绑在一起；如果规定“每个角色一个 AB”，又无法表达界面、配置、场景和其他业务的需求。通用框架需要提供一套能描述项目差异的结构，让具体项目把自己的分包策略填进去。

本文就从这个问题出发，按照背景、目标、设计和结果的顺序，理解 YooAssets 在资源收集界面中呈现的四层结构：Package → Group → Collector → MainAssets。

本文以 YooAsset 2.3.19 源码为依据。“四层结构”描述的是资源组织与收集的观察层次，其中 MainAssets 是主资源收集器计算出的条目，并非与前三层一样手动配置的容器。

一、通用资源管理器需要表达哪些差异

上一篇的分包策略给出了一个判断方向：经常一起使用、释放和更新的资源，可以优先考虑放在一起；独立更新或按需下载的内容，再根据实际需求拆分。

但这是项目的业务判断。框架需要把这些判断转化为可执行、可复用的配置。

例如，同一批资源可能同时存在几种不同的组织方式：

观察角度 可能的划分方式
发布与版本管理 基础资源、扩展内容、独立更新的内容集合
业务管理 角色、界面、关卡、活动
源文件存放 Prefabs、Textures、Materials、Animations
实际打包 一个角色一个包、一个目录一个包、一个资源一个包
运行时访问 按地址加载预制体，通过引用带出材质与贴图

这几种划分并不总是重合。一个骑士的资源可以分散在四个类型目录里，却希望合成同一个 Bundle；一个活动目录也可以因为内容体积和更新频率不同，拆出多个 Bundle。

因此，框架需要让项目分别描述：资源属于哪个管理范围，按什么业务分组，从哪里收集，以及收集后如何寻址与归包。 这些问题如果全部压在一个“包名”字段里，配置就很难扩展。

在 YooAssets 的 Bundle Collector 界面中，可以从外向内看到：

Group 哪些收集器属于同一个管理分组？ 业务分组、激活规则、组标签、Collectors
Collector 从哪里收集，选哪些资源，怎样寻址和计算包名？ 路径、类型、过滤规则、寻址规则、打包规则

这里要先区分 Package 和 AssetBundle。YooAssets 的 Package 可以包含很多 Bundle；Group 和 Collector 也不天然对应一个 Bundle。四层结构负责组织资源和表达规则，最终的物理分包由打包规则及后续构建处理决定。

三、Package：确定资源集合的管理边界

1. 为什么最外层需要 Package

如果项目只有一份资源清单、统一发布和更新，那么把资源放进一个 Package 就能满足大部分需求。

但有些内容需要独立构建、维护版本或使用不同的资源构建形式。例如，常规 Unity 资产与原生音频文件的构建和加载方式就存在差异。此时需要在单个 Bundle 之上，再提供一个资源集合的管理层次。

Package 承担的就是这个角色。编辑器中的 AssetBundleCollectorPackage 定义该集合的收集配置；运行时通过对应名称的 ResourcePackage 初始化资源系统、使用资源清单并发起加载。

可以把它理解为：先选定在哪一套资源管理上下文中工作，再讨论其中具体资源怎样分类与打包。

2. Package 管什么

Package 中包含 PackageName、Groups，以及寻址、忽略资源和自动收集 Shader 等配置。构建时针对指定 Package 收集资源，运行时则在对应 Package 中查找资源位置。

一个 Package 可以有自己的版本和清单，清单再关联该集合中的资源与 Bundle。它的名字不是某个单独 AB 文件的名字。

当前项目的配置就包含：

Package 配置用途
DefaultPackage 预制体、材质、配置和场景等 Unity 资源
AudioPackage Wwise 音频原生文件
CodePackage 热更新程序集与 AOT 元数据文件
VideoPackage 视频原生文件

这些名称和用途属于项目自己的设计。对于原生文件，还要使用匹配的构建管线与加载方式，不能将它们全部理解为 Unity AssetBundle。

3. 什么需求适合放在这一层

当需求涉及资源集合的独立构建、版本和初始化时，可以考虑 Package 边界。只是希望让某个角色单独成包，通常在一个 Package 内配置打包规则即可；按需下载也可以在 Package 内结合标签、资源和依赖来实现。

跨 Package 的资源引用需要额外考虑。把共享材质放进另一个 Package，不会自动建立跨 Package 的依赖装载关系，也不能据此保证只构建一份共享内容。

四、Group：为相关收集器提供管理分组

1. 为什么 Package 下还需要 Group

一个 Package 可能包含几千个资源。如果把所有收集路径平铺在一张列表中，角色、界面、活动和关卡的配置就会混在一起。

Group 让这些配置有了业务上的组织方式。例如：

也可以继续按更细的业务单位建立 Group，例如 character.knight、ui.inventory。YooAssets 提供分组机制，项目决定使用什么粒度。

2. Group 管什么

AssetBundleCollectorGroup 中主要包含：

配置 作用
GroupName、GroupDesc 标识并说明该分组
ActiveRuleName 决定该组是否参与本次主动收集
AssetTags 为组内主资源提供公共标签
Collectors 保存该组的收集器列表

这让项目可以把多个路径作为同一组管理，而无需修改源文件的目录布局。骑士的预制体、贴图、材质和动画即使分散存放，也可以放在同一个 Group 下。

组激活控制的是主动收集。即使某组未启用，其中的资源仍可能被其他启用资源引用，并经依赖分析进入构建。标签则用于分类和相关下载选择，同样不会直接切割物理文件。

3. Group 与 Bundle 的关系

Group 本身不会强制组内资源合包。如果 Collector 使用 PackDirectory，就按每个资源的直接父目录计算包名；使用 PackGroup 时，才会以 Group 名作为包名依据。

因此，同一个 Group 可以管理多个 Bundle，也可以通过一致的 PackGroup 规则，把多个 Collector 的资源合入同一个 Bundle。Group 提供组织信息，具体打包规则决定如何使用这些信息。

五、Collector：把项目差异表达成可组合的规则

1. 为什么收集器是关键的一层

Package 与 Group 确定了资源属于哪里，但还没有回答：具体从哪个目录找，哪些文件参与，地址如何生成，包如何拆分。

这些变化集中在 Collector 中。每个 AssetBundleCollector 都描述一套收集规则，CollectPath 可以指向文件夹，也可以指向单个文件。

对于文件夹，收集器搜索范围内的候选资源，再应用忽略规则和过滤规则；对于单个文件，则对该文件进行相应判断。

2. 将几个经常变化的问题分开

配置 负责的问题 例子
CollectPath 去哪里找？ Assets/Res/Prefabs/Characters
FilterRuleName 直接选中哪些文件？ CollectPrefab 只直接收集预制体
AddressRuleName 可寻址主资源使用什么地址？ AddressByFileName 使用文件名
PackRuleName 资源按什么方式归包？ PackDirectory、PackGroup
CollectorType 收集条目承担什么角色？ Main、Static、Depend
AssetTags 给主资源增加哪些分类标签？ Knight、Optional
UserData 给扩展规则提供什么上下文？ 自定义规则约定的数据

这种拆分允许项目独立调整策略。例如，从“文件名寻址”改成“相对路径寻址”，不必同时改动目录范围和分包方式；把整个角色合包改成每个资源单独打包，也不必重新定义过滤规则。

YooAssets 还提供 IFilterRule、IAddressRule、IPackRule 等扩展接口。内置规则不能表达项目需求时，可以在相应维度扩展，而不是重写整套资源管理流程。

这正是通用性的一个来源：框架提供稳定的配置结构和执行流程，把容易因项目而变化的部分交给规则实现。

3. 分包策略如何落在这一层

几种常用内置打包规则分别对应不同的粒度：

规则 包名依据 可以表达的策略
PackSeparately 资源文件路径 每个直接收集的资源单独计算包名
PackDirectory 资源的直接父目录 按资源所在目录分包
PackTopDirectory Collector 下的顶级目录 按第一层子目录组织深层资源
PackCollector 收集器路径 一个 Collector 的直接收集资源使用同一个包名
PackGroup Group 名称 同组中采用此规则的 Collector 跨目录合包

Collector 会对收集到的每个资源分别计算 BundleName：计算结果相同的资源在构建阶段汇总到同一个包，结果不同的资源则进入不同包。一个 Collector 可以因此对应多个包，多个 Collector 的资源也可以合入同一个包。第八节用具体资源说明这层映射关系。实际归包还需要满足场景、资源类型和构建管线的约束，并考虑 Shader 等特殊处理。

这些规则不会替项目判断“应该怎样分包”。上一篇讨论的业务策略，最终需要在这里选择对应规则来落实。

六、MainAssets：从规则落到具体资源条目

1. 最内层显示的是什么

设置完 Collector，还需要确认规则实际选中了谁。展开一个 MainAssetCollector，界面会显示 Main Assets 及其资源条目；开启 Addressable 时，还会展示生成的地址。

源码中，Collector 用 CollectAssetInfo 表示收集条目，其中包含资源信息、收集器类型、Address、BundleName、标签和依赖列表等内容。

MainAssets 可以视为观察结构的第四层，但它是规则输出。 项目不需要再手动创建一个 MainAssets 容器；向收集范围内添加符合条件的资源，再刷新预览，就会得到新的条目。

2. 主资源与依赖资源

假设业务按地址加载 Knight.prefab，它再引用材质和贴图。预制体是一个可直接加载的入口，材质和贴图则可以通过依赖关系参与加载。

“主资源”不等于资源更重要，也不等于一份资源只能有一种业务用途。它主要表达是否作为 YooAssets 清单中的独立加载入口。

CollectorType 进一步区分了三种情况：

类型 参与构建的条件 是否生成普通 Location 加载入口
MainAssetCollector 直接收集后参与 是
StaticAssetCollector 直接收集后参与 否
DependAssetCollector 被 Main 或 Static 主动收集资源引用时保留，否则剔除 否

对应类型的界面预览会显示 Main Assets、Static Assets 或 Depend Assets。Static 不代表资源在运行时永久驻留，Depend 也不能代替业务代码按字符串地址发起的加载需求。

如果业务需要单独按地址加载某张贴图，它就应有相应的 Main 入口；如果只通过预制体引用它，则可以根据归包需求考虑 Depend 收集器，或交由后续依赖分析处理。

3. MainAssets 与最终 Bundle 内容的区别

2.3.19 的界面预览通过 RefreshFoldoutContent 调用 Collector 的 GetAllCollectAssets，并设置 IgnoreGetDependencies，跳过依赖查询。

所以，MainAssets 里只显示一个预制体，并不代表构建中只有这个文件。只直接收集预制体，也不代表预制体引用的贴图被排除了。依赖分析仍会在构建流程中继续进行。

同样，FBX 内的 Mesh 和动画等 Unity 子资产，也不能直接按 MainAssets 条目数量判断。这里列出的是收集层面的资源文件，完整产物要结合构建报告查看。

四个骑士 Collector 一致使用 PackGroup，就能用相同的组名计算包名；活动图片使用自己的 Group 和打包规则。类型目录得以保留，打包结构则由配置明确表达。

八、Collector 下的 Assets 如何映射到 AssetBundle

Collector 收集到资源后，会对每个 Asset 分别执行 PackRule，得到一个 BundleName。在同一 Package 内，参与归包的资源按 BundleName 汇总：包名相同，归入同一个 AssetBundle；包名不同，归入不同的 AssetBundle。

例如，一个 Collector 收集了下面三个预制体，使用 PackDirectory：

Asset 规则依据 对应 AssetBundle（包名示意）
Characters/Knight/Knight.prefab 父目录 Characters/Knight knight.bundle
Characters/Knight/KnightPreview.prefab 父目录 Characters/Knight knight.bundle
Characters/Mage/Mage.prefab 父目录 Characters/Mage mage.bundle

这个 Collector 收集了三个 Asset，却对应两个 AssetBundle。如果改用 PackCollector，三个 Asset 就会按同一个 Collector 路径计算包名，从而归入同一个包。

反过来，上一节四个骑士 Collector 一致使用 PackGroup，就会为各自的 Asset 计算出相同的包名，让分散在不同目录的资源归入同一个 AssetBundle。

Collector 与 AssetBundle 的关系由每个 Asset 的 BundleName 建立：一个 Collector 可以对应多个包，多个 Collector 的资源也可以合入同一个包。 Address 决定如何定位资源，BundleName 决定资源归入哪个包，两者职责不同。

这里说明的是直接收集资源的归包映射。依赖处理及这些映射如何生成实际的 AB 文件，放到下一篇的打包流程中讨论。

九、这套抽象最终解决了什么

YooAssets 通过 Package 管理资源集合，通过 Group 组织相关收集器，通过 Collector 描述项目的收集、寻址和打包规则，把规则落实为 MainAssets 等具体收集条目，再依据条目上的 BundleName 确定资源到 AssetBundle 的归属。

这样，按类型存放、按功能管理、按更新范围分包就可以同时存在。项目可以保留自己的目录习惯，并用规则表达不同的打包粒度。

具体应用时，可以按下面的顺序检查：

  1. 用 Package 确定这批资源的构建、版本和运行时归属。
  2. 用 Group 组织相关 Collector，并设置必要的激活规则与标签。
  3. 用 Collector 明确路径、过滤、寻址、类型和打包规则。
  4. 在 MainAssets 等预览中确认直接收集的资源与地址。
  5. 对照各资源的 BundleName，确认哪些资源共包、哪些资源分包。

预览还不能代替 Package 级校验。同一 Package 内重复收集资源、生成重复地址，仍会产生冲突；Shader 与共享依赖的归包也需要在构建报告中确认。

这套结构提供了表达不同项目需求的能力，实际分包是否合适，仍取决于项目如何选择边界。前一篇回答“哪些资源应该放在一起”，这一篇则说明 YooAssets 如何提供一组分层的概念，让这些判断成为可以配置和执行的资源管理方案。
