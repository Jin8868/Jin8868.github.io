Unity AssetBundle 结构解析笔记

基于 AssetStudio 逆向源码（BundleFile.cs / SerializedFile.cs）与 YooAssets 源码整理。
Unity 未公开官方格式文档，本文以逆向工程实现为准（Unity 2022.3 为 UnityFS 主流版本）。

0. 概述

  • .assetbundle 文件是 Unity 的私有格式，YooAssets / Addressables 等框架都只是调用 BuildPipeline.BuildAssetBundles 产出后在外层做 hash / 加密 / 清单，不改变文件内部结构。
  • 完整的资源体系是三层结构：外层是一个自定义压缩归档（UnityFS），里面躺着若干个 Unity 序列化文件（SerializedFile，即资产真正存放的地方）；bundle 之上还有一层独立文件 manifest（清单），记录所有 bundle 的组织关系。

2.3 解压流程（AssetStudio 实现）

  1. 按头部 flags 解压 BlocksInfo（None / LZMA / LZ4 三分支；LZ4 解压后校验字节数）
  2. 按 StorageBlock 表逐块解压数据区，拼进统一 blocksStream（超过 2GB 落盘临时文件）
  3. 按 Node 目录从 blocksStream 切出各 SerializedFile 和 .resS

2.4 压缩方式与加载行为（LZMA vs LZ4）

数据段存放的是 Assets 序列化后的原始字节，选哪种压缩方式直接决定了运行时的加载行为：

LZMA —— 整体压缩

  • 对序列化后的完整字节数组作为一个整体压缩，压得最紧（体积最小）
  • 代价是失去随机访问能力：算法依赖前后文，要读其中任何一小段都得从头解压整个流
  • 适合”下载完就用完”的场景，即远程资源包的传输形态

LZ4 / LZ4HC —— 分块压缩

  • 数据区切成多个 StorageBlock 逐块独立压缩，块之间无依赖
  • LoadFromFile() / LoadFromStream() 时只把 Header（含 BlocksInfo 目录）读入内存建立索引，数据段继续留在磁盘上
  • LoadAsset() 时才发生真正的磁盘读取：按目录定位资源所在的块，只把对应的块解压加载进内存，其余块不动
  • 这就是懒加载 / 懒解压的物理基础，首包和本地缓存用它（加载快）

选型口诀：下载选 LZMA（省流量），加载选 LZ4（省时间）。两者不冲突——把远程 LZMA 包下载后转存为 LZ4 缓存，一次付解压成本，之后每次加载都快。

3.3 跨文件依赖机制（bundle 依赖的物理来源）

  • Material 引用另一个 bundle 的 Texture 时，序列化里存的是 (externals 表下标, pathID) 二元组，不是路径。
  • 解析引用 = 按 pathName 找到对应 SerializedFile → 按其 Objects 表的 pathID 找到对象。
  • 因此运行时必须先把被引用的 bundle 全部加载，引用才解析得通——Unity 运行时加载器和 AssetStudio 的 ObjectsDic 做的是同一件事。
  • 打包工具（YooAssets 依赖 Task / Unity BuildPipeline）算出的依赖图，最终就是落成这张 externals 表。

4.5 框架清单与原生清单的关系

原生清单是给原生 API 直载用的；YooAssets 等热更框架构建自己的清单文件（如 PackageManifest：增加地址寻址、tags、每 bundle 的 FileHash/FileCRC/size/加密标记，按版本组织文件，配合 ActiveManifest 原子切换），原生清单在这条路上不再出场。但两者扮演的角色相同——清单管导航（决定备谁/下谁），bundle 内的 externals 管粘合（解析对象引用）。

6. 结构决定行为：机制背后的因果

理解了上面三层结构后，很多”行业常识”其实是结构直接推导出的必然结果：

① 为什么加载资源前必须先加载整条依赖链？
因为引用的存储形态是 (externals 表下标, pathID)——它指向”另一个已在内存中的 SerializedFile 的某个对象”。引用解析发生在加载期，被引用的 bundle 不在内存，这个二元组就无从解析，加载直接失败。”备哪些 bundle”由清单的闭包列表导航（4.3 节），”接上引用”由 externals 粘合。

② 为什么 bundle 是最小热更单位，做不到文件级热更？
因为资源不是独立文件，是嵌在 SerializedFile 里的 Object（有偏移、有序）。改一个资源 → 它所在 Object 变 → 整个 SerializedFile 的字节布局变 → 整个 bundle 重写 → hash 必变。清单里的 Hash（原生 manifest 的 AssetFileHash）正是客户端比对增量更新的依据。

③ 为什么 bundle 切太碎会导致资源冗余？
因为 externals 引用要求”被引用的文件同时可用”。跨 bundle、跨 Package 引用一个资源，意味着两边必须同时加载、生命周期绑定。为了避免这种绑定，打包工具会把共享资源拷贝一份打进每个引用方 bundle——拷贝就是冗余（磁盘翻倍、内存翻倍、Unity 视为两个不同的 asset 实例）。

④ 为什么加载单个资源不用解压整个 bundle？
因为数据区是块级压缩 + 偏移索引：条目 → offset → 只解它落在的那几个 StorageBlock。这是远程包用 LZMA（小）下载、本地缓存转 LZ4（快）能成立的结构基础。

⑤ 为什么 Unload(true) 会”连坐”销毁整个 bundle 的资源？
因为 Object 的内存对象与所在 SerializedFile 的生命周期绑定，Unity 不做单 Object 级回收——文件卸了，从它反序列化出来的资产就失去来源。这也是”bundle 划分要按生命周期一致性”的底层原因：混在一个 bundle 里的资源，要么一起活着，要么一起消失。

⑥ 为什么 GUID / TypeTree 不可省？

  • FileIdentifier 里的 GUID 是资产间引用的稳定标识（路径会变、GUID 不变），重命名资源不断引用靠它。
  • TypeTree 是”字段布局说明书”：没有它，同一份二进制在新版本 Unity 里无法解析。打包时剥离 TypeTree 换体积，运行时靠引擎内置的类型布局兜底——这也是 bundle 与 Unity 版本强绑定的原因之一。

⑦ 为什么热更要”先更新清单再下载”？
因为客户端需要先知道”世界长什么样”（新清单）才能对比出”我缺哪些 bundle”（本地清单 vs 远端清单的 Hash 差集）。清单不动、bundle 白下——原子切换清单（框架层）或统一版本目录（原生层）都保证了对比期间旧世界照常可玩。

8. 加密 bundle 的观察方法

框架的加密几乎都是对标准 UnityFS 做包装（因为 Unity 加载器最终要能读，算法必须加载时可逆）：

  1. 头部插入偏移字节：文件头塞一段随机长度垃圾字节，加载时跳过（YooAssets offset 加密即此思路）
  2. 头部若干字节 XOR/变换：破坏签名识别
  3. 全文件流式变换（少见，加载慢）

观察步骤：找到解密实现 → 用同样算法逆处理 → 得到标准 UnityFS → 丢进 AssetStudio / UnityPy 查看；或直接构建一个不加密的包用于研究。

9. 与 YooAssets 概念的对应

概念 说明
.manifest 文本 / AssetBundleManifest 对象 Unity 原生清单层（第 4 节）；YooAssets 用自己的 PackageManifest 承担同一角色
bundle = 最小热更单位 改一个资源 → Object 变 → SerializedFile 变 → 整包重写，hash 必变
切太细导致冗余 资源不在本 bundle 就只能 externals 跨文件引用；要避免跨包引用就得拷贝进每个引用方
AssetBundle.Unload(true) 连坐 Object 的内存对象与所在 SerializedFile 生命周期绑定，Unity 不做单 Object 级回收
