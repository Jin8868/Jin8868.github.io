Text 与 TMP 艺术字实现方案

1、需要显示艺术字

游戏中的战力、伤害、倍率和胜负提示，通常要求保留美术制作的渐变、金属纹理、立体高光与装饰。这些效果既可能出现在数字上，也可能出现在“胜”“利”“战”“力”等少量汉字上。

这里的素材是美术逐字提供的透明背景 PNG。我们需要把这些图片组合成可变化的艺术字内容，例如“战力12345”“+1280”“胜利”，并让业务层像更新普通文字一样使用：

需求包括保留图片原色、控制基线和字距、支持内容更新，以及复用既有 Text 或 TMP 界面。每套风格有明确的静态字符集，所有可见字符都应来自同一套美术素材。

2、实现艺术字的方法

2.1 从字体渲染原理看艺术字

之前文章《Unity的TMP和Text原理和使用优化》中说到，动态 Text 会从字体文件获取字形，按字号等条件生成位图，再通过图集显示；TMP 常见的 SDF 路径则先生成距离场图集，再由 shader 重建边缘。

对逐字绘制好的艺术字，可以把生成字形图像的步骤替换为使用美术图片，继续复用文本组件的字符查找、排版和网格生成能力。

路径 图集内容 显示方式 对本需求的适用性
常规 Text 字体 字形覆盖率位图 通过字体位图显示轮廓 不能直接还原逐字绘制的彩色素材
TMP SDF 字体 字形边缘的距离信息 shader 重建边缘与参数化效果 适合轮廓、描边与阴影，不能直接还原任意彩色绘制细节
图片艺术字 已绘制完成的 RGBA 颜色 按图集 UV 输出原色和透明度 适合本文的逐字 PNG 素材

图片字体交给 TMP 显示后仍然是位图，放大质量受素材分辨率限制，不会自动获得 SDF 的缩放能力。下面分别讨论 Text 与 TMP 如何接入这种图片艺术字。

2.2 Text：静态自定义 Font

Legacy UGUI Text 可以使用自定义 UnityEngine.Font，通过 CharacterInfo 保存字符码点、字形范围、步进与 UV，并为字体配置 RGBA 图集和材质。

业务层接入：在 Text 组件上绑定生成的 .fontsettings，配置好字号和颜色，之后直接设置原生 .text：

**性能特点：**字形图片与映射在编辑器中准备完成，运行时无需为这些字符动态生成字形位图。多个字形由文本组件生成网格，无需逐字创建 Image。内容更新仍会涉及字符串处理、排版与网格重建，最终批次受材质、遮罩、Canvas 和绘制顺序影响。

这也是在保持原生 Text 字符查找与排版流程的前提下，直接用 .text 显示自定义图片字形的主要路线。自行派生组件或编写网格渲染器也可以提供同名属性，但要额外维护字形查找、布局和 UI 行为，不属于原生字体资产接入。

2.3 TMP：使用 SpriteAsset 标签显示艺术字

即使只显示艺术字，也可以把逐字图片制作成 TMP SpriteAsset，让每张图片对应一个 sprite，再通过标签组合内容。这里所有图片仍是艺术字字形。

**业务层接入：**配置 SpriteAsset 后，使用图片名称或索引构造标签。例如显示“01”：

业务若接收普通字符串，就需要先转换成标签字符串。可以把转换封装到展示层，但名称映射、转义、缓存和素材调整后的对应关系仍需维护。直接使用索引还需要保证资产排序稳定。

**性能特点：**TMP 会解析标签、查找 sprite 并生成网格。一个标签不会创建一个 Image GameObject，也不意味着一次 DrawCall；纯艺术字使用同一 SpriteAsset 与共享材质时，多个字形可以在同一批次内绘制，最终仍需检查 UI 的实际合批条件。

额外成本主要在普通字符串到标签字符串的转换、临时字符串分配，以及更长的输入和标签解析。缓存可以减少重复转换，但需要管理缓存范围。仅凭存在标签，不能断言它的 GPU 开销明显高于位图字体。

SpriteAsset 还可以为字形配置 Unicode，通过 TMP 的字符查找路径显示普通字符，不过需要处理字体优先命中同一码点等查找规则。对于整串艺术字，使用专门的位图字体资产更容易明确字符覆盖与风格归属。

2.4 TMP：静态位图 FontAsset

把艺术字图片打包成图集，为 TMP_FontAsset 创建字形表和字符表，通过 Unicode 将普通字符串映射到图片字形。再使用保留 RGBA 的材质，交给 TMP 完成排版与显示。

**业务层接入：**在 TMP 组件上配置生成的 FontAsset 和共享材质，之后直接设置原生 .text：

**性能特点：**省去普通字符串到 sprite 标签的转换，运行时直接按字符查询字体；字形图集静态生成，无需动态扩充这些艺术字。文字更新仍会产生解析、排版与网格重建成本。

在相同图集、材质复杂度、可见字形数量和屏幕覆盖面积下，它与纯 sprite 方案的 GPU 开销可能接近。其优势主要是业务接口直接、资产语义清晰，以及减少标签转换和相关字符串管理。

2.5 业务接入与性能对比

方法 业务层输入 额外接入工作 CPU 更新特点 GPU 与内存特点
Text 静态 Font 普通字符串 生成 Font，配置字体与材质 原生文字排版与网格重建 由图集、材质、网格和 UI 合批条件决定
TMP Sprite 标签 标签字符串，或先转换普通字符串 生成 SpriteAsset，维护名称或索引与转换逻辑 标签解析；转换过程可能额外分配字符串 单字不是单个 Image；共享图集和材质有利于合批
TMP 位图 FontAsset 普通字符串 生成 FontAsset，配置 RGBA 材质 直接查找字形，无需业务标签转换；仍需排版与重建 与相同条件的 sprite 方案可能接近，无天然 DrawCall 优势

同一批 RGBA 素材采用相同图集尺寸和导入设置时，纹理占用主要由图集决定。Text 与 TMP 的 CPU 排版、网格及资产管理实现不同，不能直接断言某一方总是更快。

原文章中的 Text 与 TMP 性能数字对应当时的字体、图集和测试内容，不能直接作为这里图片艺术字的性能结论。比较时应统一字符数量、字号、刷新频率、图集格式和目标设备。

3、选择静态位图字体方案

选择“编辑器生成静态位图字体，运行时使用原生文本组件”的方案：已有 Text 界面导出 UnityEngine.Font，已有 TMP 界面导出 TMP_FontAsset，两者共用美术源图与排版配置。

3.1 核心收益：业务代码无感，只替换组件字体

这套方案最主要的好处是把艺术字作为字体资产接入。对于已经通过 .text 更新内容的界面，业务不需要知道字体来自普通字体文件还是美术图片，也不需要增加艺术字专用的显示分支、字符串转换或逐字图片操作。

字体材质由生成工具配套创建并绑定，字形映射、基线和字距保存在字体资产中。UE 人员可以在预制体上完成字体替换和显示调整，业务层无需接入新的运行时接口。对于原本显式指定了其他材质的组件，应同时恢复或绑定与新字体匹配的材质，避免覆盖字体默认材质。

业务无感的前提是新字体覆盖原有显示内容。例如“战力12345”中的汉字、数字，以及数值格式化可能产生的正负号、小数点和单位，都需要有对应素材。组件上的字号、颜色与布局由 UE 人员按设计效果调整，这些都属于展示配置。

3.2 工具封装后，由 UE 人员独立维护

程序需要一次性封装好素材校验、图集打包、字体生成、材质绑定和原地更新工具。工具交付后，日常修改可以完全由 UE 人员完成：

  1. 准备或替换对应风格的逐字图片，配置字符映射与排版参数。
  2. 通过生成工具导出或更新 Text / TMP 字体资产。
  3. 在预制体上替换 Font / Font Asset，调整字号、颜色与布局并预览效果。
  4. 根据工具提示补齐缺字或修正素材，再保存预制体与相关资产。

后续更换艺术字风格、调整数字字距、替换美术素材，都通过配置和资产更新完成，无需让程序逐个界面修改业务代码。工具必须提供可理解的缺字、重复映射、图集容量和引用错误提示，并在重新生成时保留资产 GUID，才能让这套流程稳定交给 UE 人员使用。

3.3 选择依据

选择位图字体的重点是业务接口保持不变，以及把日常维护交给展示层和工具：程序负责通用生成能力，UE 人员负责字体资产与界面表现，业务继续负责内容更新。

对于 TMP，相比逐字构造 sprite 标签，位图 FontAsset 还省去了标签转换、名称或索引映射及相关字符串管理。但在相同图集、材质和字形规模下，不能据此承诺明显的 GPU 性能提升；实际性能仍需在目标设备上测量。

4、我们的方案需要实现的东西

需要封装一套可交给 UE 人员独立使用的编辑器生成工具，覆盖素材配置与校验、图集打包、Text 字体导出、TMP 字体导出、材质自动绑定、原地更新与效果预览。工具应提供清晰的操作入口和错误提示，让 UE 人员无需修改代码即可完成字体制作与替换。运行时复用原生文本组件，不需要逐字创建显示对象。

4.1 显示链路：用字体资产连接字符串与图片

一个可用的图片字体包含四类信息：字符映射、字形度量、图集与材质。

以“胜利”为例，文字组件在重建时解析字符串，根据字符表找到两个字形；再根据字形的宽高与基线偏移生成四边形，根据图集区域生成 UV。材质在四边形内部采样原图，图外由 Alpha 保持透明，最终得到两个艺术字。

字符可以产生字形四边形，但空格、换行等不必产生可见四边形。文字变化通常会使布局或网格变脏，由 Unity 在重建阶段处理，并非每次属性赋值都立即绘制。

这条路线复用了原生组件的排版与渲染入口，Text 和 TMP 的内部实现、缺字策略及材质约定仍各不相同。

4.2 字形度量：区分图片尺寸、基线偏移与光标步进

仅记录“字符对应图集哪一块”还不够。生成器至少需要保存以下数据：

数据 用途 示例
Unicode 从字符串查到字形 “胜”为 U+80DC，即 32988
Glyph ID 标识一个字形，供字符表引用 从 1 开始稳定分配
Atlas Rect 图集中的像素采样区域 x=8，y=8，w=48，h=60
Width / Height 字形四边形的设计尺寸 48 × 60
Bearing X 字形左边相对光标的偏移 0
Bearing Y 字形顶边相对基线的高度 60
Advance 当前字符结束后光标前进的距离 52
Face Metrics 整套字体的字号、上升线、下降线和行高 设计字号 64，行高 72

例如一个字宽 48、高 60、Bearing Y 为 60，字形就处于基线上方；Advance 为 52，代表给下一个字额外留下 4 个设计单位。若 Bearing Y 写成 0，字形会向基线下方延伸，从而导致上下错位。

描边、投影与外发光也可能占用图片空间，视觉范围不一定等于排版步进。裁透明边时必须同步补偿 Bearing，避免裁完图片后文字上下跳动。滚动数字建议设置相同 Advance，防止数值改变时整串文字宽度抖动。

4.3 素材配置：统一字符映射与排版规则

建议每套风格使用一份配置，记录设计字号、基线、行高、默认字距，以及每个字符的图片、码点、Bearing 和 Advance。不要仅凭文件尺寸自动推断所有排版数据。

文件可命名为 0.png、胜.png；对文件名不合法的符号以及非 BMP 字符，使用 U+002F.png 等码点命名，或显式配置映射。生成器应拒绝重复码点、无效 Unicode 标量、空图片和未配置的排版数据。

Unicode 码点与 C# char 不是同一个概念。普通汉字通常可以直接取 char 的整数值；非 BMP 字符需要解析 UTF-16 代理对，不能简单按字符串中的每个 char 生成一条记录。配置层建议统一使用 uint 存储 Unicode 标量。Legacy Text 对非 BMP 字符的实际支持还需单独验证，不能仅凭 CharacterInfo.index 是整数就承诺支持。

默认按“一个 Unicode 标量映射一个字形”制作素材。若美术提供的是完整的“胜利”一张图，它应作为整词图片显示；要在普通 text = "胜利" 下将两个字符替换成一个整体字形，需要额外的词组替换或 shaping 机制，不能仅靠基本字符表自动实现。

空格应有合理的 Advance，可以没有可见图像；同时明确支持半角、全角、正负号和百分号的范围，避免业务格式化后出现未收录字符。

4.4 图集生成：一次打包并稳定更新资产

编辑器生成流程建议为：读取并校验配置，按码点稳定排序，打包图集，保存并重新导入 PNG，再用同一次打包得到的矩形生成字体资产，最后执行字符覆盖与引用检查。

图片使用 RGBA，初始可采用无压缩、无 MipMap、Clamp、Bilinear 的设置，再按目标平台验证压缩效果。Bilinear 下不建议采用零间距打包，应预留例如 2～4 像素间隔，并根据需要做边缘颜色扩展，降低串色和透明边黑边问题。字体 UV 指向有效字形区域，避免把隔离区算进文字宽度。

若使用 Texture2D.PackTextures，必须检查输出矩形与源图的尺寸关系；容量不足时它可能缩小图片，不能仍使用原始图片尺寸假定是无损打包。固定精度的艺术字应选择扩大图集、明确分页，或报错要求拆分风格。首版建议限制单页，超限时给出清晰提示。

4.5 Text 导出器：生成静态 UnityEngine.Font

Text 路径输出 .fontsettings、持久化材质与图集 PNG。对每个字符创建 CharacterInfo，设置码点、几何范围、Advance 与四角 UV，再写入 Font.characterInfo。

材质使用支持 RGBA 采样与 UGUI 裁剪的 shader，例如 UI/Default，其主纹理指向已保存并导入的图集。给 Text 配置生成的 Font，组件材质保持默认使用字体材质，Color 为白色；设计好字号与布局后保存预制体，业务直接设置 .text。

Legacy 自定义 Font 的尺寸换算涉及其序列化度量和 Unity 版本。应在目标版本用固定设计字号建立参考预制体，校准设计高度、基线与行高。内部 m_PixelScale 的近似换算不应当作稳定公开 API。

此路径不依赖 TMP 的 fallback 机制。缺字应在生成期或界面配置检查中发现，并明确告警或替代字策略；不能假定会自动回退到系统字体。

UGUI Outline 会复制偏移后的网格，并继续使用纹理 Alpha，并非必然画成矩形。但它会增加顶点量，也难以还原美术的复杂描边与投影；这类效果优先烘焙在图片中。

4.6 TMP 导出器：静态 FontAsset 与 RGBA 材质

TMP 界面使用静态位图 FontAsset，让字体资产直接参与字符查找。与 Text 路径一样，业务通过原生 .text 属性设置艺术字内容；两条路径共享素材与排版配置，分别导出对应的字体资产。

4.6.1 当前版本的类型与初始化

以下 API 以 TMP 3.0.6 为例，使用 UnityEngine.TextCore.FaceInfo、Glyph、GlyphRect、GlyphMetrics，字符映射使用 TMPro.TMP_Character。应使用当前版本的 TextCore 类型定义。

该版本 glyphTable、characterTable 的 setter 为 internal，外部编辑器工具应通过公开 getter 获得列表后执行 Clear() 和 Add()，而不是直接替换整个属性。

生成器还需正确初始化字体版本与渲染模式。可以基于当前版本提供的 TMP_FontAsset.CreateFontAsset 创建有效的位图字体骨架，再替换图集、材质、FaceInfo 和表数据，切换为 Static 并清理临时资源；也可以通过隔离的编辑器序列化适配层生成资产。不要仅 CreateInstance 后随意填几个字段：空版本可能触发 TMP 的旧资产升级逻辑。涉及内部序列化字段的方式必须集中封装，并在升级 TMP 时检查。

4.6.2 彩色艺术字的材质选择

当前版本的 TextMeshPro/Bitmap 从 _MainTex 获取 Alpha，RGB 来自 Face 纹理与颜色；TextMeshPro/Mobile/Bitmap 也主要使用字形 Alpha。这两者不能直接当作保留彩色图集原色的通用方案。选择 shader 时应核对当前版本的实际名称和采样逻辑。

SDF shader 依赖距离场编码，不能直接拿普通 RGBA 图片当距离场使用。字体放进 TMP 后显示不对，首先区分是字符查找、度量、UV 还是材质采样问题。

下面展示生成器内部填表逻辑；假定 fontAsset 已完成上述骨架初始化，配置与图集均已校验。这是关键流程片段，不能单独作为完整生成工具运行。

上例为单字示意。完整工具应为全部字形分配稳定且唯一的 Glyph ID，循环填表后只调用一次 ReadFontAssetDefinition()。设置 FaceInfo 时使用统一的设计字号、基线、上升线、下降线及行高；字形 Bearing Y 则表示各自顶边位置，不能统一填零。

以 UI 正交显示、各级 scale 为 1 为例，字号与设计 Point Size 的比值可作为设计空间缩放的基础。fontSize 等于 Point Size 可作为参考尺寸，但最终屏幕像素还受 CanvasScaler、Transform 等影响。字号可以调整，只是位图放大可能变糊；建议固定设计字号并关闭 Auto Size，保持美术效果稳定。

4.6.4 持久化完整依赖

设置 Static、图集尺寸、实际 Padding、纹理与材质引用，按需关闭多图集扩展。将字体、材质和图集全部保存后，重新导入并验证查表与引用。

材质既可以作为 FontAsset 的子资产，也可以是独立 .mat；关键在于它必须持久化。图集若保留为独立 PNG，.asset 仍然依赖它，不能称为“一个文件包含所有内容”。如需单文件分发，材质与纹理都要作为子资产保存，并设计对应更新流程。

4.7 字符覆盖校验与业务接入

每套风格应收录实际需要显示的全部字符。伤害数字除 0～9 外，可能还需要正负号、小数点、百分号和倍率符号；战力显示若使用“万”“亿”等单位，也要同时制作并收录。固定文案应在生成或构建前检查覆盖情况，数值显示则检查格式化规则可能产生的完整字符集合。

缺字时记录明确告警，并按界面约定使用同风格替代字或拒绝该内容。普通字体回退无法补齐同风格的美术素材，不能用它掩盖缺字。只接收普通内容时关闭 Rich Text，避免特殊字符被当作格式控制信息。

在预制体中绑定字体、共享材质、设计字号和颜色，校准基线、字距、行高与显示范围。业务只设置 .text，组件存活期间保持字体、材质与图集引用有效。

大量伤害飘字应复用整个文本对象，合理控制同时显示数量。按内容变化更新，避免每帧重复格式化和强制刷新；数值转字符串与文字重建仍有成本，不能承诺零 GC。对滚动数字设置等宽 Advance，避免数值变化导致宽度抖动。

5、结果

这套方案的目标产物是一套 UE 人员可独立操作的生成工具、一份艺术字配置、一张共享 RGBA 图集，以及适配 Text 或 TMP 的静态字体资产。UE 人员通过工具更新字体，在组件上替换 Font / Font Asset，即可完成艺术字风格切换；已有业务代码继续通过原生 .text 属性更新内容。

单图集与共享材质有利于减少状态切换，但最终批次仍以 Frame Debugger 为准。按内容变化刷新文本，避免每帧重复格式化；字符串拼接、数值格式化和布局重建仍可能产生开销，不能承诺 .text 调用本身零 GC。

纹理预算可先按未压缩格式估算：1024×1024 RGBA32 约 4 MiB，2048×2048 约 16 MiB，均未包含 MipMap、可读副本及其他资产开销。优先按实际字符集选择图集尺寸，完成生成后关闭不再需要的运行时 Read/Write。
