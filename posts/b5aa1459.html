Unity-YooAssets运行时加载与卸载

YooAssets 运行时加载与卸载：从构建产物到资源生命周期

上一篇《YooAssets 打包流程：Builtin 管线》介绍了 Collector 的资源如何经过依赖分析，最终生成 AssetBundle、资源清单和版本文件。

现在，把这些文件放进安装包或上传到资源服务器。业务代码只传入一个 "Knight"，YooAssets 就能返回骑士预制体。但这中间还有几个问题：

  1. 运行时怎样使用打包生成的文件，找到资源及其依赖？
  2. AssetHandle、Provider、Loader 三层分别做什么，为什么需要拆成三层？
  3. 调用 Release 后发生了什么，什么时候才会真正卸载资源？

继续沿用上一篇的例子：骑士和法师分别放在两个 Bundle 中，共用一个包含材质和贴图的依赖包。两个界面同时需要骑士，另一个系统需要法师。加载时要复用资源，关闭一个界面时，又不能破坏其他使用者。

本文先建立 Package 的运行环境，再沿着这次资源请求，从清单查询一直追踪到最后一次卸载。

本文依据项目使用的 YooAsset 2.3.19 源码，讨论常规 AssetBundle 的异步加载与默认卸载机制。公开句柄类型名为 AssetHandle；本文所说的 Loader 层，在该版本中主要由 LoadBundleFileOperation 实现。示例用于说明调用关系和引用计数，未执行对应运行时实验。

一、加载之前，先初始化 Package

Package 对应 Collector 配置与构建时选择的资源包，名称需要保持一致。下面以 DefaultPackage、版本 1.0.0 为例，按顺序说明每一步使用的文件；文件名采用默认的空清单前缀，若配置了 PackageManifestPrefix，版本、校验和清单文件名还会带上该前缀。

  1. 初始化全局环境：调用 YooAssets.Initialize()，建立异步操作调度与更新驱动。这一步不读取 Package 的构建产物。
  2. 创建 Package：调用 YooAssets.CreatePackage("DefaultPackage")，在内存中创建并注册资源包；此时不读取版本、清单或 AB，后续业务复用该对象。
  3. 配置运行模式：离线使用 OfflinePlayModeParameters 和内置文件系统；联机使用 HostPlayModeParameters，通常组合内置与缓存文件系统，并提供远端地址服务。这一步只是准备参数，还没有读取资源文件。编辑器模拟模式则使用 EditorSimulateModeParameters，本文后续以真实 AB 加载为主。
  4. 初始化 Package：调用 package.InitializeAsync(parameters)，建立资源管理器与文件系统。默认内置文件系统读取安装包中的 BuildinCatalog.bytes，得到内置 Bundle 的文件目录；缓存文件系统扫描、校验已有的本地缓存文件。若额外开启复制内置清单配置，还会读取内置 .version，并按该版本复制 .hash 和 .bytes 到指定目录。
  5. 确定资源版本：调用 RequestPackageVersionAsync()，读取 DefaultPackage.version 中的版本字符串，例如 1.0.0。离线模式读取内置版本文件，常见联机配置从远端请求该文件；若业务直接指定版本，可跳过本次版本文件读取。
  6. 启用资源清单：调用 UpdatePackageManifestAsync("1.0.0")，取得 DefaultPackage_1.0.0.hash 与 DefaultPackage_1.0.0.bytes，用前者校验后者，再反序列化并激活清单。离线模式读取内置文件；常见联机配置使用缓存，缺失时从远端下载。
  7. 下载与加载资源：按清单需要预下载或按需获取实际的 AssetBundle 文件，再由 LoadAssetAsync 打开主包和依赖包、加载其中的 Unity 对象。AB 的实际文件名由清单记录，取决于构建时的命名方式。

Package 初始化成功表示运行环境已经建立，启用清单后才具备资源查询能力。 每个异步步骤都应检查状态，成功后再继续。使用 package.LoadAssetAsync 可直接指定 Package；使用 YooAssets.LoadAssetAsync 等静态快捷接口时，还需通过 YooAssets.SetDefaultPackage(package) 指定默认 Package。

二、从资源地址找到 Bundle

1. 清单连接地址、资源路径和 Bundle

清单启用后，LoadAssetAsync<GameObject>("Knight") 会通过 PackageManifest 将业务地址解析为资源路径，再查出主 Bundle 和依赖 Bundle。

在这个例子中，可以把清单的查询结果简化为：

PackageManifest 中的 AssetList 描述可寻址资源，BundleList 描述 Bundle 文件。普通单资源加载通过资源记录中的 BundleID 找到主包，通过 DependBundleIDs 找到依赖包；Bundle 记录再提供文件标识、大小、CRC 等信息。

运行时不再重新遍历 Collector，也不再调用编辑器 API 分析预制体依赖。构建阶段已经把收集与依赖分析的结果固化进清单，运行时按清单执行。

这也解释了前面两篇之间的连接：Collector 决定收集什么，构建流程确定包归属，运行时消费这些结果。

2. 文件系统决定去哪里拿 Bundle

确定 Bundle 后，还需要回答“这个文件在哪里”。这部分由运行模式配置的文件系统处理。

常见模式 文件来源
编辑器模拟模式 通过编辑器文件系统访问资源，不能替代真实 AB 加载验证
离线模式 使用随安装包携带的内置资源
联机模式 组合内置文件系统与缓存文件系统，必要时从服务器下载

在常见联机配置中，PlayModeImpl 按文件系统顺序判断 Bundle 的归属。内置文件系统通常通过 Catalog 判断是否包含该 Bundle；其余交由缓存文件系统处理。

缓存文件系统发现文件已经存在时，直接使用缓存。文件缺失时，默认可以按需下载；若配置禁止按需下载，则加载会失败，需要提前完成下载。

对于常规未加密磁盘 AB，文件准备好后，底层会调用 AssetBundle.LoadFromFileAsync 打开它。加密文件则经过配置的解密服务处理。

到这一步拿到的是可读取的 AssetBundle，里面的骑士预制体还没有完成加载。

三、为什么要分成 Handle、Provider、Loader 三层

假设两个界面同时请求骑士：

这两次调用应该分别记录使用者的持有关系，同时复用底层的资源加载。如果把“谁在使用”“加载哪个对象”“打开哪个文件”混在一起，复用和释放就很难协调。

YooAssets 用三层分别管理它们：

层次 管理的对象 核心职责
AssetHandle 一次加载调用的持有关系 向业务提供状态、结果与释放入口
Provider 一项资源加载操作 等待主包和依赖包，加载具体 Unity 对象，复用加载结果
Loader 一个 Bundle 的加载与持有状态 通过文件系统打开 Bundle，为多个 Provider 复用

1. Handle：每次调用都有自己的持有关系

每次 LoadAssetAsync 都会创建一个新的 AssetHandle。业务通过它等待完成、获取 AssetObject，并在不再使用时调用 Release()。

即使两个 Handle 指向同一个 Provider，它们仍然是两份独立的持有关系。释放第一个，不会直接释放第二个仍在使用的结果。

但普通 C# 变量赋值不产生新的持有关系：

这里两个变量指向同一个 Handle，引用计数不会增加。若两个模块需要独立释放，应分别发起加载请求，并各自保存自己的 Handle。

2. Provider：复用一次资源加载

ResourceManager 维护 ProviderDic。对于普通 LoadAssetAsync，会根据加载方式和 AssetInfo 的内部标识查找 Provider；找到可复用的 Provider 后，给它创建新的 Handle。

该内部标识由资源路径和请求类型等信息组成，不能直接理解为资源 .meta 中的 GUID。因此，本文讨论的复用前提是：同一个 Package 中，以相同加载方式和类型请求同一个资源。 场景、子资源、整包资源加载有各自的处理方式。

普通资源由 AssetProvider 负责。它需要完成两件事：先等主 Bundle 和依赖 Bundle 都准备好，再从主 Bundle 中加载目标对象。

重复请求可以共享正在进行的加载，也可以共享已经完成的结果。

3. Loader：复用 Bundle 文件

ResourceManager 还维护 LoaderDic，以 BundleName 查找 Loader。

骑士与法师是两个不同资源，需要不同 Provider，但它们依赖同一个材质包。这个共享包只需要一个 Loader，由两个 Provider 共同持有。

同样，同一个 Bundle 内的两个不同预制体可以拥有不同 Provider，同时共享主包 Loader。资源复用和 Bundle 复用发生在不同层，不能只用“同一个资源有没有加载过”来判断。

四、一次 LoadAssetAsync 怎样到达 Unity

把前面的索引查询与三层结构连起来，一次普通资源加载可以分成五步。

1. 用地址查到 AssetInfo

ResourcePackage.LoadAssetAsync<T> 先将 location 转换为 AssetInfo，得到真实资源路径、请求类型以及清单中的资源记录。

2. 获取或创建 Provider，并返回 Handle

ResourceManager 查找对应 Provider。若需要新建，Provider 会取得主包和依赖包的 Loader，并分别增加它们的引用计数。

无论复用还是新建 Provider，本次调用都会拿到自己的 Handle，并使 Provider 的引用计数加一。

3. Loader 准备主包和依赖包

Provider 启动相关 Loader，等待加载结果。Loader 通过文件系统获取文件并打开 Bundle，产出 BundleResult。

共享 Loader 让多个 Provider 等待同一个包的加载结果，不需要各自重复下载或打开。

4. Provider 从主包加载 Unity 对象

主包和依赖包全部成功后，AssetProvider 调用主包结果的 LoadAssetAsync。对于 AssetBundle，最终落到 Unity API：

依赖包提前准备好，是为了让 Unity 加载预制体时能够解析材质、贴图等跨包引用。

5. 通过 Handle 交付结果

Provider 保存加载结果并结束操作，Handle 随之表现为完成。业务仍需检查 Status：完成也可能意味着加载失败。

    A[业务调用 LoadAssetAsync] --> B[清单解析地址与资源路径]
    B --> C[获取或创建 Provider]
    C --> D[创建并返回本次 Handle]
    C --> E[主包 Loader]
    C --> F[依赖包 Loader]
    E --> G[文件系统准备文件并打开 Bundle]
    F --> G
    G --> H[Provider 等待全部 Bundle 成功]
    H --> I[主包调用 Unity LoadAssetAsync]
    I --> J[Provider 保存 Unity 对象]
    J --> K[Handle 提供状态和结果]

至此，拿到的是骑士预制体资源。若要在场景里显示骑士，还需要实例化；资源加载完成与实例创建是两个阶段。

五、共享资源时，引用计数究竟记在哪里

现在让两个界面分别加载骑士，再让另一个系统加载法师。全部加载完成后，关系如下：

    graph TD
    H1[界面 A 的 Knight Handle] --> P1[Knight Provider]
    H2[界面 B 的 Knight Handle] --> P1
    H3[Mage Handle] --> P2[Mage Provider]
    P1 --> L1[Knight Loader]
    P1 --> LS[Shared Loader]
    P2 --> L2[Mage Loader]
    P2 --> LS

这里存在两种引用计数：

对象 引用计数 计数来源
Knight Provider 2 两个 Knight Handle
Mage Provider 1 一个 Mage Handle
Knight Loader 1 Knight Provider
Mage Loader 1 Mage Provider
Shared Loader 2 Knight Provider 与 Mage Provider

Handle 增加 Provider 的引用；新建的 Provider 增加相关 Loader 的引用。 第二个骑士 Handle 复用了已有 Provider，因此不会再给骑士包和共享包各增加一次 Loader 引用。

这就是三层结构的价值：业务持有者可以有很多个，实际资源加载和文件加载仍然按各自粒度复用。

六、Release 为什么不等于立即卸载

1. Release 先结束当前调用者的持有关系

AssetHandle.Release() 沿用 HandleBase 的实现，主要做三件事：

  1. 从 Provider 移除当前 Handle，并减少 Provider 引用计数。
  2. 当 Provider 引用计数归零时，尝试触发配置允许的自动卸载。
  3. 断开 Handle 与 Provider 的关系，使当前 Handle 失效。

它首先表达的是“这个调用者不再需要资源”。它不直接等价于销毁实例，也不直接等价于卸载 Bundle。

当前版本初始化参数中的 AutoUnloadBundleWhenUnused 默认是 false。默认配置下，即使最后一个 Handle 已经释放，Provider 和 Loader 仍可能保留，等待后续清理。

因此，常见做法是在界面、关卡或资源批次的生命周期结束时释放各自 Handle，再在适当时机调用：

如果开启自动卸载，最后一个 Handle 释放时会尝试清理相关 Bundle；能否卸载仍然取决于加载状态和其他引用。

Provider 必须已经不处于加载阶段，并且没有 Handle 引用，才能正常销毁。销毁时，它才会归还自己对主包、依赖包 Loader 的持有。

这意味着：Provider 引用归零，与 Loader 引用减少之间，还隔着 Provider 的清理。 不能在每次 Handle 释放后，直接把同一次操作理解为“Bundle 引用也减一”。

3. Loader 归零后，还要检查依赖顺序

Loader 的正常销毁也有条件：没有正在进行的文件加载、引用计数归零，并满足包之间的依赖卸载约束。

清单初始化时会根据 Bundle 依赖建立反向引用关系。默认实现检查依赖当前包的其他 Bundle 是否已经销毁，以避免先卸掉仍被其他包依赖的包。

例如骑士包依赖共享材质包，需要先处理骑士包，再处理共享包。深层依赖可能需要多轮扫描，UnloadUnusedAssetsAsync 默认执行 10 轮。

这个参数是扫描次数，不是“无论资源何时加载完，都等待到全部释放”的保证。循环依赖也可能阻碍正常卸载，需要从分包关系上排查。

4. 用骑士与法师验证释放结果

假设上述资源均已加载完成，每个阶段释放后都执行一次无用资源清理：

操作 Provider 的变化 Bundle 的变化
界面 A 释放骑士 Handle Knight Provider 从 2 变为 1 骑士包和共享包继续保留
界面 B 释放骑士 Handle Knight Provider 归零，清理时销毁 骑士包可卸载；共享包仍由 Mage Provider 持有

如果只执行 Release，没有执行清理，也没有开启自动卸载，就不能预期表格中的 Bundle 立即卸载。

另外，加载中释放 Handle 不等于取消加载。特别是共享 Provider 时，其他调用者仍可能需要结果。加载尚未结束的 Provider 会暂时保留，之后需要有清理机会；一次过早的清理完成，不代表这些资源以后会自动消失。

七、实例还活着时，为什么不能提前释放 Handle

在《AssetBundle 加载与卸载》中，我们区分过 AssetBundle.Unload(false) 与 AssetBundle.Unload(true)。

本版本普通 AssetBundle 的卸载最终由 AssetBundleResult.UnloadBundleFile 调用 AssetBundle.Unload(true)。这会卸载从包中加载的资源对象。

因此，不能只根据“预制体已经实例化”就释放它的 Handle。实例仍可能引用包里的材质和贴图；这些资源卸载后，场景里的实例会出现引用失效。

1. 实例化不会自动增加 Handle 引用

无论使用 Object.Instantiate，还是 AssetHandle.InstantiateSync()，都不能理解为“新实例自动持有了一份 Handle”。实例创建本身没有建立这样的引用关系。

反方向也一样：Destroy(instance) 不会自动替业务释放加载 Handle。

需要让 Handle 的持有时间覆盖实例实际使用资源的时间。最简单的关系是：一个拥有者负责加载、保存 Handle、创建实例，并在实例结束使用后释放 Handle。

八、区分四种容易混淆的“清理”

操作 实际作用
Destroy(instance) 销毁业务创建的 Unity 实例
handle.Release() 结束本次加载调用的持有关系
package.UnloadUnusedAssetsAsync() 清理满足条件的 Provider、Loader，并卸载对应 Bundle
清理下载缓存 删除磁盘上的缓存文件，需要使用相应缓存管理流程

Bundle 从内存卸载后，下载缓存通常仍在磁盘上，下一次加载可以继续使用。Unity 的 Resources.UnloadUnusedAssets 和 C# GC 也属于不同层次，不能替代 YooAssets 的 Handle 释放。

另外还有两个使用边界：

  • 场景使用场景自己的卸载入口。 SceneHandle.UnloadAsync() 负责场景卸载流程，不能仅以普通 Release() 替代场景卸载。
  • UnloadAllAssetsAsync 用于整体清理。 它会强制销毁资源管理对象，使仍被业务保存的 Handle 失效。应在停止相关加载与使用后，用于整个 Package 的退出或重置，不能当成关闭普通界面的常规手段。

九、回到开头的三个问题

运行时如何使用构建产物？

版本文件决定使用哪一版清单，清单将加载地址映射到资源路径、主包与依赖包，文件系统再根据内置目录、缓存和远端配置取得 Bundle。Collector 的工作已经在构建阶段完成。

为什么分成三层？

Handle 记录调用者的持有关系，Provider 复用具体资源的加载，Loader 复用 Bundle 文件的加载。同一资源的多个使用者可以共享 Provider，不同资源也可以共享 Loader。

什么时候真正卸载？

Release 先归还调用者的使用权；Provider 无人使用且加载结束后，清理流程释放其 Loader 引用；Loader 再满足引用与依赖约束，才真正卸载 Bundle。业务应让 Handle 的生命周期覆盖所有实际使用该资源的实例。

从第四篇的资源分类、第五篇的构建，到这里的运行时加载，整条链路就连接起来了：配置决定资源范围，构建固化包与依赖关系，运行时按清单加载，再按持有关系释放。
