AlloyFramework(一)：一个游戏框架最少需要包含几个模块

发表于2026-11-10|更新于2026-11-10
|总字数:5.1k|阅读时长:14分钟

从重复需求出发，明确框架要解决什么

写一个 Unity Demo 时，我们通常希望尽快把核心玩法跑起来。但真正开始动手后就会发现：在玩法之外，总有一批基础逻辑需要先写。

程序从哪里启动？资源怎么加载？倒计时怎么管理？配置表怎么读取？怎样与服务器通信？资源和代码怎么更新？界面如何打开、关闭和切换？

换一个 Demo，这些问题依然存在。项目规模扩大之后，它们还会带来初始化顺序、资源释放、异步取消、异常恢复等更具体的问题。

这就是我想搭建 AlloyFramework 的原因：把项目中反复出现的通用需求整理出来，形成可以复用的基础能力，让开发新项目时能够把更多精力放在玩法和业务上。

这一篇先不讨论具体代码，也不把需求描述当作已经完成的功能清单。我们先回答一个问题：一个最小的游戏框架，需要替项目承担哪些职责？

一、统一的启动入口：让游戏按确定的顺序进入运行状态

Unity 提供了 Awake、OnEnable、Start 等生命周期方法，但这些方法并不会自动形成一条清晰的业务启动流程。

项目很小时，把初始化代码写在几个组件里似乎就够了。随着模块增加，依赖关系会逐渐显现：读取配置之前可能需要准备资源包，打开登录界面之前需要初始化 UI，而正式进入游戏之前，可能还要完成版本检查和更新。

如果这些操作散落在不同对象的生命周期中，启动顺序就很难直观看清，也容易出现某个模块已经开始工作、它依赖的模块却尚未准备好的问题。

因此，框架需要一个统一的启动入口，负责组织启动阶段和模块之间的依赖。

它至少应该满足以下需求：

  • 明确启动流程，让每个阶段的职责和执行顺序可以被理解。
  • 支持异步初始化，让资源准备、配置加载等操作可以被等待。
  • 提供启动状态与进度，方便界面展示当前正在进行的工作。
  • 在启动失败时保留明确的失败原因，并由业务决定重试、退出或其他处理方式。
  • 允许项目接入自己的业务步骤，例如登录、角色选择和首个场景加载。

统一入口并不意味着把所有初始化代码塞进一个巨大的类里。各模块仍然负责自己的初始化，入口负责把它们组织起来。

最终需要达到的效果是：当我们想知道“游戏是怎么启动的”时，可以找到一条明确的执行路径。

二、资源加载模块：统一资源获取与生命周期管理

游戏离不开资源。界面预制体、图集、音效、场景和配置文件，都需要在合适的时机加载，并在不再使用时释放。

Demo 阶段可以通过直接引用或简单加载快速完成需求。但进入实际项目后，资源来源和使用方式会更加复杂：编辑器下需要方便调试，发布后可能需要从资源包加载，部分资源还可能需要先下载。

如果每个业务模块都自行处理这些细节，加载代码会逐渐分散，释放规则也容易不一致。

资源模块的核心需求，是为业务提供统一的资源获取方式，并建立清晰的使用与释放约定。

它至少需要考虑：

  • 支持异步加载，避免耗时操作阻塞游戏流程。
  • 对资源定位建立统一规则，减少业务对物理路径和打包方式的依赖。
  • 明确资源句柄、实例和加载结果的所有权，知道由谁负责释放。
  • 在底层方案支持的基础上，管理重复加载、依赖资源和资源复用。
  • 提供失败结果与取消机制，处理资源不存在、下载失败或使用者提前退出等情况。

例如，一个界面在资源加载完成前就被关闭，稍后返回的加载结果应该如何处理？这类问题如果没有统一约定，很容易变成项目中的隐性泄漏。

资源模块的价值，不只是少写几行加载代码，更是让资源从申请到释放有一致的生命周期。

三、时间模块：为延时、计时和周期任务建立共同规则

技能冷却、活动倒计时、定时刷新、延迟关闭界面，这些需求都与时间有关。

直接在 Update 中累计时间，或者为每个功能单独写协程，都能完成某个具体需求。但当这样的逻辑越来越多时，暂停是否生效、对象销毁后任务是否继续、重复任务如何停止，就会变成反复处理的问题。

时间模块需要统一常见的定时任务，并明确不同时间语义。

它至少应该提供：

  • 一次性延时任务与周期任务。
  • 任务取消能力，以及与业务对象生命周期配套的清理方式。
  • 受游戏时间缩放影响和不受其影响的计时方式。
  • 一致的触发与异常处理规则，避免某个任务异常破坏其他任务的调度。

这里还需要区分游戏运行时间与真实世界时间。技能表现可能跟随游戏暂停，运营活动的结束时间通常不能因为游戏暂停就延后。

对于服务器决定的活动时间，框架可以提供服务器时间偏移或校准后的查询能力，但不能把本地倒计时当作最终结算依据。客户端展示剩余时间，关键规则仍需要由服务器确认。

时间模块的目标，是让业务说明“什么时候执行、是否跟随暂停、何时停止”，而不用反复实现计时细节。

四、配置表模块：让规则数据有统一的访问入口

角色属性、道具信息、关卡参数和技能数值，往往需要通过配置来管理。

把这些数据写在代码里，修改成本会随着内容增加而上升。改为配置表后，又会产生新的问题：表如何加载？什么时候可用？如何根据 ID 查找？找不到记录怎么办？表之间的引用如何验证？

配置模块需要把这些访问与生命周期问题组织起来，让业务可以稳定地读取规则数据。

它至少需要满足：

  • 统一配置初始化与读取入口，保证业务访问时所需数据已经就绪。
  • 提供明确的数据类型与查询方式，减少字符串约定和重复解析。
  • 对缺失记录、非法数据和引用错误提供可定位的信息。
  • 与资源加载及版本更新流程配合，保证当前代码能够正确读取当前配置。

配置生成工具和运行时配置模块可以各司其职。前者负责导出与生成，后者负责加载、访问以及项目需要的适配逻辑，没有必要重新实现已有工具已经解决的问题。

配置表也应与玩家存档区分开。道具的基础属性属于配置，玩家拥有多少道具属于运行时或存档数据，两者的修改方式和生命周期不同。

五、网络模块：统一通信流程，让业务专注于协议含义

联网项目中，登录、角色数据、背包操作和战斗交互都需要网络通信。

如果每个业务自行建立连接、序列化消息、等待返回并处理超时，很快就会出现大量重复代码，而且很难保持一致的错误处理行为。

网络模块需要提供稳定的通信基础能力，让业务更多关注“发送什么请求”和“如何处理结果”。

它通常需要考虑：

  • 连接建立、主动关闭以及连接状态通知。
  • 消息发送、接收、序列化和协议分发。
  • 请求与响应的对应关系，以及超时、取消和错误返回。
  • 服务器主动推送消息的订阅与解绑。
  • 根据项目需要提供心跳、断线检测和重连支持。

这里尤其需要划清基础能力与业务决策的边界。网络模块可以发现连接中断并尝试恢复连接，但是否重新登录、是否返回登录界面，需要业务决定。

同样，请求超时不一定代表服务器没有执行操作。购买、领取奖励等请求不能简单地一律自动重发，需要结合协议的幂等设计和业务状态处理。

对于纯单机 Demo，网络模块可以不启用。框架具备这一能力，不代表每个项目都必须依赖它。

六、热更新：让资源与代码具备可控的版本演进能力

项目发布之后，内容和逻辑仍然可能变化。更新一张图片、调整配置、增加活动内容，或者修复一段业务逻辑，都可能涉及版本更新。

热更新需要分别看待资源更新与代码更新。

资源更新关注资源清单、版本检查、差异下载、文件校验，以及新资源何时可以投入使用。代码更新则关注热更新代码的构建、加载、执行入口，以及它与主包代码之间的兼容关系。

两者需要协同，但并不是同一件事。

从框架需求出发，至少应该明确：

  • 如何识别本地版本与目标版本，以及本次需要更新的内容。
  • 如何展示下载进度，并处理网络失败、存储空间不足和校验失败。
  • 如何确认目标版本所需文件完整，避免在部分下载完成时切换到不可用状态。
  • 如何约束代码、配置和资源之间的兼容关系。
  • 更新完成后，如何交回启动流程并进入后续业务阶段。

代码热更新也有适用边界，它受目标平台、发布渠道和所选技术方案限制。不能假定所有平台都支持同样的方式，也不能假定所有改动都可以绕过主包更新。

因此，热更新的核心需求是建立可检查、可恢复的版本切换流程。至于采用何种资源方案和代码方案，可以在后续实现中展开。

七、UI 模块：统一界面的生命周期与交互秩序

UI 往往是项目中增长最快的部分之一。登录界面、主界面、背包、设置、提示框和加载界面，看起来只是不同的预制体，实际却共享很多管理需求。

界面如何打开和关闭？重复打开时复用还是新建？窗口之间如何排序？关闭弹窗后返回哪里？界面关闭时，消息监听和定时任务是否一起清理？

如果各个界面各自处理这些问题，随着数量增加，交互行为和资源管理就很容易失去一致性。

UI 模块至少需要提供：

  • 统一的界面打开、关闭与实例管理方式。
  • 明确的生命周期，让初始化、显示、隐藏和销毁各有职责。
  • 层级、遮罩与输入阻挡规则，维护合理的显示和交互顺序。
  • 界面参数传递方式，支持不同业务场景复用同一个界面。
  • 与资源模块配合的加载和释放规则。
  • 按项目需要支持返回栈、弹窗队列、界面缓存和打开关闭动效。
  • 移动端异形屏与安全区域适配，兼顾不同宽高比、横竖屏变化和系统手势区域。
  • 提供 AlloyFramework 自行封装的通用 UI 组件，例如无限列表，供业务界面复用。

移动端还需要专门考虑异形屏适配。刘海、挖孔、圆角以及底部手势区域，都可能影响界面的显示和操作。仅仅按照分辨率缩放 UI，并不能保证按钮、文字和重要信息始终处于合适的位置。

因此，AlloyFramework 的 UI 模块需要提供统一的安全区域适配能力，根据设备报告的可用区域调整内容布局，并在屏幕尺寸、横竖屏方向或安全区域发生变化时重新计算。对于底部手势区域等系统交互边界，还需要结合平台表现和项目需求预留合适的操作间距。

适配时也需要区分不同内容的布局要求：背景和全屏遮罩通常需要铺满屏幕，返回按钮、确认按钮以及关键文字则应放在安全区域内。框架应允许界面配置哪些容器需要适配、适配哪些边缘，以及是否增加额外留白，避免把整个界面统一缩进后产生背景露边或布局失衡。

这些规则应由 UI 模块集中提供，让业务界面通过配置使用，并结合不同宽高比和典型异形屏设备验证显示与点击效果，减少每个界面重复编写适配逻辑。

并不是所有界面都适合同一种管理策略。常驻主界面、可返回的功能页面和一次性提示框，生命周期可能不同，框架应该允许这些差异被明确表达。

UI 框架负责界面管理规则，背包如何排序、任务奖励如何领取等内容仍属于业务。把这个边界保留下来，框架才能被不同项目复用。

八、AlloyFramework 的实现思路：不重复造轮子，封装成熟方案供业务使用

前面七个模块描述了游戏开发中反复出现的需求。落实到 AlloyFramework 的实现上，并不需要把每个模块的底层能力都从头写一遍。

AlloyFramework 的一个基本原则就是不重复造轮子。对于已有成熟方案的领域，选择合适的工具，在其基础上做一层面向业务的封装，再把它们接入统一的框架流程。

其中，资源模块使用 YooAsset，配置表使用 Luban，代码热更新使用 HybridCLR。资源热更新由 YooAsset 承担相应的底层能力，框架负责将资源更新与代码加载组织起来。

1. 资源模块：基于 YooAsset，统一业务的资源使用方式

YooAsset 提供资源包管理、资源加载、版本清单和资源下载等能力。AlloyFramework 在此基础上封装业务常用的加载入口，并约定资源的持有和释放方式。

例如，UI 模块需要加载一个界面预制体时，可以通过框架的资源接口发起加载。资源包如何初始化、当前使用哪种运行模式，以及加载句柄如何配合界面生命周期释放，这些共性问题由框架统一组织。

这层封装的重点是建立适合项目使用的接口和生命周期规则，让各个业务模块遵循同一套约定。

2. 配置表模块：基于 Luban，衔接导出数据与运行时访问

Luban 负责配置数据的导出、校验和配套代码生成。AlloyFramework 的配置表模块围绕这些产物，组织运行时的数据加载、表实例初始化和统一访问入口。

业务需要读取一条道具配置时，应该能够通过明确的类型和 ID 获取数据。配置文件从哪里加载、何时完成初始化，以及初始化失败如何反馈，则由框架与资源模块、启动流程共同处理。

封装时可以保留 Luban 生成的强类型数据结构，把框架代码集中在加载和接入部分，避免为了统一接口再复制一套配置模型。

3. 热更新模块：结合 YooAsset 与 HybridCLR，组织完整更新流程

在热更新方案中，YooAsset 与 HybridCLR 各自承担不同的职责。

YooAsset 负责更新所需资源文件的版本管理与下载。热更新程序集等文件也可以作为资源交付，再由框架组织后续加载。HybridCLR 提供代码热更新所需的运行时能力，并支持按需要补充 AOT 元数据。

AlloyFramework 需要把这些能力接入启动流程：准备资源包、检查版本、下载所需文件、准备代码运行环境、加载热更新程序集，再进入对应的业务入口。

这里的封装价值在于流程衔接，包括阶段状态、进度反馈、失败处理，以及主包与热更新代码之间的入口约定。HybridCLR 本身不负责远端文件下载，资源下载完成也不代表代码已经完成加载，这些步骤需要由框架明确组织。

4. 框架层：把独立能力组织成业务可以直接使用的模块

采用成熟方案之后，AlloyFramework 仍然需要解决项目中的共性问题：模块如何初始化，资源由谁释放，配置何时可用，更新失败后如何反馈，以及 UI 如何使用这些基础能力。

这几层的职责可以这样理解：

层次 主要职责 示例
第三方方案 提供专业领域的基础能力 YooAsset、Luban、HybridCLR
AlloyFramework 封装常用接口，统一生命周期，组织模块协作 资源接口、配置初始化、更新流程、UI 管理
业务层 使用框架能力实现具体玩法和产品需求 登录、背包、任务、战斗

以打开背包界面为例，业务层发起打开界面的请求，UI 模块通过资源模块加载预制体，资源模块再使用 YooAsset 完成底层加载。界面展示道具信息时，通过配置模块访问 Luban 生成的配置数据。界面关闭后，则按照框架约定清理监听、定时任务和资源引用。

这样，第三方方案的接入细节集中在框架层，业务层能够围绕具体功能编写代码。后续升级依赖或调整接入方式时，也可以优先在封装位置处理，减少对业务代码的影响。

封装的范围应当由实际使用需求决定。对于稳定且适合直接使用的数据类型，可以保留；对于重复出现的初始化、加载、清理和错误处理逻辑，则应统一收进框架。没有必要把第三方库的每一个接口都重新包装一遍。

统一启动入口、时间、网络和 UI 模块也遵循同样的原则：围绕项目中重复出现的需求建立共同规则，并与已有基础能力协作。

因此，AlloyFramework 的实现会从这七类需求出发，结合 YooAsset、Luban 和 HybridCLR，把通用能力封装成业务层容易使用的模块。后续文章将围绕这些模块的具体接入和封装展开，说明每一层承担什么职责，以及它们如何在项目中配合运行。
