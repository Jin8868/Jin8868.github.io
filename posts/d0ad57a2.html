AlloyFramework(三)：框架循环与时间模块

发表于2026-11-11|更新于2026-11-12
|总字数:3.5k|阅读时长:12分钟

游戏业务中，经常需要“等一会儿，再执行一段逻辑”：提示显示两秒后关闭，角色死亡后延迟复活，或者等下一帧再刷新界面布局。

因此，框架需要提供一种方便的延迟写法，让业务能够直接表达“多久之后做什么”。例如，让提示两秒后关闭：

这里的 CloseTip 是业务自己的关闭方法，计时器负责等待并在到期后调用。返回的任务 ID 则用于提前取消：如果提示已经被玩家手动关闭，就可以取消原来的延迟任务。

从一次延迟继续往下看，还会遇到每秒刷新一次倒计时、每隔几帧检查一次状态、重复执行指定次数等需求。游戏暂停时，有的任务需要一起暂停，有的界面刷新则需要继续。这些都是同一类计时需求的不同用法。

Unity 的协程和 UniTask 都可以表达等待。AlloyFramework 在这里提供统一的时间模块，让需要回调调度的业务使用相同的添加、重复和取消方式，并明确时间缩放、执行次数与退出清理规则。

有了业务接口，接下来就要解决它如何运行：谁来推进时间，又由谁判断任务已经到期？

当前实现使用 Unity 的帧更新驱动计时器。GameLoop 先把 Unity 的更新回调统一分发给普通 C# 对象，时间模块再把调度器注册进去，每帧推进任务并执行到期回调。

这就是本篇将 GameLoopManager 和 TimerManager 放在一起介绍的原因：前者准备帧驱动，后者接入计时能力，共同支撑业务层简单的一次延迟调用。沿着上一篇的启动管线，它们的初始化与运行过程分为三步：

  1. 初始化游戏循环：创建 MonoFacade，接收 Unity 的 Update、LateUpdate 和 FixedUpdate。
  2. 初始化时间模块：创建 TimerScheduler，注册到 GameLoop 的更新列表。
  3. 业务添加定时任务：通过 AlloyTimer 创建任务，调度器每帧检查是否到期，到期后执行回调。

这里的方法返回 UniTask，用于保持统一的初始化接口。这两个模块当前的准备工作可以同步完成，所以返回 UniTask.CompletedTask，无需额外等待。

本文代码涉及 AlloyFramework、AlloyFramework.Timing、Cysharp.Threading.Tasks、System.Threading 和 UnityEngine 等命名空间。UniTask 在这里负责统一启动接口，计时器本身由 Unity 帧回调驱动。

二、GameLoopManager：建立统一的帧驱动

1. 管理器接入框架生命周期

因此，业务场景不用额外挂载一个更新管理对象，驱动对象由框架初始化时自动建立。

2. MonoFacade 将 Unity 回调交给 GameLoop

3. 用接口声明对象需要哪种更新

框架提供三种更新接口，分别对应 Unity 的三个更新阶段：

对象实现所需接口后，通过 GameLoop.Register 注册；不再需要更新时，调用 GameLoop.Unregister。一个对象可以实现多个接口，注册时会分别加入对应的更新集合。

例如，一个纯 C# 的业务对象需要每帧更新状态，只要实现 IUpdateable 并注册，就能收到 OnUpdate，不必为它单独创建 GameObject。

GameLoop 内部为三种接口分别维护注册集合，使用 List 遍历对象，使用 HashSet 避免重复注册。回调期间发生的注册和移除会暂存，分发结束后统一处理，避免遍历时直接改变列表。已标记移除的对象会在后续遍历中跳过，新注册对象则不会插入当前这轮分发。

三、TimerManager：把计时器接入游戏循环

1. 初始化统一的计时器入口

TimerScheduler 实现了 IUpdateable。注册后，每一帧的 Update 会沿着 MonoFacade → GameLoop → TimerScheduler.OnUpdate 这条路径推进计时。

这里的职责可以分成三层：TimerManager 接入启动与退出，AlloyTimer 提供业务调用入口，TimerScheduler 保存任务并执行调度。

2. TimerScheduler 如何判断任务到期

调度器内部维护活跃任务列表和按 ID 查找任务的字典。创建任务时，记录时间间隔或帧间隔、剩余执行次数、回调方法等信息，并返回一个唯一 ID。

每次 OnUpdate 遍历任务，按任务类型判断是否到期。核心判断如下：

任务到期后，调度器更新剩余执行次数；次数用完就移除任务，需要重复执行则计算下一次等待时间，然后调用回调。

当前实现中，每个任务每帧最多触发一次，卡顿期间错过的次数不会集中补发。按秒重复的任务会根据超出的时间计算下一个间隔；按帧重复的任务则从本次触发帧重新计算帧间隔。

这意味着计时器回调精度受帧更新影响。例如，设置一秒间隔，是在累计时间到期后的调度更新中执行，并不保证精确到某一个系统时钟瞬间。

3. 回调中的新增、取消与异常

回调本身可能继续创建或取消任务，所以调度器不会在遍历过程中直接插入新任务。新增任务先放入待添加列表，当前调度结束后再合入活跃列表。

取消任务时，会标记任务失效并移除 ID 索引，随后清理失效项。这样，一个回调取消另一个尚未执行的任务时，后者在当前轮中就可以被跳过。

定时器回调由 try/catch 单独保护，异常交给 AlloyDebug 记录，其他计时器仍然继续处理。重复任务不会仅因为回调抛出异常就自动取消；业务如果需要停止它，应主动移除。

这些处理让任务在执行过程中调整自身或其他任务时，仍然能够遵循确定的调度规则。

四、业务如何使用 AlloyTimer

业务等待框架初始化完成后，通过 AlloyTimer 添加任务，不需要自己创建 TimerManager 或 TimerScheduler。

常用接口如下：

接口 用途
DelaySeconds 延迟指定秒数执行一次
RepeatSeconds 按秒间隔执行指定次数或无限重复
DelayFrames 延迟指定帧数执行一次
RepeatFrames 按帧间隔执行指定次数或无限重复
Remove 使用任务 ID 取消指定任务

创建任务会返回 ID，业务需要保存自己负责的任务，并在界面关闭或对象退出时取消。当前计时器不会自动感知业务对象已经失效。

接口也支持带参数回调。业务可以通过泛型重载显式传入上下文，配合命名方法使用，避免通过捕获变量的 lambda 携带状态。

时间缩放与帧延迟的选择

按秒计时默认使用 Time.deltaTime，会受 Time.timeScale 影响。例如，跟随游戏速度变化的技能计时可以使用这个模式。设置 useTimeScale: false 后，使用 Time.unscaledDeltaTime，适合暂停时仍需更新的 UI。

按帧计时根据 Time.frameCount 判断，不受时间缩放影响，但仍然依赖游戏继续产生帧。它适合延后一帧刷新等需求，不代表真实世界中的固定时长。

DelaySeconds(0, ...) 会在后续调度更新中执行，不会在添加时立即调用；如果明确要求最早下一帧执行，应使用 DelayFrames(1, ...)。

非缩放计时也需要 Unity 持续更新，并不等于应用进入后台后仍持续运行的系统时钟。涉及服务器活动结束时间时，应根据目标时间重新计算剩余时间，让计时器承担定时刷新展示的职责。

五、退出时先停止计时器，再关闭游戏循环

启动顺序是 GameLoopManager → TimerManager，正常退出按相反顺序执行。

TimerManager 先调用 AlloyTimer.Shutdown，从 GameLoop 注销调度器、清空任务并解除引用。随后 GameLoopManager 调用 GameLoop.Shutdown，清理更新注册并释放驱动对象。

业务层通常只需要调用 Remove 清理自己保存的 ID。RemoveAll 会清除整个时间模块中的任务，应留给确实需要全局清理的场景。

这两个模块共同建立了框架的运行基础：GameLoop 将 Unity 帧回调提供给普通 C# 对象，Timer 在这个驱动上统一管理定时任务。后续模块既可以通过更新接口接入逐帧执行，也可以直接使用 AlloyTimer 完成延时和周期逻辑。
