AssetBundle 分包策略：哪些资源应该放进同一个包

前两篇《Unity-AssetBundle结构解析》和《Unity-AssetBundle加载与卸载》，分别讨论了 AB 文件内部的组织方式，以及资源加载后由谁持有、什么时候释放。

这一篇讨论构建时的问题：哪些资源应该放进同一个包？

一般项目会先按资源类型划分文件夹，把动画、纹理、预制体、材质、配置和字体分别存放，方便查找和日常管理：

如果直接把每个类型文件夹打成一个包，打包规则会很简单：Animations 对应一个动画包，Textures 对应一个纹理包，Prefabs 对应一个预制体包。

但随着项目资源增加，这些包也会越来越大。角色、战斗、场景和界面的纹理都可能进入同一个纹理包，各个玩法的预制体也可能进入同一个预制体包。文件夹按类型整理得很清楚，包内却混合了使用范围完全不同的资源。 这种直接按类型目录打包的方式，就会带来大包的问题。

一、大、小包的问题

1. 大包的问题：下载、更新和生命周期相互牵连

以整个 Textures 目录打成一个包为例，原本分别用于角色、战斗、场景和界面的纹理被绑在了一起，下载、更新和整包回收也因此相互牵连。

在常见的“下载完整文件、校验、落盘后加载”的流程里，首次进入一场战斗前，需要先准备相关包。如果当前角色的贴图位于全项目的纹理大包中，用户可能为了这一小部分资源下载整个大包，首次进入的等待就被无关内容拉长了。

更新也存在类似问题。在以完整 Bundle 为更新单位、没有二进制差分的方案中，只要包内容发生变化，客户端通常就需要下载新版本整包。 如果经常替换的活动图片与长期稳定的场景贴图都在纹理包中，仅修改一张活动图片，就可能让玩家把场景贴图所在的大文件一起重新下载。改动小，下载量却很大。

这里要区分“重新构建”与“产生新下载”：执行了构建，并不代表所有输出文件都变化；客户端下载哪些文件，取决于清单、文件标识和内容校验规则。依赖包变化是否进一步影响引用它的包，也要检查具体构建管线的产物，不能一概而论。

生命周期的牵连则发生在运行时。如果常驻界面的纹理与某个关卡的独占贴图都在纹理包中，关卡退出以后，界面仍然在使用该包。采用整包引用计数和 Unload(true) 回收策略时，就无法安全地把这个包整体卸载。此前已加载、且没有被其他机制回收的关卡贴图，可能因此保留得更久。包被各处依赖，整包回收就要等到最后一个使用者退出。

但不能把这种情况简化成“大包一打开，所有资源都进入内存，而且全部无法释放”。上一篇已经说明：

  • 打开包与加载具体资源是两步，包内未使用的资源不一定被实例化。
  • LZ4 支持按块解压；LZMA 的解压行为不同，首次加载成本还取决于加载 API 和缓存状态。
  • 包管理数据、已加载的 Native 资源和 GPU 数据有不同的生命周期。
  • Unload(false) 可以保留已加载资源并卸载包，但后续复用和回收需要另外管理。

因此，大包的主要风险是准备成本扩大，以及下载、更新和整包回收的边界过粗，并非文件体积直接等于常驻内存。

2. 碎包的问题：固定开销被重复支付

既然一个类型目录打一个包太大，那把目录里的每个资源分别打包呢？这就走向了另一个极端：每张图片、每个材质、每个动画都独立成包。

此时，加载一个角色就需要准备多个包，一场包含多种角色、怪物和技能特效的战斗，可能需要打开几十甚至上百个包。每个包都有文件访问、读取管理数据和维护状态的成本；远端缓存未命中时，还会增加请求、校验和调度工作。大量小包也会扩大清单、依赖图和加载管理器的维护规模。

异步加载、缓存和并发请求能够缓解等待，但不能消除这些固定开销。另一方面，包多也不代表每个包都一定触发一次物理磁盘随机读取，实际行为还受操作系统缓存、存储介质和加载实现影响。

这些资源如果每次都一起加载，拆分就未必减少实际下载或内存占用，却实实在在增加了访问次数。大包的问题是为少量需求付出过多成本，小包的问题是为同一批需求反复支付固定开销。

二、设计目标：控制牵连范围，也控制访问开销

大包与小包的缺点正好形成矛盾：合并能减少包数量，却扩大了下载、更新和整包回收的牵连范围；拆分能缩小这些范围，却增加了访问与管理开销。 因此，分包不能只追求包少，也不能只追求包小。

需要达到的目标可以归纳为四点：

  1. 首次加载少等待。 进入一个关卡或加载一个角色时，尽量只准备当前需要的内容，避免被无关资源拖慢。
  2. 结束使用后能释放。 尽量避免常驻资源与临时资源共包，让关卡、角色等独占资源有清晰的整包回收边界。
  3. 小改动少下载。 高频更新的配置或活动资源发生变化时，尽量不牵连大块稳定内容。
  4. 一次使用少开包。 总是一起使用的小资源适当合并，减少重复的文件访问、校验和加载调度开销。

前面三点要求缩小包的牵连范围，第四点又要求避免拆得过碎。接下来就需要寻找合适的资源边界，让拆分与合并分别服务于这些目标。

三、设计思路：按使用、释放和更新范围确定边界

要同时满足这些目标，首先要判断资源之间的关系，而不只是比较文件大小：

判断维度 需要回答的问题 对包边界的影响
使用时机 是否经常在同一次操作中被使用？ 经常一起使用的资源，适合先归为一组
释放时机 是否由相同业务持有，并在相近时机结束使用？ 生命周期相近，便于整包回收
更新节奏 是否通常随同一功能或活动一起变化？ 高频变化内容应与稳定内容隔离
共享范围 是某个功能独占，还是多个功能共同依赖？ 共享资源需要明确归属和使用者

一个实用的起点是：同一功能内，经常一起加载、一起结束使用、一起更新的资源，优先放进同一个包。

这几个条件可能冲突。例如，某个玩法的配置与战斗场景总是一起使用，但活动参数经常调整，场景模型和贴图却长期稳定。此时就值得为了缩小更新范围，将活动配置与场景资源分开，再用测量确认新增包的成本是否可接受。

据此，可以形成一套基本思路：以功能和使用范围作为初始分组，按生命周期划清释放边界，按更新频率隔离变化内容，再合并其中总是一起使用的小资源。共享依赖则单独检查，防止它把已经拆开的内容重新绑成一个大包。

四、分包方案：在类型目录下确定合理的包边界

开头的类型目录可以继续保留，用于资源查找和日常管理。资源较多时，也可以在类型目录下按用途细分，例如 Textures/Characters、Textures/Levels。

需要调整的是直接按整个类型目录打包的规则。文件夹分类不要求与 AB 包一一对应。 同一类型的资源可以分到不同包，不同类型的资源也可以因为属于同一功能而放进同一个包。具体边界再结合使用范围、更新频率和释放时机判断。

1. 按功能分组，减少无关内容的加载与保留

为了缩小首次准备的资源范围，并让独占资源能随功能退出而释放，可以先按角色、关卡、玩法等使用范围分组。

例如，角色独占资源、关卡独占资源和基础配置可以分别归组：

骑士专用的 Prefab、Mesh、材质、贴图和基础动画，先归入 character.knight.bundle；森林关卡独占的场景资源归入 level.forest.bundle。这些是初始分组，最终归属由打包配置表达，不必强制一个文件夹对应一个包。

“一个角色或一个关卡先作为一组”适合用作起点，但还要考虑实际行为：

  • 角色的基础模型、专用材质和必用动画，通常适合共包。
  • 可选皮肤、特殊形态和很少触发的大型技能特效，可以独立，避免加载角色就必须准备全部内容。
  • 多个关卡共同使用的怪物和战斗特效，应另行处理共享归属。
  • 大场景可以按进入区域拆分，避免为了出生点附近的内容准备整个地图。
  • 配置可按基础系统、战斗玩法和活动划分，但若运行时始终一次读取全部配置，也没有必要仅因表多就拆成大量小包。

独立界面也可以采用相同的判断方式。分组应跟随真实的使用与释放范围，而不只是资源类型或文件数量。

2. 按更新频率拆分，避免小改动牵连大资源

为了减少小改动带来的下载量，活动资源适合与稳定资源隔离，还应该避免不同活动之间互相牵连。

例如，一个限时战斗活动可以进一步分为：

包 主要内容 拆分依据
activity.autumn.config.bundle 关卡参数、奖励和活动规则配置 调整频繁，适合独立更新
activity.autumn.level.bundle 活动场景模型和环境贴图 内容相对稳定，进入关卡时使用
activity.autumn.boss.bundle 首领模型、动画和专用特效 进入首领战时才需要

这也不是要求每个活动固定拆成三个包。如果活动很小，所有内容都随版本一起替换，合并成一个活动包可能更合适。

同样，活动配置与基础配置也不一定适合共包：两者虽然都是配置，更新节奏和使用范围却可能不同。如果配置输出为 AB 包内的 TextAsset 或 ScriptableObject，可以采用这样的拆分；如果使用独立配置文件，则应在对应的文件更新策略中处理。

字体通常比活动资源稳定，适合独立管理，但新增语言、字形或修改字体图集时，它仍然可能更新。分包应依据实际变更记录，而不是假定某一类型永远不变。

3. 检查共享依赖，避免重复与不必要的牵连

只分配入口 Prefab 的包名，还不足以确定最终内容。需要继续检查它们引用的材质、纹理、字体和 Shader。

在原生 AssetBundle 构建中，如果两个包引用同一个资源，而该资源没有明确分配到独立包，它可能作为隐式依赖被分别包含，导致重复打包。不同框架可能自动提取共享依赖，最终仍应以构建报告为准。[2]

例如，两个关卡都会出现骑士与哥布林，而它们的材质又依赖同一份 Shader 资源，可以明确整理为：

    flowchart TD
    Forest["森林关卡包"] --> Knight["骑士包"]
    Dungeon["地牢关卡包"] --> Knight
    Forest --> Goblin["哥布林包"]
    Dungeon --> Goblin
    Knight --> Shader["共享 Shader 包"]
    Goblin --> Shader

图中的箭头表示构建后确认的序列化依赖关系。如果角色由刷怪配置中的地址指定，再在运行时单独加载，它属于业务加载关系，需要另外记录，不能指望构建清单自动发现。

共享资源提取也有代价。把一切都提取到一个 shared.bundle，可能重新形成“任何模块都依赖，退出任何模块都无法整包卸载”的大包。

因此，共享包还要按用途和生命周期划分。例如，常用字体、基础 UI 组件、战斗共享特效，可以属于不同的共享包。不要因为都被多个地方使用，就把它们放在一起。

可以采用这样的判断顺序：

  1. 只有一个功能使用的资源，优先跟随该功能。
  2. 多个功能使用、体积明显或对象身份需要一致的资源，优先明确共享归属。
  3. 很小、稳定且互不同时使用的资源，可评估允许少量重复，换取更少的跨包依赖。
  4. 允许重复必须是有记录的取舍，并核查下载体积和运行时副本，不能由隐式依赖偶然决定。

尤其要避免让地牢关卡依赖森林关卡包，只为了取得一个共用怪物。应将怪物移到合理的共享范围，而不是把森林关卡整个变成地牢的依赖。

依赖方向也应尽量清晰：业务包依赖共享包，共享包不反过来依赖具体业务。发现循环依赖时，要检查是否可以重新归属资源、提取共同部分，或合并本来就无法独立使用的内容。

4. 图集先按使用范围组织，再决定包归属

图集不能仅凭“都是小图标”就合并成一个全局大图集。

图集中的 Sprite 会共享底层纹理页。加载某个 Sprite 时，通常也需要它对应的图集页，因此图集会让原本独立的小图在加载和内存占用上产生关联。一个 SpriteAtlas 也可能包含多张纹理页，不能一律理解为“一张图用了，整个 Atlas 所有页都必然加载”。

可以先按用途组织：背包常用图标一组、商城专用图标一组、活动图片一组，少量全局基础图标单独组织。活动横幅尤其不宜混进稳定的基础 UI 图集，否则修改横幅可能导致图集纹理和相关包一起变化。

当某个界面的图集只有它自己使用，并且更新、释放时机一致时，可以与该界面共包；被多个界面使用时，再考虑独立共享包。没有必要固定成“每个图集必有独立包”。

SpriteAtlas 的打包模式、Include in Build 设置和构建管线会影响最终依赖与重复情况。不能只检查源目录，还要确认构建后图集纹理究竟进入了哪些包。

5. 合并零散小资源，控制访问与管理开销

为了避免包拆得过碎，可以适当合并零散小资源。但“零散”只是文件组织上的描述，不是足够的分包理由，合并仍然需要限定使用范围。

某个关卡专用的几段机关动画、几张小贴图和几个小材质，如果总是随关卡一起使用，可以合进关卡包。同一玩法中总是一起读取、更新节奏一致的小配置，也可以合成一个配置包。多个战斗玩法共用的小特效，则可以归入战斗范围内的共享包。

反过来，把登录提示图、战斗音效、活动图标和过场材质全部塞进 misc.bundle，只会制造新的耦合。

合并前至少检查三件事：使用范围是否接近，更新节奏是否一致，是否会让一个长生命周期资源拖住大量短生命周期资源。

6. 最后用体积和访问开销修正粒度

完成逻辑分组后，再看实际构建产物的大小、数量和依赖关系。

如果一个功能包明显偏大，优先寻找有业务意义的切分点：按角色、关卡区域、语言、可选高清资源或进入阶段拆分，而不是直接按固定大小机械切块。

如果一次进入战斗、加载角色或读取配置要访问大量微小包，就优先合并其中总是一起请求、释放时机接近、更新节奏一致的部分。

不建议将“每包固定 5 MB”之类数字当作通用标准。压缩后的文件大小影响下载，但不能直接反映资源加载后的内存；同样大小的配置、纹理和音频，也可能有完全不同的读取与使用方式。

可以为项目设定大包和碎包的检查阈值，但阈值应触发分析，而不是自动决定结果。先解决业务边界，再用目标设备上的数据修正粒度。

7. 把规则沉淀到构建流程

当初始方案稳定后，可以让构建报告持续回答这些问题：

  • 哪些资源被重复包含，重复了多少字节？
  • 哪些包有大量反向依赖，是否混入了无关功能？
  • 哪些入口需要准备很多包，依赖链是否过深？
  • 哪些高频更新资源与大块稳定内容共包？
  • 哪些包体积或依赖关系相比上个版本发生了异常变化？

构建环境也应保持可追踪。Unity 版本、导入设置、压缩方式或构建配置变化，都可能扩大产物变化范围。分包只能降低合理边界内的牵连，不能保证任意构建之间都只有被编辑的资源发生变化。

五、最终落地：目录怎么细分，具体打成哪些包

前面的判断可以收敛为一个默认方案：保留类型目录，在类型目录下按角色、关卡、功能和更新范围细分；将选定的子目录作为打包单元，每个单元默认一个包。总是一起使用的小目录，可以在打包配置中明确合并到同一个包。

因此，Textures 下确实需要继续细分，但不是把所有层级的文件夹各打一个包，也不是无条件把每个最深层目录打一个包。需要明确选定打包边界：选中 Textures/Characters/Knight 作为单元后，其内部子目录默认一起归入这个单元，不再自动生成额外包；需要独立更新的内容则提前移出这个单元。

2. 目录与最终包的对应关系

下表中的路径均相对于 Assets/Res/。包名用于说明归属，实际文件名可以由构建流程生成。

目录范围 最终包 本例采用的规则 后续资源添加与调整
Prefabs/Characters/Knight/、Textures/Characters/Knight/、Materials/Characters/Knight/、Animations/Characters/Knight/ character.knight.bundle 四个目录明确合并成一个角色包，专用资源随角色一起加载和释放 骑士基础资源加入对应目录，沿用同一包；新角色建立独立目录和包，可选皮肤另设目录和包
Prefabs/Levels/Forest/ level.forest.prefabs.bundle 场景物件单独一个包 同一区域物件加入现有目录；新关卡另建目录和包；关卡过大时按区域拆分，替换原来的整体打包范围
Textures/Levels/Forest/ level.forest.textures.bundle 较大的关卡贴图目录独立成包，不与其他关卡贴图混合 普通新增贴图沿用该包；需分区加载时，按 Entrance、BossArea 等子目录分别打包，取消原整体目录的打包范围
Prefabs/UI/Inventory/、Textures/UI/Inventory/ ui.inventory.bundle 本例假设界面较小且资源独占，两个目录合并成一个界面包 新增独占资源加入对应目录；独立界面另建包；可选高清预览等大资源单独拆出
Textures/Activities/Autumn/Banners/ activity.autumn.banners.bundle 高频更新图片单独一个包，与稳定贴图隔离 同批替换图片沿用该包；其他活动另建目录和包；需要单独轮换的大图再拆为独立单元
Prefabs/Battle/SharedEffects/、Materials/Battle/SharedEffects/ battle.shared.effects.bundle 本例中体积较小、共同使用的特效与专用材质合并 同范围的小特效继续加入；大型或仅特定玩法使用的特效另建包，避免共享包持续膨胀
Configs/Core/ config.core.bundle 一组基础配置一个包，不按每张表拆包 同加载、同更新的基础配置继续加入；高频变化或仅特定功能使用的配置移至独立目录和包
Configs/Battle/ config.battle.bundle 战斗配置单独一个包 始终一起读取的战斗表继续共包；按需读取且规模较大的玩法配置再按玩法拆分
Configs/Activities/Autumn/ config.activity.autumn.bundle 当前活动配置一个包，避免牵连基础配置与其他活动 当前活动配置沿用该包；新活动建立独立目录和包，不并入基础配置包
Fonts/Common/ font.common.bundle 常用字体独立一个包，作为共享依赖 必需的常用字体继续加入；可选语言或特定功能字体另建目录和包
Fonts/Languages/Japanese/ font.japanese.bundle 可选语言字体独立一个包，按语言需求准备 日语字体沿用该包；新增语言建立各自目录和包

本例的配置假定为需要进入 AB 的 TextAsset 或 ScriptableObject。角色模型与 Mesh 也假定由角色目录中的源资产提供；实际项目若另设 Models 目录，应将对应目录加入角色包的归属配置。

这些目录划分不会自动产生跨目录合包。四个骑士目录要生成同一个包，必须在构建配置中把它们明确映射到同一个 Bundle。 如果只是对每个目录分别打包，它们仍然会生成四个包。

每份资源应有唯一的最终包归属。被角色、特效或关卡共同引用的材质、纹理和 Shader，要先识别为共享依赖，再明确其归属，不能为了凑齐目录内容而重复收进多个包。图集纹理的实际归属还要结合前文的图集规则检查。

六、怎么判断拆分与合并是否值得

分包之后，需要回答的仍然是开头的矛盾：拆小后节省的下载、更新和资源保留成本，是否值得新增的文件访问与包管理开销；合并后减少的访问次数，又是否以过多无关内容为代价。

这些是设计预期，是否有效，需要构建对比和目标设备测量。下面的例子只说明验证方法，不代表实测成绩。

1. 同时观察入口包及其全部依赖

假设关卡入口包只有 1 MB，但它依赖一个 100 MB 的公共包。若本地缓存都未命中，且两个包都需要完整下载，那么首次进入仍需准备约 101 MB，而不是 1 MB。

评估一个功能时，应统计“入口包与递归依赖包的去重集合”。再根据本地缓存和已经加载的包，计算本次真正新增的下载与加载成本。仅靠静态依赖清单仍不足以涵盖运行时按地址加载的可选资源，需要结合实际请求记录补充。

2. 比较调整前后的同一组操作

验证操作 记录内容 判断依据
无本地下载缓存，首次进入战斗关卡 新增下载字节、请求数、从进入到可操作的耗时 首次准备范围是否缩小，实际等待是否改善
已有文件缓存，再次加载同一组角色 打开包耗时、文件访问、资源加载和主线程峰值 分包是否引入了过多固定开销
基础系统仍运行，退出战斗关卡 包持有关系、已加载资源及内存快照 关卡独占资源是否按策略释放，常驻资源是否仍有效
反复进入两个共享怪物的关卡 包重载次数、资源副本、帧耗时 是否产生卸载后立即重载的抖动
一次读取玩法所需的多份配置 访问包数、总耗时和加载次数 配置是否拆得过碎，合并是否更划算
仅修改活动配置，发布下一版 变化包列表、实际新增下载量 更新是否主要限制在预期范围
检查共享材质、Shader 和战斗特效 构建重复报告、运行时资源实例 是否避免无意重复，实际归属是否符合设计

运行时检查应在相同目标设备、相同构建配置和可比较的缓存条件下进行，并重复采样。Unity Profiler 用于分析加载和帧耗时，Memory Profiler 用于检查资源对象、占用及持有关系。不能只看退出关卡后进程内存是否立即下降。

如果玩家连续进入的两个关卡都会使用同一种怪物，刚退出前一关就立即释放怪物包，可能导致下一关重新加载。此时可以保留有限时间的缓存，或在更大的业务阶段结束后释放。缓存策略与包边界需要配合，不能只靠继续拆包解决。

3. 用一次小修改验证更新边界

可以保留基线版本 A，仅修改一份活动奖励配置后构建版本 B，比较两个版本的清单、文件 Hash 和下载计划。

假设配置原来与场景资源共处在 80 MB 的包内，拆分后位于 200 KB 的配置包内；在没有差分下载、且只有这个包变化的前提下，该次更新的资源文件下载量就从 80 MB 缩小到 200 KB。这里的数字是示意，不包含清单和协议等额外开销。

如果修改一份配置却导致多个稳定包变化，应进一步检查引用关系、资源归属以及构建环境差异。验证的重点是解释实际变化的文件，而不只是确认分包配置里写了几个名字。

实际落地时，可以先采用这样的顺序：按功能确定独占资源，按更新节奏隔离变化内容，按依赖关系处理共享资源，再在相近的使用与释放范围内合并小资源，最后用构建和运行数据调整粒度。

决定哪些资源放进同一个包，最终是在判断：它们是否值得一起准备、是否适合一起保留，以及一次修改是否应该让它们一起更新。把本来就一起使用的小资源合并，把使用、释放和更新范围明显不同的内容拆开，才能同时控制大包的牵连与小包的开销。
