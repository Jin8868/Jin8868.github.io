AlloyFramework的实现(五) - 业务代码准备、配置与数据模型

发表于2026-11-17|更新于2026-11-17
|总字数:6.5k|阅读时长:21分钟

上一篇介绍了 AlloyFramework 的资源管理系统。这一篇继续沿启动流程，介绍业务代码准备、配置预加载和 Model 管理，分别说明它们解决的问题与具体实现。

内容以当前框架与 game-template 源码为准；HybridCLR 重点介绍启动时的校验、加载和反射安装流程，完整构建发布另行讨论。

一、先看整体启动流程

这三个处理过程也有先后依赖：资源服务先就绪，随后准备业务代码，由业务安装配置加载器，再执行配置加载和 Model 管理器初始化。当前 FrameworkStartupPipeline 中的顺序如下：

配置文件需要通过资源系统取得，具体配置加载器又定义在业务程序集中，所以这个顺序体现的是依赖关系。PrepareGameCodeStep 是代码准备步骤，Config 和 Model 则作为框架系统参与初始化与退出。

    Install --> Loader["登记业务配置加载器"]

这张图有两个容易混淆的地方。第一，业务安装入口不等于正式业务入口：前者只安装配置加载器等早期约定，后者要等框架系统全部就绪后才执行。第二，ModelManager 就绪不等于所有 Model 已创建：类型注册与实例初始化发生在后续阶段。下面说明各个系统的详细逻辑。

二、业务代码接入：通过反射调用约定的安装入口

有些项目需要热更新，但是有些项目又不需要热更新。所以框架不应该直接写死对应的逻辑，而是给项目选择的空间。而实现选择的方式可以是：1、配置。2、反射。我这里选用的反射的方式，因为热更新可能有多种的实现方式(ILRuntime、InjectFix、HybirdCLR)，为了后续的拓展这里采用约定安装入口、通过反射调用的方式。两种代码准备服务分别负责取得程序集，随后执行相同的安装约定，为后续配置加载提供接入点。

2. DefaultGameCodePreparation：使用主包内的业务代码

项目侧的 DefaultGameCodePreparation 遍历当前已加载程序集，按配置名称找到业务程序集，再查找公开静态的无参 Install 方法。

它不读取热更新 DLL，也不执行 Assembly.Load。Default 模式的前提是业务程序集已经静态编译进主包并可被找到。

准备成功后，结果记录业务程序集和完成标记，后续启动步骤可以继续使用这份结果。

3. HybridCLRCodePreparation：校验、加载并安装热更新代码

HybridCLRCodePreparation 负责准备热更新业务代码。Editor 中直接复用 Unity 已加载的程序集；Player 中则通过资源系统取得代码文件，完成以下流程：

  1. 读取代码清单：准备 CodePackage，取得元数据与业务 DLL 的文件信息。
  2. 校验内容：检查平台、主包基线和业务入口是否匹配，并校验文件哈希。
  3. 补充 AOT 元数据：调用 HybridCLR 接口，为相应 AOT 程序集补充运行所需的元数据。
  4. 加载业务程序集：按清单顺序调用 Assembly.Load，保存目标业务程序集。
  5. 执行安装入口：反射调用业务 Install 方法，注册配置加载器，并标记准备完成。

完成后，启动管线继续执行 Config 初始化。Editor 复用已有代码，真实热更新仍需在目标平台的 IL2CPP Player 中验证；进入元数据或程序集加载阶段后，当前实现无法回滚，后续失败需要重启 Player。

三、配置预加载：把选择权交给业务，把调用时机交给框架

进入首个界面之前可能就需要 UI 跳转表，而战斗配置可以等到进入战斗前再准备。不同项目的表结构、文件格式和使用时机也不一样，框架怎样让业务自己决定哪些表需要提前加载，同时保证后续模块使用时已经准备好？

为此，框架提供加载器注册入口，由业务决定要提前准备的配置集合；ConfigManager 在启动流程中调用它，并等待这批配置可用。具体文件读取和构表仍由业务实现。

1. 配置系统同样分为业务层、框架层和实现层

业务需要的是“取得某个 ID 对应的配置”，如果各个功能直接操作 Luban 的 Tables 和生成表，配置加载、查询和释放就会与具体配置工具绑定。因此，配置系统也沿用前面资源系统的三层结构：业务层 → 框架层 → 实现层，当前实现层使用 Luban，由框架接口封装它的加载与查询能力。

    Business["业务层：界面、角色等功能读取配置"]
    Framework["框架层：AlloyConfig 与 ConfigManager"]
    Contract["框架契约：IAlloyConfigLoader 与 IAlloyConfigTable"]
    Implementation["实现层：配置加载器与表适配器"]
    Luban["Luban：ByteBuf、Tables 与生成表"]

    Framework -->|通过接口调用| Contract

层级 当前对应代码 职责
业务层 使用配置的界面、角色等业务功能 表达查询需求，使用配置驱动业务行为
框架层 AlloyConfig、ConfigManager 及配置接口 统一加载时机、表注册、按类型与 ID 查询，以及退出清理
实现层 GameConfigLoader、GameConfig、UIJumpConfigTableProvider 对 Luban 的适配 读取配置资源，使用 Luban 解析并构造表，将生成表的查询方式适配为框架接口

运行时由框架通过接口调用具体实现；接口定义在框架侧，Luban 适配代码实现这些接口。框架的通用管理逻辑不需要直接引用项目生成的 Tables 类。

当前 Luban 适配代码放在游戏工程中，因为它需要知道这个项目生成了哪些表。这里按职责划分层次：GameConfigLoader 虽然位于项目侧，但在这条调用链中承担的是实现层的加载适配职责；普通业务功能通过 AlloyConfig 查询，不必自己构造 ByteBuf 或管理 Tables 的加载过程。

例如，查询 UI 跳转配置时，业务调用 AlloyConfig.Get<UIJumpConfig>(id)，框架找到已注册的 IAlloyConfigTable<UIJumpConfig>，再由 UIJumpConfigTableProvider 调用 Luban 生成表的 GetOrDefault。如果以后改用其他配置方案，需要替换加载器和表适配器，框架的通用加载与查询流程可以继续使用。

当前封装覆盖加载、表查询与生命周期，返回的配置记录仍是项目生成的 UIJumpConfig 类型，并没有额外转换为独立的数据类型。因此，更换生成方案时还需要保持记录结构兼容，不能仅凭三层接口就认为所有业务代码都无需调整。

2. IAlloyConfigLoader：给业务提供配置表预加载入口

IAlloyConfigLoader 是框架留给业务层的预加载入口：哪些配置表需要在启动时提前准备，由业务自己决定。 框架负责在资源和业务代码就绪后调用加载器，并等待它完成，再继续初始化后面的模块。

例如，进入首个界面之前就需要 UI 跳转配置，业务可以在这个入口提前加载；只有进入战斗才需要的配置，则可以留给后续业务流程准备。框架不需要知道项目有多少张表，也不替业务决定每张表的加载时机。

4. 加载失败不能留下可被误用的半成品

AlloyConfig.LoadAllAsync 先检查加载器是否安装，只有 LoadAsync 成功后才设置 IsLoaded。加载失败时清空已注册表，并调用加载器的 Unload。

这要求业务加载器能够处理部分完成的状态。例如，文件已经取得但构表失败，或者第一张表已注册而第二张表加载失败，都应释放自己持有的资源。

配置加载完成后不能直接替换加载器。当前代码提供启动期加载与卸载，不应把 SetLoader 理解为运行中的配置热切换接口。

四、Model 管理：用统一生命周期代替各自维护单例

玩家、背包、任务和商店都有自己的数据。如果每个 Model 都写一个静态 Instance，对象创建、初始化、重置与销毁就会分散在各个类中。切换账号或退出游戏时，也容易遗漏某个对象的清理。怎样保留统一访问的便利，又不用让每个 Model 都变成单例？

1. 把 Model 的生命周期交给框架

ModelManager 提供一个集中的对象管理入口：框架持有 Model，并在约定时机调用初始化、重置和销毁方法，业务通过管理器取得对象。 各个 Model 因此不用再重复维护自己的静态实例与创建逻辑。

原先设想的使用方式是：业务创建具体 Model 实例并注册进来，框架接管它的生命周期；业务需要使用时，再向管理器取得对应对象。Model 自身只负责业务数据和行为，不再负责维护全局实例。

当前源码采用了略有不同的创建方式：注册 Model 类型，首次获取时由框架创建实例。 现有接口是 Register<T>()，尚未提供直接接收已有 Model 对象的注册接口。下文按当前接口说明用法，二者共同的设计目的都是把实例管理集中到框架，而不是让每个业务 Model 各自成为单例。

ModelManager.Instance 是统一访问入口，各个业务 Model 类型无需再定义自己的静态 Instance。同一类型在管理器内只有一份实例，是管理器的持有规则，并不要求 Model 类本身采用单例写法。

2. 配置与 Model 分别存什么

配置通常描述规则，例如道具价格、角色基础属性和界面跳转关系；Model 保存运行时状态，例如当前金币、角色当前生命值和背包内容。

数据 更适合的位置
某类道具的基础价格 配置表
玩家当前持有的道具数量 背包 Model
角色的初始生命值规则 配置表
本次战斗中的剩余生命值 战斗或角色 Model

Model 可以读取配置建立初始状态，但不应把玩家当前状态直接写回共享配置记录。当前配置接口并不强制记录不可变，这个边界仍需要业务代码遵守。

3. 当前实现：注册类型，由框架创建和持有实例

ModelManager.InitializeAsync 主要检查是否重复初始化，设置可用状态，并发布 ModelManager.Instance。它不会扫描业务程序集，也不会创建全部 Model。

框架完成其余系统初始化后，业务启动管线执行 RegisterGameModelsStep，由它调用 GameModelRegistration.RegisterModels()。当前模板中的集中注册方法还是空的，新增业务类型后需要显式添加注册。

业务通过 ModelManager.Instance.Register<T>() 登记类型和创建方式，不触发初始化；首次调用 ModelManager.Instance.Get<T>() 时才创建并初始化对应实例。

同一管理器内，同一个注册类型对应一个实例。后续再次 Get 返回同一实例；未注册类型会报错，TryGet 则只读取已经创建的实例，不触发创建。

这样的 Model 不适合直接表达“场景中每个敌人各有一个同类型实例”。可以由一个战斗 Model 管理多份敌人数据，或使用其他对象生命周期方案，不应把按类型唯一的管理器当成通用对象池。

这些生命周期都是同步方法。需要异步加载存档、请求网络或准备资源时，应在明确的业务异步步骤中完成，再将结果交给 Model；不能在 OnInitialize 中启动无人等待的任务，却让调用方误以为数据已经就绪。

五、Model 的生命周期为何不能只靠一个字典

1. 首次获取成功后才公开实例

首次 Get<T>() 的过程是：创建对象，调用初始化，成功后写入注册记录，并加入已创建列表。

框架不会在初始化前先把对象交出去，避免其他业务读到半初始化状态。如果初始化失败，会尝试销毁本次对象，同时保留类型注册，让后续访问仍可尝试创建。

Model 初始化期间可以读取其他 Model。例如 A 初始化时获取 B，管理器会先完成 B，再完成 A。但如果 A 获取 B、B 又获取 A，正在初始化的标记会阻止这条循环依赖，并抛出异常。

需要注意，这不是跨 Model 的事务回滚：A 初始化失败时，此前已经成功创建的 B 不会因此自动销毁。它仍由管理器持有，直到后续生命周期操作或框架退出。

2. Reset、Remove 和 Clear 的含义不同

方法 实例处理 类型注册
Reset<T>() 重置已创建实例；未创建时不创建 保留
ResetAll() 按初始化完成顺序重置所有已创建实例 保留
Remove<T>() 销毁该类型实例，下次 Get 可重建 保留
Clear() 按初始化完成顺序逆序销毁所有实例 清空

Reset 是否适合登出取决于业务实现，管理器不会自动清理账号凭证或网络状态。Clear 清空注册之后，再次获取前需要重新注册。

业务缓存的 Model 引用也需要注意：Remove 或 Clear 会执行生命周期清理，但普通 C# 引用不会自动变成空值。调用方不能继续把旧实例当作管理器当前持有的对象使用。

3. 生命周期重入与批量清理

管理器使用生命周期深度和类型忙碌标记限制重入：初始化期间允许建立其他 Model，但重置和销毁期间不能创建新实例；生命周期回调中也不能随意注册、移除或清空集合。

批量操作会继续处理其他实例，最后将收集到的错误汇总为 AggregateException，避免某个 Model 清理失败就直接跳过其余对象。

逆序销毁有助于处理初始化阶段建立的依赖关系。例如 A 初始化时先创建 B，完成顺序为 B、A，退出时就先销毁 A，再销毁 B。不过运行中后来建立的任意依赖并不会被自动推导，业务仍应控制跨 Model 的持有关系。

这些集合按 Unity 主线程使用设计，不是线程安全容器。后台任务完成后，应回到合适的主线程业务流程再访问管理器。

六、更换实现时的职责边界

前三个模块虽然沿启动顺序相邻，但它们没有合并成一个“万能业务初始化器”。代码准备只解决代码与早期安装，配置模块解决表数据，Model 管理器解决运行时对象生命周期。把它们分开，才能在更换代码交付方式或配置格式时保留其他部分。

更换配置方案时改哪里

如果把 Luban 改成 JSON，不需要修改 ConfigManager 的启动位置。业务可以替换加载器和表适配器，继续遵守 IAlloyConfigLoader 与 IAlloyConfigTable<TConfig>。

但配置资源地址、反序列化方式、记录类型及业务访问需要相互匹配。统一接口减少了框架对生成工具的依赖，并不意味着所有业务数据结构都能自动兼容。

更换代码准备方式时改哪里

提供新的 IGameCodePreparation 实现，并在启动配置中选择它。实现必须满足当前创建方式的构造约定，准备正确的业务程序集，调用安装入口，并写入供后续步骤使用的结果。

只要这份约定保持一致，Config 和 Model 的启动流程就不需要知道业务代码来自静态主包还是动态加载。

七、退出顺序与使用边界

框架按启动步骤的反向顺序清理已经开始的步骤，也会让失败的当前步骤参与退出。因此，在关闭后续业务与框架模块之后，本文相关部分按以下顺序退出：

    graph TD
    Model["ModelManager：销毁实例并清除注册"]
    Config["ConfigManager：卸载配置和配置资源"]
    Code["PrepareGameCodeStep：清空准备结果引用"]
    Resource["ResourceServiceManager：关闭资源服务"]
    Model --> Config --> Code --> Resource

Model 先清理，配置和资源服务后关闭，可以让 Model 释放自己持有的订阅和资源时，相关基础设施仍然存在。配置卸载也需要在资源服务关闭前归还资源句柄。

但不能把“逆序清理”理解为所有操作都可回滚：动态程序集加载不会因为清空 RuntimeAssembly 引用而撤销。发生不可逆阶段失败时，仍应按实现要求重启 Player。

日常使用还要遵守几个边界：

  • 反射安装入口只做早期安装，不提前访问尚未初始化的 Model、UI 等系统。
  • 配置查询应发生在配置加载完成之后，新增表需要显式加载和注册。
  • Model 类型需要公开无参构造函数，业务通过管理器获取实例。
  • Model 生命周期不承接异步初始化；异步准备由业务流程组织。
  • 清理方法应能处理部分初始化，且业务不再使用被移除的旧实例。

八、总结

资源系统解决了文件和资产如何取得，本篇的三个模块继续解决业务代码、配置数据和运行时状态如何进入框架。

PrepareGameCodeStep 让不同代码来源汇合到明确的业务安装入口；ConfigManager 与 AlloyConfig 统一配置加载时机和访问方式；ModelManager 集中持有业务对象并管理生命周期，让每个 Model 不必再维护自己的单例。当前采用显式注册类型、首次获取时创建实例的方式实现这份管理责任。
