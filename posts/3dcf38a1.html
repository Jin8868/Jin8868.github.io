YooAssets 打包流程：从 Collector 到 AssetBundle 与发布产物

上一篇《YooAssets 的 AB 资源分类与管理》介绍了 Package、Group、Collector 和 MainAssets，也说明 Collector 会为每个资源计算 BundleName：同名资源归入同一个 AssetBundle。

但配置只是开始。一个预制体会引用材质、贴图和 Shader，不同包中的预制体还可能引用同一份资源。构建流程需要把这些配置与引用关系整理成 Unity 的打包输入，再生成可发布、可加载的文件。

本文沿 Builtin Build Pipeline 的执行过程，回答四个问题：

  1. 如何使用 Collector 的数据？
  2. 如何避免共享依赖在多个 AB 中重复包含，实现资源零冗余？
  3. MainAsset 如何进入 Unity 的 AssetBundle？
  4. 构建产物有哪些，分别有什么用？

本文依据 YooAsset 2.3.19 源码，讨论常规 AssetBundle 构建。示例用于说明数据变化，未执行对应构建实验。Builtin 指 Unity 内置构建管线；源码中的 Buildin 文件则指随安装包携带的内置资源。

一、构建流程的主线

BuiltinBuildPipeline 将一组任务交给 AssetBundleBuilder 顺序执行，任务通过 BuildContext 传递数据。整条流程可以分成五个阶段：

阶段 关键任务 解决的问题
准备 TaskPrepare_BBP 检查参数、未保存场景与输出目录
建立映射 TaskGetBuildMap_BBP 收集资源、分析依赖、确定包归属
Unity 构建 TaskBuilding_BBP 生成实际的 AssetBundle
整理版本 验证、加密、更新文件信息、生成清单与报告、复制发布文件 将 Unity 产物接入 YooAssets 的发布体系
准备内置资源 TaskCopyBuildinFiles_BBP、TaskCreateCatalog_BBP 按配置准备随安装包携带的文件 
    graph TD
    A[Collector 配置] --> B[收集资源与递归依赖]
    B --> C[剔除未引用 Depend 条目]
    C --> D[确定共享依赖归属]
    D --> E[按 BundleName 汇总]
    E --> F[转换为 Unity 构建输入]
    F --> G[生成 AssetBundle]
    G --> H[验证与可选加密]
    H --> I[生成清单和报告并整理发布文件]
    I --> J[按配置复制内置资源并生成 Catalog]

前半段决定“资源进入哪个包”，后半段补齐“怎样发布、查找和校验这些包”。

二、Collector 的数据如何进入构建

1. 重新执行收集规则，得到 CollectAssetInfo

TaskGetBuildMap_BBP 调用 CreateBuildMap，通过下面的调用关系收集指定 Package：

它读取 Package 配置，检查 Group 是否激活，再执行 Collector 的搜索、过滤、寻址与打包规则。正式构建使用的是重新计算的结果，并会查询递归依赖；不要求先在窗口中展开 MainAssets。

每个直接收集的资源对应一份 CollectAssetInfo，其中有三类关键信息：

信息 数据 用途
资源身份 AssetInfo、CollectorType 标识资源，并区分 Main、Static、Depend
配置结果 BundleName、Address、AssetTags 确定包归属、加载地址与标签
引用关系 DependAssets 保存递归依赖，供后续分析使用

下面用一个例子贯穿后续流程：骑士和法师分别进入两个 Bundle，共用一份材质和贴图。

假设只直接收集两个预制体，材质和贴图交给依赖分析处理。两份预制体记录各自有 BundleName，DependAssets 则都包含 Shared.mat 和 Shared.png。以下省略 Shader 等其他依赖，包名使用逻辑示意。

2. 先剔除没有被引用的 Depend 条目

如果项目还配置了 Depend Collector，收集结果中可能存在没有被使用的资源。RemoveZeroReferenceAssets 通过两个集合判断它们是否应该保留：

  1. 集合 A： 遍历所有 Main 和 Static 条目，将它们的 DependAssets 路径合并进一个 HashSet<string>。递归依赖包含在内。
  2. 集合 B： Depend Collector 直接收集到的所有条目，按资源路径参与比较。
  3. 逐条判断： 遍历 B，用每个条目的路径查询 A。存在则保留，不存在则从本次收集结果中移除，记入报告的 IndependAssets。

也就是：保留 B ∩ A，剔除 B − A。 实现中直接遍历收集列表里的 Depend 条目，不必额外创建名为 B 的集合。

例如，若 Depend Collector 收集到了共享材质、贴图和一张未使用贴图：

这一步只移除收集条目，源文件保留。Main、Static 不会因为无人引用而被剔除；几个 Depend 资源即使彼此引用，只要不存在从 Main 或 Static 出发的引用链，仍会被剔除。

这里处理的是“哪些 Depend 资源被使用”，下一节处理的则是“被使用的资源会不会跨包重复”。

3. 统一为 BuildAssetInfo 资源表

随后以资源路径为键建立 BuildAssetInfo 字典。直接收集的资源继承已有包名、地址和类型；仅通过依赖发现的资源先不分配包名。同一路径再次出现时复用已有记录，并补充引用它的 Bundle 名。

在只直接收集两个预制体的方案下，资源表如下：

资源 当前 BundleName 引用它的不同 Bundle
Knight.prefab knight.bundle 本例中无其他资源引用它
Mage.prefab mage.bundle 本例中无其他资源引用它
Shared.mat 暂无 knight.bundle、mage.bundle
Shared.png 暂无 knight.bundle、mage.bundle

资源表中同一路径只有一条记录，还不能保证实际 AB 没有重复内容。 共享依赖需要继续取得明确归属，才能避免被分别包含进多个包。

三、共享依赖如何实现零冗余

1. 将隐式共享依赖变成显式归包资源

如果只向 Unity 指定两个预制体的归属，没有给共享材质、贴图分配包，普通隐式依赖可能随两个预制体分别进入各自的包：

YooAssets 的处理方式是在 Unity 构建前识别跨包共享依赖，为它们分配明确的 BundleName。Unity 据此将共享内容放入指定包，其他包通过依赖使用它：

2. 按不同引用包的数量判断

BuildAssetInfo 用 HashSet<string> 保存引用它的 Bundle 名，GetReferenceBundleCount 返回集合大小。这里统计的是不同 Bundle 的数量：

引用情况 引用包数量 含义
同一个包内十个预制体引用一张贴图 1 不因资源引用多就认定存在跨包重复
两个包各有一个预制体引用同一张贴图 2 若没有明确归属，就有跨包重复风险

开启 EnableSharePackRule 后，ProcessingPackShareBundle 为仍没有 BundleName 的依赖执行共享归包。默认规则以资源的直接父目录生成包名，并加入 share 标识。

若材质和贴图都位于 Assets/Res/Shared/，它们会取得相同的共享包名；启用 UniqueBundleName 时类似：

所以，共享提取不是每个依赖各建一个包，也不是把所有共享资源塞进一个全局包。同目录资源可以合包，不同目录可能生成不同共享包。已经由 Collector 明确分配包名的资源，则沿用原归属。

3. 单包引用的依赖怎样处理

SingleReferencedPackAlone 决定只被一个包引用的依赖是否也显式归包：

参数组合 处理方式
EnableSharePackRule = false 跳过自动共享归包，需靠显式配置避免跨包重复
共享规则开启，SingleReferencedPackAlone = false 提取多包引用依赖；单包引用依赖可随引用包隐式打入
共享规则开启，SingleReferencedPackAlone = true 单包引用依赖也按共享规则显式归包，同目录仍可能合包

2.3.19 官方 BBP 窗口会开启共享规则，并沿用 SingleReferencedPackAlone = true。自定义脚本需留意：参数类中 EnableSharePackRule 的默认值是 false，与窗口入口的实际设置不同。

没有取得包名的依赖会被移出显式打包资源表，但仍可能由 Unity 随引用资源隐式包含进包。这与前面剔除未使用的 Depend 条目不同。

4. 零冗余的适用范围

这套机制主要解决同一 Package 内、依赖分析能识别的同一资源路径被多个 AB 重复包含的问题。内容相同但路径不同的两份贴图、跨 Package 的重复，以及图集和引擎生成对象等情况，仍需结合实际产物检查。Shader 还会受 AutoCollectShaders 的专门规则影响。

明确共享归属可以减少重复内容，但也会引入依赖包访问。是否继续拆分或合并，仍要结合分包策略中的使用范围、更新节奏和加载开销判断。

四、MainAsset 如何进入 Unity AssetBundle

1. 从资源表转成包列表

完成依赖归包后，具有 BundleName 的 BuildAssetInfo 被交给 BuildMapContext.PackAsset。它以包名为键查找 BuildBundleInfo：有同名包就追加资源，没有就创建一条包记录。

这一步把“每个资源属于哪个包”，转换成“每个包包含哪些显式资源”。包内可以同时包含 Main、Static、保留的 Depend 和自动归包的共享依赖。

2. 转成 AssetBundleBuild 数组

BuildBundleInfo.CreatePipelineBuild 把每条包记录转换为 Unity 的 AssetBundleBuild，核心字段为：

字段 来源
assetBundleName 当前包的 BundleName
assetNames 当前包的显式资源路径数组
addressableNames 开启 ReplaceAssetPathWithAddress 时填入对应地址

五、构建后如何整理成 YooAssets 发布内容

1. 确定发布文件及其标识

配置了有效加密服务时，管线会为需要加密的包生成 .encrypt 中间文件。随后选择原始包或加密文件作为发布源，计算文件 Hash、CRC 和大小。

这里应区分两类信息：Unity Hash、Unity CRC 来自原始 AB 构建结果；发布文件的 MD5、CRC32 和大小针对最终发布源文件计算。加密改变了文件字节时，不能将两者混用。

FileNameStyle 决定发布文件使用 BundleName、Hash，还是 BundleName 与 Hash 的组合。这也解释了为什么逻辑包名和磁盘上的发布文件名可能不同。

2. 生成 PackageManifest

TaskCreateManifest_BBP 根据构建映射和 Unity 结果生成 YooAssets 清单，核心是两张表：

表 主要内容
AssetList Main 资源的地址、路径、可选 GUID、标签、所属包 ID 和依赖包 ID
BundleList 包名、文件 Hash、CRC、大小、加密标识、标签和依赖包 ID

只有 Main 条目生成普通加载入口；Static、Depend 和自动共享依赖可以进入 AB，但不会自动成为 AssetList 中可单独寻址的资源。

资源记录的依赖包 ID 根据资源依赖和包归属计算，BBP 的包级依赖则读取 Unity 返回的 AssetBundleManifest.GetAllDependencies。主资源标签还会传递给相应包和依赖包，供标签下载、内置文件选择等使用。

这份清单把“怎样定位一个资源”和“需要准备哪些文件”连接了起来。

六、构建产物有哪些，各有什么用

1. 三处目录分别服务于什么阶段

下列根路径来自构建参数，平台、Package 和版本为示意：

官方构建窗口通常将内置目录放在 Assets/StreamingAssets/yoo 下，具体以实际参数为准。

2. OutputCache：Unity 产物与构建资料

文件 用途
各逻辑包名对应的 AB Unity 直接生成的资源内容
各 AB 的 .manifest 文本 查看单包的构建信息与依赖
OutputCache 包含 Unity AssetBundleManifest 对象的总清单 Bundle
OutputCache.manifest 总清单 Bundle 的文本清单
*.encrypt 实际执行加密时生成的中间文件
buildInfo.log YooAssets 构建任务与错误日志

OutputCache 文件是 Unity 总清单 Bundle，与同名目录要区分。该目录还服务于增量构建，发布时使用后续整理好的版本目录。

3. 版本目录：运行时文件与辅助资料

假设 Package 为 DefaultPackage、版本为 1.0.0，使用默认的空 PackageManifestPrefix：

文件 内容与用途
*.bundle 等发布资源 按 FileNameStyle 命名的资源内容，可能已加密
DefaultPackage_1.0.0.bytes 二进制 PackageManifest，供运行时寻址、依赖与文件管理使用
DefaultPackage_1.0.0.hash 二进制清单的校验值，2.3.19 使用 CRC32 字符串
DefaultPackage.version 版本号文本，此例为 1.0.0
DefaultPackage_1.0.0.json 可读的资源清单，用于检查与排错
DefaultPackage_1.0.0.report JSON 格式构建报告，用于分析资源、包与依赖
OutputCache、OutputCache.manifest 从 Unity 输出复制来的总清单及其文本版本

.version 用于选择对应版本的清单，.hash 校验 .bytes；各 AB 自身的文件 Hash 则记录在清单中。设置了清单前缀时，上述相关文件名会相应变化。

常规远端更新需要版本文件、匹配的二进制清单与校验文件，以及清单引用的发布资源。JSON、report 和 Unity 总清单作为辅助资料保存。单包 .manifest 文本主要保留在 OutputCache，BBP 不会把它们全部复制到版本目录。

构建报告可以查看参数、主资源归属、包大小、依赖与反向引用，以及被剔除的 Depend 条目。但其中的 BundleContents 来自构建映射和依赖信息，不是对最终 AB 二进制逐对象反向解析的结果。涉及图集等特殊资源时，应结合实际包内容验证。

4. 内置目录：安装包实际携带的资源

当 BuildinFileCopyOption 不为 None 时，管线复制 .bytes、.hash、.version，再按选项复制全部或指定标签的 Bundle，最后生成：

文件 用途
BuildinCatalog.bytes 内置文件系统使用的 Bundle 标识与文件名记录
BuildinCatalog.json 便于查看的 JSON 版本

PackageManifest 描述这个版本有哪些资源及其包归属，Catalog 描述安装包实际携带了哪些文件。 首包只内置部分资源时，完整清单仍可描述整个版本，Catalog 则只记录实际存在的内置 Bundle。

七、用同一个案例检查整条流程

用两个独立包中的预制体共享材质、贴图，可以验证本文的关键判断。固定 Unity 版本、目标平台和其他构建设置，对比关闭共享规则与开启共享规则的结果：

检查位置 需要确认的内容
收集结果 两个 Main 记录的递归依赖都包含共享材质与贴图
Depend 清理 若额外配置了 Depend Collector，未使用条目被剔除，实际依赖保留
共享归包 开启规则后，跨包共享依赖取得唯一明确的 BundleName
Unity 输入与输出 包列表转换为显式构建映射，实际包集合符合计划，内容无意外重复
发布与内置目录 清单记录与发布文件对应，Catalog 符合实际首包选择

如果再添加一张骑士独占贴图，可通过切换 SingleReferencedPackAlone 观察它是隐式留在骑士包，还是取得显式共享包名。实际包数量还会受目录归组、Shader 等依赖影响，不能只看包数判断结果。

这条流程中，Collector 提供资源与依赖，归包分析确定共享资源的唯一归属，Unity 根据显式映射生成 AB；清单、校验、版本与 Catalog 再把这些文件接入 YooAssets 的发布和运行时管理体系。四个问题由同一条数据转换过程贯穿起来。
