AlloyFramework的实现(七) - UI框架的需求与整体设计

发表于2026-11-18|更新于2026-11-19
|总字数:2.6k|阅读时长:7分钟

上一篇介绍了 音频系统，这一篇开始介绍 AlloyFramework 框架中基于 UGUI 实现的 UI 系统。

UI 系统为什么需要分层、生命周期、动效和导航等模块？可以先从最简单的需求出发：打开一个界面。随着界面被加载、显示、操作和关闭，业务会遇到一系列重复的问题，框架的各项能力也由此产生。

本文先沿着这个过程梳理 UI 系统的需求与整体设计，后续再按功能分篇介绍具体实现。

一、UI 框架需要解决什么问题

1. 先把界面打开：统一 Open 接口

假设现在需要打开一个背包界面。如果资源采用 AssetBundle 交付，又没有统一封装，业务就需要找到并加载对应的 AB 包及其依赖，从包中加载 Prefab，再实例化对象、挂到 UI 节点下，最后初始化界面内容。

关闭界面时，各个业务还要再写一遍销毁对象、归还资源引用以及释放不再使用的 AB 包和依赖的逻辑。界面越多，这些重复代码就越多，也越容易遗漏释放。

因此，首先需要统一的 Open 和 Close 接口。业务只提供界面定义和打开参数，由 UI 系统组织资源加载、实例化和初始化，并在关闭时按策略处理实例与资源。在 AlloyFramework 中，底层 AB 包及依赖的管理已经交给资源模块，UI 系统继续调用资源模块，不再重复实现一套 AB 加载逻辑。

2. 统一显示顺序与交互规则：层级与输入管理

界面创建出来后，还要决定它显示在哪一层。背包应当显示在主界面之上，物品详情又要显示在背包之上，Loading 和系统提示则可能需要覆盖它们。

如果各个业务自己指定父节点、调整兄弟节点顺序或修改 Canvas 排序值，就很容易出现后打开的弹窗被遮住、普通窗口盖住引导等问题。因此，需要由框架统一划分逻辑层，并维护同层界面的显示顺序。

显示顺序正确后，还会遇到输入问题：点击详情弹窗时，操作是否会穿透到背包？点击弹窗外部，是关闭弹窗还是继续操作下层界面？这些行为也需要明确规则，于是层级管理进一步引出了输入阻挡、穿透和外部点击处理。

例如，可以按从低到高的顺序划分以下几个层级：

层级 用途
HUD 血条、小地图、操作按钮等常驻界面
Window 背包、商城、任务等普通窗口
Popup 确认框、物品详情等弹窗
Loading 加载进度与过渡遮罩，覆盖普通窗口和弹窗

业务只需要声明界面所属的层级，由框架统一维护显示顺序。

3. 分离数据、表现与交互逻辑：MVC 分层与组件绑定

背包显示出来后，需要给图标赋值、刷新数量、绑定按钮事件，并在点击物品时打开详情。如果这些逻辑全部写在同一个 MonoBehaviour 中，组件引用、业务数据和交互流程很快就会混在一起。

因此，需要把职责分开：View 持有组件并负责表现，Controller 组织交互和刷新流程，业务 Model 保存与处理数据，ModelManager 继续承担 Model 的管理职责。

组件引用本身也存在重复劳动。每个界面都手动声明字段、拖拽引用，或者运行时按路径查找，既繁琐又容易遗漏。由此再引出编辑器绑定工具，让它按约定生成代码并写回组件引用。

4. 规范创建、打开、刷新与释放：界面生命周期管理

背包可能要先准备数据才能显示，按钮事件只需绑定一次，而物品列表每次打开都要刷新。关闭之后，数据通知是否还要监听？下次打开时，是重新加载还是复用原来的对象？

这些逻辑需要有固定的执行阶段，否则每个界面都会自己约定“初始化”“打开”“关闭”分别做什么。框架因此需要统一生命周期，区分首次创建、每次打开的数据准备、刷新、关闭和最终销毁。

框架提供以下生命周期回调：

回调 用途
OnCreate 首次创建时执行，绑定按钮事件等一次性逻辑
OnPrepareAsync 每次打开时异步准备数据
OnInitData 准备完成后，初始化本次界面内容
OnOpen 开场动效结束后执行打开逻辑
OnRefresh 按刷新策略重复打开已有界面时，更新数据与显示
OnPause / OnResume 处理导航中的暂停与恢复
OnClose 退场动效开始前执行关闭逻辑
OnDispose 实例最终释放时执行清理逻辑

这些回调为业务逻辑提供统一的执行时机。业务按需填入初始化、刷新和清理逻辑，由框架负责调度，并处理重复打开、缓存复用与最终释放。

5. 适应屏幕比例与异形屏：分辨率与安全区适配

界面在开发分辨率下正常，不代表换成长屏或带刘海的手机后仍然正常。背景可能无法铺满，按钮可能靠近屏幕缺口，横竖屏切换后布局也可能失效。

如果每个业务分别计算缩放和安全区，同样会产生重复逻辑和不一致的结果。因此，需要统一屏幕信息与适配规则，再根据内容特点区分背景铺满、固定比例区域和安全区内的交互内容。

6. 统一动画播放、复用与调试：动效管理

界面通常会使用淡入、淡出或缩放动画表现打开与关闭过程。框架需要等待开场动画结束后再启用交互，也需要等待退场动画结束后再隐藏或释放对象，避免动画被提前打断。

如果每个界面自己计时等待，再分别处理快速开关、动画中断和游戏暂停，就会重复编写大量状态控制。因此，需要统一的动效管理，把播放、完成等待、取消和帧事件接入界面生命周期。

开发时还需要反复调整和检查动画效果，因此框架同时提供配置复用、预览和按帧播放调试：

  • 配置与复用：通过配置关联动效 Key、AnimationClip 和播放参数，节点路径与动画属性兼容的界面可以复用同一份 Clip，减少重复制作。
  • 预览：在编辑器中直接选择动效播放、暂停，快速检查效果，不必每次都从业务入口走完整个打开流程。
  • 按帧调试：拖动时间轴定位，或前进、后退一帧，检查某一帧的位置、缩放与透明度，方便排查闪烁、跳变和衔接问题。

运行时由框架管理播放流程，开发时通过预览与逐帧调试定位表现问题，减少反复进入业务流程验证动画的时间。

7. 处理粒子排序、裁剪与回收：UI 特效管理

给高品质物品增加粒子光效后，又会遇到新的问题：粒子能否位于背景与图标之间？放进滚动列表后，能否被遮罩裁剪？界面关闭和缓存复开时，粒子应该怎样停止与重置？

普通 ParticleSystem 挂到 UI 节点下，并不会自动遵守 UGUI 的渲染与裁剪规则。因此，需要考虑 UIParticle 这样的接入方案，并明确特效与界面的生命周期关系。

8. 管理界面跳转与返回关系：导航管理

最后，玩家从背包打开物品详情，再进入物品获取途径。这时只提供 Open 和 Close 已经不够：打开目标后，来源界面是否暂停？返回时恢复详情还是背包？不同入口进入同一个页面，返回目标是否相同？

如果这些关系全部写在按钮回调中，界面之间会互相依赖，流程一变就要修改多处代码。因此，需要导航系统统一描述跳转目标、参数准备、来源处理和返回策略。

沿着“打开一个界面”逐步展开，就能看到这些模块各自的必要性：Open 收拢加载与创建，层级管理显示顺序，MVC 组织业务代码，生命周期管理实例，适配处理屏幕差异，动效与粒子负责表现，导航维护界面之间的关系。业务通过统一 API 使用它们，UIManager 负责组织流程，各模块分别完成自己的职责。

二、总结

从打开一个界面开始，UI 系统的需求逐步扩展到层级与输入、MVC 与组件绑定、生命周期、屏幕适配、动效、粒子，以及导航与返回。框架把这些重复的工作统一起来，让业务主要关注界面内容与交互逻辑。

下一篇从一个具体界面出发，介绍 MVC 的依赖关系、View 的绑定方案与代码生成，以及 Controller 生命周期和 ModelManager 的配合。层级、适配、动效和导航再分别展开；UIParticle 作为待接入扩展另行介绍。
