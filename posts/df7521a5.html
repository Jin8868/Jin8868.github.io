AlloyFramework(二)：框架启动流程

发表于2026-11-11|更新于2026-11-11
|总字数:4.9k|阅读时长:17分钟

上一篇介绍了 AlloyFramework 需要提供哪些基础模块。这一篇介绍这些模块如何启动，以及框架完成准备后，如何把流程交给业务层。

整个启动结构主要分为三块：

  1. 框架入口：在启动场景挂载 FrameworkBootstrap，从它的 Awake 开始启动。
  2. 模块初始化流程：统一组织模块，按顺序初始化，完成热更代码准备，并通过反射获得业务入口。
  3. 业务入口：初始化业务、执行项目自身逻辑，完成从框架启动流程到业务流程的交接。

代码中使用的 UniTask

本文的异步代码使用 UniTask，需要引入 Cysharp.Threading.Tasks 命名空间；取消令牌 CancellationToken 来自 System.Threading。

资源加载、代码准备和场景加载都可能需要等待。启动方法返回 UniTask，管线通过 await 等待当前步骤完成，再执行下一步，从而把异步操作写成清晰的顺序流程。等待期间可以把执行机会交还给 Unity，await 本身不会自动把工作放到子线程中，同步执行的耗时操作仍然会占用当前线程。

UniTask 为 Unity 提供了基于 PlayerLoop 的异步支持，并通过值类型和对象复用等方式减少分配。它不意味着所有异步代码都绝对零 GC，具体原理可以阅读之前的文章：UniTask 0GC实现原理。本篇重点关注它如何组织启动流程。

一、框架入口：从 FrameworkBootstrap 的 Awake 开始

项目准备一个独立的 Boot 场景，作为游戏运行时加载的第一个场景，并在其中挂载 FrameworkBootstrap。

FrameworkBootstrap 继承自 MonoBehaviour，因此可以通过 Unity 的 Awake 发起启动。它持有启动配置引用，当前项目配置的是 GameHotUpdateSettings，用来提供资源模式、代码模式、日志和 Loading 预制体等信息。代码中的字段使用其父类 FrameworkBootSettings 声明，方便不同项目提供自己的配置实现。

Awake 先检查是否已有框架入口，避免重复启动；然后将入口设置为跨场景保留，创建启动控制器，安装日志、校验配置并创建 Loading，最后发起模块初始化流程。

Awake 完成环境准备后，由启动控制器运行 FrameworkStartupPipeline，接下来进入模块初始化流程。

1. 用 FrameworkSystem 统一模块生命周期

启动过程除了初始化模块，还包含读取配置、准备代码和创建业务入口。因此，FrameworkStartupPipeline 保存的是启动步骤列表 List<IFrameworkStartupStep>。

后续新增普通模块，只需要继承 FrameworkSystem，实现生命周期方法，再包装为初始化步骤，加入列表的合适位置。新增特殊启动操作，则实现 IFrameworkStartupStep 后注册到列表。

3. 热更代码模块如何接入

热更代码准备被安排在资源模块之后、配置模块之前。资源模块需要先准备好，才能获取代码文件；业务代码需要先可用，才能创建项目自己的配置加载器。

这里先明确 AOT 和 HotUpdate 的边界。在当前 HybridCLR 方案中，两者按程序集划分，决定了哪些代码可以通过热更新发布，哪些改动需要重新构建和安装主包。

部分 当前项目中的内容 修改后如何发布
AOT 主包代码 框架启动与基础模块、Game.Bootstrap 中的启动配置逻辑，以及主包内的 HybridCLR 接入代码 修改这些代码需要重新构建并发布安装包
HotUpdate 业务代码 配置为热更新程序集的 Game.Runtime，包括 GameEntry、业务配置加载器和业务逻辑 在与现有主包兼容的前提下，重新构建并发布热更新 DLL，无需更换主包

AOT 表示代码在构建主包时提前编译。FrameworkBootstrap、模块初始化管线以及代码加载能力需要先存在于主包中，才能启动游戏并加载后续业务代码。HotUpdate 则是通过 HybridCLR 加载执行的业务程序集，当前项目在热更新配置中指定的是 Game.Runtime。

例如，修改 Game.Runtime 中的背包业务逻辑，且仍使用主包已有接口，可以发布业务 DLL 更新；修改主包里的 FrameworkSystem、启动管线顺序，或者新增业务要调用的框架接口，就需要重新出包。原生插件、Unity 引擎版本等主包能力发生变化时，也需要更新安装包。

补充 AOT 元数据用于支持相关泛型执行需求，不会把已经编译进主包的 AOT 代码变成可替换代码。热更新业务仍然必须使用当前主包能够提供的类型和接口。

代码更新与资源更新也需要区分：仅修改可更新资源包中的预制体或配置数据，可以走资源更新；修改主包内嵌且未纳入资源更新的启动场景、启动配置或展示资源，则需要随新主包发布。使用 Default 模式时，业务代码静态编译在主包内，修改业务代码同样需要重新出包。

这一部分使用 IGameCodePreparation 作为统一接口，由启动配置决定采用哪一种实现。当前提供两种方式：

  • DefaultGameCodePreparation：使用静态编译到主包中的业务程序集。
  • HybridCLRCodePreparation：负责 HybridCLR 模式下的业务代码准备与加载。

启动步骤只负责创建所选实现并调用 PrepareAsync，具体如何取得程序集、如何准备运行环境，由对应实现处理。准备完成后，将业务程序集保存到本轮启动上下文中，供后续创建业务入口使用。

取得程序集后，还会根据配置中的业务安装类型，通过反射调用其 Install 方法。当前项目在这里安装 GameConfigLoader，把业务对配置加载的具体实现交给框架，随后配置模块才能继续初始化。

后续如果需要接入其他代码准备方案，可以新增 IGameCodePreparation 实现，并在启动配置中选择它。实现沿用现有的创建约定，完成业务安装并提交准备结果，后面的模块初始化与业务入口流程就能继续复用。

Game.Runtime 是当前项目在启动配置中明确指定的名称，反射激活器本身接收的是 Assembly 对象。因此，更换项目程序集名称时，需要同步调整 asmdef、启动配置以及相关构建与热更新配置。

当前启动路径只扫描代码准备阶段提交的这个程序集。如果项目拆分为多个业务程序集，需要把唯一的 IGameEntry 实现放在指定的入口程序集中。

入口类本身不要求一定叫 GameEntry，框架通过接口识别它。它需要是能够实例化的非抽象、非开放泛型类型，并提供无参构造函数；当前反射调用也允许非 public 的无参构造函数。当前业务入口使用 [Preserve] 标记，保留反射所需的类型信息。

入口创建完成后，框架通过 IGameEntry 接口依次调用业务初始化和业务主流程，具体执行逻辑由业务层提供。

三、业务入口：初始化业务并执行游戏逻辑

GameEntry 是业务层自身的统一入口，实现 IGameEntry 接口，由框架创建，无需再挂载到场景。

业务入口分为初始化和正式进入游戏两个阶段。

1. InitializeAsync：准备业务模块与框架扩展

框架先调用 InitializeAsync。业务在这里注册自己的模型、安装框架所需的业务扩展，并初始化网络等项目相关能力。

当前项目通过业务启动管线组织这些操作。以打开背包为例：框架知道如何加载、显示和关闭一个界面，但需要业务告诉它“背包使用哪个界面预制体”，以及“配置表中的背包跳转 ID 对应哪个界面”。业务在初始化时把这些界面信息和配置读取方法交给 UI 模块，后面就可以通过统一接口打开目标界面。

前面的配置加载器和这里的 UI 扩展，都属于业务对框架的接入，只是安装时机不同：配置加载器需要在配置模块初始化前安装，UI 扩展则等框架与配置就绪后再安装。

后续增加业务模块时，也可以加入业务启动管线，保持项目自身的初始化顺序清晰。

2. MainAsync：执行业务自身的入口逻辑

业务初始化完成后，框架调用 MainAsync，正式进入项目自己的流程。

当前项目在这里加载 Scenes/SampleScene，然后打开首页。其他项目可以根据自己的需求进入登录、角色选择、新手引导或战斗场景，这些流程由业务层决定。

业务入口等待初始场景和界面就绪后返回，框架结束启动 Loading。至此，框架的启动流程结束，后续游戏流程由业务层组织，框架继续提供资源、时间、配置、网络和 UI 等基础服务。

3. 保留对应的退出入口

业务入口还提供 ShutdownAsync，用于关闭业务界面、卸载场景和清理业务模块。框架退出时先调用业务退出，再逆序释放已经开始的框架步骤；启动中途失败时，也沿用对应的清理机制。

这三块结构分别负责启动环境、模块准备和业务执行。通过统一的模块父类、启动步骤列表和业务入口接口，后续扩展可以在对应位置接入，继续沿用已有的执行顺序与生命周期管理。
