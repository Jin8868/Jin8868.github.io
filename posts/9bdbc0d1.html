AlloyFramework的实现(八) - UI框架的MVC分层与界面绑定

发表于2026-11-18|更新于2026-11-18
|总字数:3.3k|阅读时长:10分钟

上一篇梳理了 AlloyFramework UI 系统的总需求。这一篇介绍一个界面内部的代码应该如何组织，以及 View、Controller 和 Model 如何分工协作。

一个界面通常需要显示数据、响应点击并处理打开与关闭。把这些逻辑全部放在一个 MonoBehaviour 中也能运行，但随着功能增加，组件引用、交互流程与业务数据就容易相互牵连。

因此，先把它们的职责与依赖关系确定下来。

一、从一个界面看 MVC 的依赖关系

AlloyFramework 按照 MVC 划分职责，由 Controller 获取 Model 数据并驱动 View 刷新：

    graph TD
    Controller["Controller"] <-->|数据读写与变化通知| Model["Model"]
    Controller <-->|交互事件与界面刷新| View["View"]

一个界面按照 MVC 划分为三个部分：

部分 对应职责 主要内容
View 持有 UI 组件，展示数据 文本、图片、按钮、列表与界面动效
Controller 处理交互，协调 Model 与 View 响应事件、发起业务操作、刷新与关闭界面
Model 保存和处理业务数据 数据状态、业务规则与变化通知

View 与 Model 不直接依赖，由 Controller 衔接数据与表现。Model 独立于界面存在，关闭界面不会影响业务数据的保存与更新。

二、View：把 Prefab 变成代码可访问的界面

1. UIView 负责什么

AlloyFramework 的 View 基类是 UIView，继承 MonoBehaviour，挂在界面 Prefab 根节点上。

UIView 提供所有界面共用的表现入口，包括与 UIAnimationPlayer 对接、播放自定义动效和转发动效帧事件。具体界面的按钮、文本和列表引用，则由派生 View 提供。

UIManager 加载并实例化 Prefab 后，从根节点取得对应 View，再交给 Controller。Controller 通过泛型 View 属性访问它，不需要每次把 UIView 转换成具体类型。

View 的业务内容应尽量保持在表现范围内，例如设置文本、切换选中状态、刷新图标。是否允许出售物品、出售后数据如何变化，应交给 Controller 协调业务逻辑与 Model。

2. 组件绑定的两种选择

Controller 要操作一个 Text，首先需要 View 能提供这个组件。常见的做法有两种：

方式 做法 需要维护的内容
手动引用 编写序列化字段，在 Inspector 中拖拽组件 字段代码与每个 Prefab 的引用关系
前缀生成 使用 txt_、btn_ 等命名约定，让工具扫描并生成绑定 节点命名、组件类型与生成规则

手动引用很直观，也不依赖节点名字。只要引用对象没有被替换，移动节点或重命名通常不会破坏已有的序列化引用。界面较小、组件较少时，这种方式足够简单。

但当界面有几十个控件，或者需要制作多套皮肤时，就会反复编写字段、拖拽组件、检查遗漏。AlloyFramework 选择前缀生成，让工具完成这些重复操作。

需要明确的是，前缀生成最终也会生成序列化引用，区别在于由工具自动维护，而不是由开发者逐个拖拽。 它不是在每次打开界面时按字符串查找节点。

这样的好处有：

  • 方便换皮。 保持关键节点的层级、名字、组件类型和业务含义，沿用同一个具体 View 类型，更换节点或 Prefab 后重新生成绑定，就可以继续复用原来的 Controller。业务逻辑不变时，替换背景、图标、字体和布局不需要重新编写交互代码。
  • 方便阅读与 AI 辅助开发。 生成代码中列出 TxtTitle、BtnClose、ListItems 等控件及其类型，同时记录控件的完整父子路径，让开发人员和 AI 都能直接对照 Prefab 层级，理解控件的位置与结构关系，方便开发和维护。

三、Controller：把业务逻辑放进明确的生命周期

Controller 基类是 UIController，属于普通 C# 对象，由 UIManager 创建和调度。

业务 Controller 可以继承 UIController<TView, TData>，其中 TView 是具体 View 类型，TData 是本次打开界面的参数类型。不需要打开参数时，使用 UIController<TView>，其内部采用 UIEmptyData。

View 准备好之后，Controller 负责把控件与业务流程连接起来。但“连接起来”不能全部放进一个初始化方法：按钮事件通常只绑定一次，打开参数需要每次更新，异步数据可能要先准备，关闭时还要停止监听。

因此，框架为这些工作提供了明确的生命周期入口。

1. 生命周期总览与打开流程

完整的生命周期回调及主要流程如下。首次创建才执行 OnCreate，缓存复开从数据准备阶段继续；刷新、暂停和恢复按对应操作触发，不是每次打开都依次执行。

    graph TD
    Create["OnCreate：首次创建"] --> Prepare["OnPrepareAsync：异步准备"]
    Prepare --> Init["OnInitData：初始化本次内容"]
    Init --> StartOpen["OnStartOpenAnimation"]
    StartOpen --> ViewOpen["View 开场动效"]
    StartOpen --> ControllerOpen["OnOpenAnimationAsync"]
    ViewOpen --> WaitOpen["等待两项开场动效完成"]
    ControllerOpen --> WaitOpen
    WaitOpen --> EndOpen["OnEndOpenAnimation"]
    EndOpen --> Open["OnOpen：完成打开"]
    Open --> Active["界面处于打开状态"]
    Active -->|按刷新策略重复打开| Refresh["OnRefresh：刷新内容"]
    Refresh --> Active
    Active -->|导航暂停| Pause["OnPause"]
    Pause --> Paused["界面处于暂停状态"]
    Paused -->|导航恢复| Resume["OnResume"]
    Resume --> Active
    Active -->|请求关闭| Close["OnClose：开始关闭"]
    Paused -->|请求关闭| Close
    Close --> StartClose["OnStartCloseAnimation"]
    StartClose --> ViewClose["View 退场动效"]
    StartClose --> ControllerClose["OnCloseAnimationAsync"]
    ViewClose --> WaitClose["等待两项退场动效完成"]
    ControllerClose --> WaitClose
    WaitClose --> EndClose["OnEndCloseAnimation"]
    EndClose --> Invalid["本次句柄失效"]
    Invalid -->|保留实例| Cached["缓存并隐藏界面"]
    Cached -->|重新打开| Prepare
    Invalid -->|销毁实例| Dispose["OnDispose：最终清理"]
    Cached -->|最终释放| Dispose

图中展示正常流程；加载失败或准备中取消时可能提前进入释放，不会保证执行全部回调。

回调 适合放置的逻辑
OnCreate 建立一次性引用、绑定按钮事件
OnPrepareAsync 异步准备本次打开所需的数据和资源
OnInitData 将准备好的数据应用到界面，设置默认选中状态
OnStartOpenAnimation 开场动效开始前的表现准备
OnOpenAnimationAsync 返回需要与 View 开场动画共同等待的业务动效任务
OnEndOpenAnimation 开场动效完成后的收尾
OnOpen 界面完成打开，建立只在打开期间需要的业务监听

OnCreate 执行时 View 已经绑定，但本次 Data 尚未经过准备与初始化，因此不要在这里读取本次打开参数。

OnPrepareAsync 执行期间，框架让界面保持不可见且不接收输入。需要等待的操作应返回到这条异步链中，并把传入的取消令牌继续传给下游。这样界面在准备中关闭时，任务才有机会及时结束。

OnInitData 适合立即把结果写入 View。开场动画结束后才到 OnOpen，因此标题、列表等首帧内容不应拖到 OnOpen 才初始化。

2. 已打开界面的刷新、暂停与恢复

背包已经打开时再次请求打开，并不一定要重新创建。

当前 SingleRefresh 策略会对已有界面调用 OnRefresh，更新本次参数并刷新显示；它不重新执行 OnCreate、OnPrepareAsync 和完整开场流程。SingleBringToFront 则侧重把已有实例置顶。

如果新的参数需要异步请求才能使用，就不能假设 OnRefresh 会自动执行异步准备。应明确业务刷新流程，或选择适合的重新打开方式。

导航中的暂停与恢复分别进入 OnPause、OnResume。当前框架会调整状态与输入，业务可以在回调中停止或恢复自己的刷新逻辑；这不等于自动隐藏界面，也不等于暂停该界面上的所有动画。

3. 关闭与最终释放

正常关闭时的主要顺序是：

OnClose 是开始关闭时的业务通知，发生在退场动效之前，适合移除只在打开期间使用的 Model 监听。它不是“画面已经消失”的通知，因此不能在这里直接销毁退场动效还要操作的对象。

OnDispose 用于最终清理，例如解除一次性按钮绑定、释放 Controller 持有的资源。关闭后缓存的界面不会立刻进入它，因为 View 和 Controller 还要继续复用。

相应地，事件绑定要成对：在 OnCreate 中绑定、需要随实例保留的按钮事件，在 OnDispose 中移除；在 OnOpen 中建立、只关心显示期间的业务订阅，在 OnClose 中移除。若使用后一种方式，复开时也要重新订阅。

加载失败或准备中取消时，生命周期可能提前终止，不保证每次请求都经过完整的 OnOpen 和 OnClose。最终清理应能够处理只完成部分初始化的情况。

四、View 与 Controller 的一键生成工具

框架提供了 ★AlloyFramework★/UI/打开界面生成器，可以一键生成 View 和 Controller 文件，不需要手动创建。选中 Prefab 并配置界面信息后，点击“生成界面代码并绑定预制体”，工具会完成以下工作：

  1. 递归扫描节点，根据 txt_、tmp_、btn_ 等前缀识别 Text、TMP_Text、Button 等组件。
  2. 生成 View 的组件字段与访问属性，例如 txt_Title 对应 TxtTitle，同时生成 Controller 骨架和界面定义。
  3. 等待 Unity 编译完成，将 View 挂到 Prefab 根节点，自动写入组件引用并保存。

运行时直接使用这些引用，不需要再按名字查找节点。后续调整 Prefab 后重新生成即可，工具会保留已有 Controller 和 View 生成区域之外的手写代码。

五、Model：继续使用 ModelManager

Model 层在 第五篇：业务代码准备、配置与数据模型 中已经介绍，这里只说明它与 UI 的关系。

业务 Model 继承 ModelBase，通过 ModelManager 注册和获取。注册不会立即创建实例，首次 Get 才创建并初始化；同一种已注册类型由管理器维护唯一实例。

不要求一个 View 必须对应一个独立 Model：背包界面可能同时读取背包 Model 和玩家 Model，而多个界面也可以读取同一个背包 Model。

以业务自行实现的 InventoryModel 为例：

ModelManager 提供管理入口，实际的物品集合和数量属于 InventoryModel。它的 OnInitialize、OnReset、OnDispose 由 ModelManager 管理，与界面的开关生命周期独立：关闭背包不应顺手销毁玩家的背包数据。

Controller 读取 Model 后更新 View；需要实时显示变化时，再订阅业务通知。当前框架没有自动注入 Model，也没有把 Model 属性自动绑定到 Text 的机制，这段连接由业务 Controller 完成。

此外，“打开背包时默认选中的物品 ID”属于本次打开参数 TData；“玩家持有哪些物品”属于 Model。把两者分开，界面关闭后临时显示状态与长期业务数据就不会混在一起。

六、总结

一个界面的代码可以沿着三条职责组织：View 提供稳定的控件与表现入口，Controller 在明确的生命周期中处理交互和刷新，Model 保存独立于界面存在的业务数据。

前缀生成把手动编写字段、拖拽引用变成可重复执行的编辑器流程。在遵守命名与组件约定的前提下，换皮可以保持 View 接口和 Controller 不变；生成的控件名称与类型也为 AI 辅助编写业务代码提供了明确上下文。完成这些约定后，业务就可以集中实现界面内容。
