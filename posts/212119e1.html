沿着播放流程，为游戏量身定做视频播放器

上一篇把视频从 MP4 到屏幕的过程拆成了读取、解封装、解码、帧调度、图形接入和最终渲染。这一篇沿着同一条链路，讨论另一个问题：已有 CRIWARE、AVPro Video 和 Unity VideoPlayer，为什么还要做 PulseVideoPlayer？

自研的直接动机，是把预热撤销、快速换片、后台暂停和资源释放纳入统一的生命周期管理，减少业务层反复修补状态与时序。游戏项目又对内容拥有较强的控制能力：美术按照约定交付母版，工具在发布前统一转换，运行时只处理经过验证的一类资源。沿着播放流程约束输入、请求和资源交接，就能把这些需求落实为边界明确的工程方案。

本文结合当前 PulseVideoPlayer 与宿主工程的源码说明设计。实现状态以源码为准：本地按需读取、Windows 后端和线程协作已经有实现；Android 已有后端源码，但不能据此宣称通过了真机兼容性验收；HTTP 边下载边播和流式加密仍属于后续设计。文中不会把“秒级首帧”当作已经取得的性能测试结论。

一、已有播放器的主要问题：生命周期复杂性仍然留给接入方

CRIWARE、AVPro Video 等成熟中间件提供了可靠的跨平台解码接入，却无法仅凭一套播放接口消除生命周期管理的内在复杂性。Unity 组件、原生会话、系统解码器与 GPU 资源各有自己的运行节奏，上层业务仍然需要协调状态流转与释放时序。

对游戏来说，播放一段视频只是最顺畅的一条路径。预热到一半被取消、界面关闭后立即重开、对象池中的播放器被复用、连续切换视频，以及准备过程中切到后台，都是需要正面支持的业务流程。这些流程会把“请求停止”“停止完成”“允许复用”和“资源已经释放”的差异直接暴露出来。

1. CRIWARE：暂停、后台暂停、停止和销毁分别有自己的语义

以 Sofdec 的 Unity 接入 CriWare.CriMana.Player 为例，官方文档明确区分了几个操作：

  • Stop() 发出停止请求后立即返回，不代表播放已经停止。
  • 自行创建的 Player 必须显式调用 Dispose()，释放其创建时分配的资源。
  • 普通暂停使用 Pause()；反映应用暂停状态时使用 PauseOnApplicationPause()，后者还涉及相关渲染处理。
  • 直接使用底层 Player 时，需要在 MonoBehaviour.OnApplicationPause 中转发应用状态；使用官方 CriManaMovieMaterial 等组件时，这部分由组件内部自动处理。

这些行为来自 CRIWARE Player 官方文档。它们说明：调用方必须区分各类暂停、停止和销毁的职责，不能把一个停止请求当作整个生命周期已经结束。

当项目进一步接入异步资源加载、预热撤销和对象池复用时，就需要把这些语义组织成自己的状态机：旧准备结果是否还能提交，何时允许设置下一段视频，后台暂停后应恢复到哪个业务状态，最终销毁由谁负责。官方组件承担了部分工作，但项目自己的请求身份与资源寿命仍然需要明确管理。

2. AVPro Video：预热取消与关闭竞态有明确的历史修复记录

AVPro Video 在 3.3.4（2025 年 12 月 2 日） 的 Android 修复记录中列出了两项相关问题：

  • 使用 ExoPlayer API，尚未调用 Play() 就调用 CloseMedia() 时，内存未被释放的问题（#2389）。
  • 关闭媒体时，由竞态导致的随机崩溃。

来源：AVPro Video 3.3.4 官方版本记录。第二项记录没有限定为 ExoPlayer，因此应与第一项的后端条件分别表述。这些都是该版本已经修复的历史问题。

从游戏业务看，第一种调用顺序正好可能出现在“先预热，但用户离开界面，没有真正开始播放”的流程中；快速换片和关闭重开，则会持续经过媒体关闭与重新创建的交接点。这些记录让生命周期问题有了具体例子，也说明预热取消应当和正常播放一样进入设计与验收范围。

3. 自研要把这部分复杂性集中到播放器内部

Unity VideoPlayer 同样需要嵌入游戏自己的界面、资源加载与应用生命周期。这里不把上述第三方历史问题套用到 Unity VideoPlayer；本文对三种方案的共同关注点，是业务能否获得清晰的准备、取消、切换与释放契约。

Pulse 的自研目标，是让这些高频场景经过同一套可检查的控制流程，减少每个界面重复拼接状态判断和释放代码。

游戏场景 播放器需要提供的保证 本文对应实现
预热后取消，尚未播放 准备操作可以收尾，旧结果不能重新绑定 请求代次、取消令牌和 Request 身份检查

这里的“对象池复用”是设计与验收场景，不表示当前已经实现了独立的播放器对象池。自研也仍然承担平台适配与长期维护成本；它的具体收益，是让项目能够定义并检查从业务请求到 GPU 资源回收的整个交接过程。

二、先把需求放回播放流程

面对“通用、跨平台、无竞态、秒级首帧、流式加密”这几个目标，直接从播放器 API 开始设计，容易把所有复杂度堆到一个类里。

更合适的方式是先确定每个问题属于哪一步。

播放阶段 要解决的问题 Pulse 的处理方向
离线制作 输入编码、帧率、色彩、透明格式过多 发布前转换并校验，缩小运行时输入范围
容器与读取 首帧前读了多少数据，是否整文件复制 MP4 索引前置、按偏移读取、文件租约与 APK 区间直读
解封装与解码 各操作系统能力不同 统一输入契约，平台后端分别接入系统媒体 API
帧调度 播放、暂停、Seek、旧请求交叉 统一时钟语义，请求代次隔离，串行访问解码器
GPU 交接 CPU 认为完成，GPU 却仍在使用资源 渲染线程提交、GPU 完成查询、延迟归还样本
Unity 显示 透明布局、方向、材质和生命周期 稳定输出纹理、共享元数据约定与 UI Shader
加密数据读取 不整文件解密，还要支持 Seek 后续在原生解封装前提供可随机访问的解密字节流

其中最值得优先投入的，是解码之前的内容规范化。它能同时减少解码器、颜色处理、透明显示和时间调度所面对的组合数量。

而多线程竞态集中发生在控制请求、解码输出与 GPU 使用之间的交接处。它需要所有权和完成条件的约束，单靠统一编码解决不了。

三、如何实现通用：美术交一份母版，发布工具负责转换

1. 把通用能力放在离线工具里

游戏通常不需要像桌面媒体播放器一样，接受用户临时提供的各种视频。更常见的工作方式是：美术按生产规范导出母版，项目工具再生成运行时资源。

因此，“美术只交一种格式”应理解为交付一套明确的母版规范，包括编码、色彩、帧率和透明语义，而不仅是统一扩展名。尤其是透明视频，母版本身必须能够保留 Alpha。

Pulse 的离线工具使用 FFmpeg 处理输入；播放器运行时接入系统解码器，当前没有引入 FFmpeg 运行时软解作为兜底。

这样，输入格式的变化主要留在开发和构建环境中处理，不要求每台玩家设备都承担同样的格式适配工作。

2. 当前导出脚本收敛了哪些条件

Tools~/encodeTool/Scripts/VideoPipeline/ExportVideos.ps1 的关键参数包括：

脚本还设置目标帧率、GOP、最小关键帧间隔，并关闭场景切换触发的自适应关键帧插入。当前默认值为 30 FPS、GOP 60、CRF 18、preset veryfast。

各项约束对应不同收益：

  • 单路 H.264、8 位 yuv420p：把解码输入限制在较常见的一组能力上。
  • 固定帧率 CFR：让帧序号与播放时间之间具有稳定的映射关系。
  • SDR：限制色彩处理范围，避免把 HDR 误当作普通 8 位视频处理。
  • 固定关键帧间隔：让 Seek 需要回退并追帧的距离更可预测。
  • moov 前置：减少获得 MP4 索引时对文件尾部的依赖。
  • 分离音频和字幕：视频后端专注于画面，音频和字幕交给宿主协调。

VideoPipelineCommon.ps1 会检查 PQ、HLG 以及已知 HDR 元数据。当前方案是拒绝这类输入并要求先完成色调映射，尚未实现自动 HDR 到 SDR 转换。缺失传递特性标记时按 SDR BT.709 处理并警告，也不能据此自动识别没有正确标记的 HDR。

3. 统一编码不等于所有设备都支持

当前输出使用 H.264 High Profile。它减少了格式变化，但不能因此得出“所有支持 H.264 的设备都支持这个产物”。

Profile、Level、分辨率、帧率、参考帧和码率都会影响设备能否播放。现有脚本也没有建立完整的设备分档规则，例如强制限制输出尺寸、固定 Level，以及按档位限制峰值码率。

下一步要扩大设备范围，应优先建立目标设备的编码预算：对不同档位生成合适的尺寸、帧率和编码参数，再做实际验证。美术仍然只需要交一份母版，平台或档位差异由离线工具负责。

这种收益比运行时遇到失败后盲目增加格式分支更直接，但不意味着完全不需要回退路径。

4. 透明视频也可以转换成普通视频问题

普通 H.264 yuv420p 不携带独立 Alpha 通道。Pulse 采用上下拼接：把彩色画面与灰度 Alpha 放进同一张编码图像。

系统解码器仍然处理普通 H.264 画面。PulseVideoSurface.shader 根据元数据分别采样两个区域，把灰度值恢复为透明度，再进行 UI 混合。

单条视频流天然避免了“颜色视频与透明度视频分别解码时如何对齐帧”的额外问题。Shader 还把采样坐标限制在各区域边缘像素中心，减少跨区域过滤造成的污染。

但这项选择有明确成本：编码高度约为原高度的两倍再加隔离带，设备要处理更多像素；灰度 Alpha 也经历有损压缩。因此必须按拼接后的编码尺寸检查硬件限制，并验证边缘与渐变质量。不能只看到透明格式兼容收益，却忽略它增加的解码负担。

5. .pulse 当前仍然是 MP4

PulseContainer.ps1 在标准 MP4 末尾追加一个 Pulse UUID Box，记录显示尺寸、编码尺寸、RGB/Alpha 区域、帧数、帧率和颜色等信息。

这种方式保留 MP4 的原有结构与样本偏移，让系统解封装器继续处理标准容器；播放器只需额外读取自己的显示约定。

所以 .pulse 扩展名表达的是项目资源契约。当前 v1 是明文，它既不是新的压缩编码，也不是加密保护。

四、如何跨平台：统一契约，分别实现平台后端

跨平台不能只看 C# 能否编译。解码器提供什么表面、图形 API 怎样采样、在哪个线程提交，以及何时释放，都依赖具体平台。

Pulse 共享的是容器约定、控制入口和状态语义；平台后端负责把这些要求落实到系统 API。

1. Windows：Media Foundation 与 D3D11

使用字节流并声明 video/mp4，可以避免仅因 .pulse 扩展名导致系统无法选择正确的容器处理方式。

后端绑定 D3D 设备管理器并允许硬件变换，使用 D3D11 Video Processor 将解码表面转换到输出纹理。C# 通过外部纹理包装使用它，不逐帧创建新的 Texture2D 和 Material。

这是避免 CPU 图像回读和重新上传的路径，但仍然存在 GPU 转换、写入与同步工作，不能称为完全没有复制或处理成本。允许硬件变换也不等于已证明每台设备都在使用同一种硬件解码器。

2. Android：MediaCodec 与 OpenGLES3

Android 后端源码的首选路径是：

Surface 路径失败时，源码提供一次线性输出回退：接受布局明确的 I420 或 NV12，根据 stride、slice-height 和 crop 提取有效区域，上传平面，再由 GLES Shader 完成颜色转换。

这里的回退仍然使用系统 MediaCodec，没有引入另一套 FFmpeg 解码器。对于无法确定平面布局的 flexible 或厂商私有格式，当前代码选择报错，不猜测内存排列。

这说明跨平台还需要分层处理失败：系统解码器是否支持输入，与它的 Surface 输出能否稳定接入 Unity，是两类问题。后者可以尝试更保守的图像交接路径，前者却未必能靠换一种纹理上传方式解决。

3. 当前支持边界必须说清楚

当前 Windows 后端面向 x64、D3D11，要求相应的设备能力；Android 源码面向 ARM64、API 24+、OpenGLES3。Android 尚缺本次可引用的编译与真机验收证据，Vulkan、iOS、macOS 等后端也不能视为已经完成。

PulseNativePump 会检查当前图形 API 和原生 ABI 版本，不匹配时明确失败。这比让错误配置继续流入纹理交接阶段更容易定位。

平台扩展的工作单元应是“解码、图形交接、同步、关闭和设备生命周期”的完整闭环。增加一个平台名称或条件编译分支，还不足以交付一个平台。

五、如何处理多线程竞态：先定义谁拥有资源，再定义什么时候交接

前面提到的预热撤销、快速切换与关闭竞态，最终都要落实到请求和资源的交接上。视频播放至少同时面对三类执行者：Unity 主线程处理业务控制，工作线程读取并解码，渲染线程向 GPU 提交命令。GPU 本身又是异步执行的。

因此，锁只能解决一部分 CPU 共享状态问题。即使所有 C++ 成员访问都受锁保护，也不能证明 GPU 已经停止使用某张纹理。

1. 第一类竞态：旧请求晚到，覆盖了新请求

例如，播放 A 尚未准备完成，用户已经关闭并打开 B。A 的异步操作随后完成，如果直接绑定纹理，就可能把 B 替换掉。

PulsePlayer 使用 m_generation 区分打开和关闭请求，并在异步等待之后检查请求是否仍然有效。宿主 VideoPlaybackCoordinator 也会检查当前 Request 身份，避免旧的下载、字幕或音轨准备结果影响新会话。

取消令牌表达“这次操作不再需要”，代次或请求身份表达“这个结果是否属于当前会话”。二者承担不同职责，需要配合使用。

2. 第二类竞态：读取与 Seek 同时操作解码器

Windows 后端没有让主线程直接调用 Source Reader 的定位函数。主线程提交目标和 Seek 代次，DecodeLoop 再在同一工作线程中执行 SetCurrentPosition 与 ReadSample。

已经在途的旧解码结果还要检查其代次。即使它成功解码，也不能被当作最新 Seek 的目标画面。

3. 第三类竞态：解码样本归还过早

解码器输出的样本可能持有内部表面池中的一块资源。GPU 转换命令引用它以后，如果 CPU 立即归还样本，解码器可能复用该表面，覆盖 GPU 还没有读完的数据。

Windows 实现把样本引用保留到 GPU 完成查询成功之后，才清理 m_sample、输入视图和输入纹理，并通知工作线程继续生产。

当前应用层采用单帧槽位进行背压：前一个输出尚未消费完，工作线程就等待。这个限制不代表系统解码器内部只有一张参考帧，也不代表它在所有设备上都是吞吐最高的策略；它的价值是让当前交接关系简单且可审计。

4. 第四类竞态：旧 GPU 工作完成，被误认为新 Seek 完成

旧请求已经提交 GPU 时，通常不能假定它会立刻撤销。正确做法是允许它安全收尾，但阻止它宣布新请求完成。

这段判断发生在 GPU 完成查询成功之后。它把两个条件合并起来：资源处理确实完成，而且完成结果属于当前 Seek。

SeekAsync 等待的因此不是“定位函数已返回”，而是对应代次的目标画面已完成 GPU 提交处理。不过，这仍不等于显示器已经扫描输出了那个像素区域。

5. 第五类竞态：关闭了界面，GPU 还在采样

PulseNativePump 把原生回调分成两个阶段：帧初检查完成情况，帧末允许写入输出纹理和处理关闭退役。

帧末回调安排在当帧 UI 绘制之后，配合 GPU 完成查询，使关闭时能够覆盖之前提交的纹理使用。不能把“C# 引用已清空”当作释放原生纹理的充分条件。

完整关闭涉及多个层次：

宿主 VideoPlaybackCoordinator.RetireAsync 会等待准备操作收尾以及视频关闭完成，再释放视频资源。这样，原生读取还未结束时，下载文件不会先被删除，YooAsset 句柄也不会先被归还。

多线程问题因此被拆成四种不同的工具：锁保护共享状态，代次隔离过期结果，单线程顺序访问解码器，GPU 完成查询保护资源寿命。 它们互相补充，不能用其中一个替代全部。

六、如何流式加载并争取秒级首帧

1. 先区分本地按需读取与网络边下载边播

两者都可能被称为“流式”，但实现难度和首帧条件不同。

场景 当前代码行为
已有本地文件 按需读取，不把整个视频装入托管内存
Android APK 中未压缩资源 获取 fd、offset、length，按文件区间读取
YooAsset 资源 等资源可用后借用文件并持有租约；可满足条件的 Android 内置资源尝试直读
直接 HTTP/HTTPS 地址 下载到独占临时文件，完成后校验并开始播放器准备

VideoResourceLoader.DownloadAsync 使用 DownloadHandlerFile，避免把整段下载内容缓存在托管 byte[] 中。但它等待下载完成之后才把文件交给播放器，因此目前没有网络渐进播放。

这一区别会直接决定首帧时间的下界：如果必须先下载整个文件，单纯优化解码器并不能绕过下载时间。

2. 当前已经减少了哪些首帧前的工作

PulseMetadataReader 按 MP4 Box 的偏移扫描，只读取必要头部和 Pulse 元数据，跳过 mdat 载荷。元数据大小限制为 1 MiB，读取工作不需要随着视频载荷大小进行整文件拷贝；不过扫描开销仍与 Box 数量及存储访问延迟有关。

FileSource.ReadAt 支持按位置读取，使用同一把锁串行化定位、读取和关闭。PulseMetadataLoader 把这部分 IO 放到独立线程，并在交付结果前切回 Unity 主线程。

Android APK 路径则通过未压缩资源的文件描述符区间，让元数据读取器和 MediaExtractor 直接访问资源。这样可以省掉“先从 APK 拷出完整视频”的准备步骤。前提是打包时资源未被压缩，否则不能假定存在可用的直接文件区间。

原生解码器随后按需读取并准备首帧，不需要先解码整段视频。Unity 包装并复用输出纹理，也减少了反复创建资源的工作。

3. 还有一个容易忽略的细节：Pulse 元数据在文件尾部

虽然导出的 MP4 使用了 Fast Start，但当前 Pulse UUID 元数据是追加到文件末尾的。

对本地可定位文件，这通常只是一次跳转读取；对未来的网络渐进播放，如果只从头顺序下载，就仍可能需要等到文件尾部才能拿到显示尺寸和透明区域等必要信息。

所以，增加 HTTP Range 时必须同时考虑：

  1. 已知文件长度并能请求所需尾部区间，或者按 Box 信息定位元数据。
  2. 缓存 MP4 索引、Pulse 元数据与起播所需样本，避免碎片化小请求放大往返延迟。
  3. 或者升级容器布局，把必要元数据放到起播可获取的位置。

第三种方案不能简单把 UUID 插入现有 MP4 开头就结束。移动媒体数据可能改变样本偏移，需要正确重封装或更新相应索引。

4. 真正的网络流式读取，需要进入原生解封装层

IPulseDataSource.ReadAt 是一个有用的托管读取抽象，但当前它主要服务于元数据读取。

Windows 原生视频读取仍然通过 MFCreateFile 创建文件字节流；Android 则使用 AMediaExtractor_setDataSourceFd。系统解封装器没有自动经过 C# 的 IPulseDataSource。

因此，未来不能仅增加一个 C# HTTP 数据源，就宣称视频已经支持边下载边播。还需要让原生解封装器接入真正可按偏移读取的数据通道，例如 Windows 自定义 IMFByteStream，或在目标 Android API 范围内评估合适的数据源回调、缓存桥接方案。

这一层还要处理缺块等待、取消、超时、缓存淘汰、Range 响应校验，以及文件版本一致性。否则 Seek 可能读到缺失区间，甚至把不同版本的区块拼在一起。

5. 秒级首帧是关键路径预算

当前宿主的准备顺序中，除了视频资源，还有旧会话关闭、字幕加载、音频预加载、指定起点定位和音轨启动。

可以用下面的串行近似帮助定位耗时，实际并行化后应按关键路径计算：

VideoPlaybackTrace、PulsePreparationTimings 以及宿主调用点已经记录了多个阶段的准备耗时。这些指标用于找瓶颈，不能直接替代屏幕实际可见时刻。

如果目标是秒级首帧，应分别测试本地冷启动、缓存命中、缓存未命中、APK 直读、无音轨与带音轨，并记录 P50/P95、机型、视频编码尺寸和起播位置。当前源码能说明优化方向，不能单独证明已经达到统一的秒级指标。

后续可以根据测量结果，把独立的字幕和音轨预加载并行化，或在进入界面前预热必要资源。但这些都需要明确取消与所有权关系，也需要产品决定是否允许先显示画面再等待声音，不能只为缩短统计数字而改变播放语义。

七、如何实现流式加密：放在读取与解封装之间

1. 当前尚未实现

当前 .pulse 为明文 MP4，转码工具也明确提示 AES-CTR 尚未启用。已有代码没有端到端的视频加密导出、原生解密读取和密钥管理链路。

因此，本节讨论的是基于现有边界的下一步设计，不是对现有功能的介绍。

2. 加密层应该放在哪里

目标是避免把整个文件解密到内存，也避免在磁盘上生成完整明文副本。解密应发生在解封装器读到数据之前：

这样可以继续复用系统 MP4 解析器和 H.264 解码器。加密并不需要改变视频压缩算法，也不应该让 Unity Shader 负责恢复压缩文件。

3. 为什么随机访问是必需条件

解封装器会读取头部、索引和样本，Seek 又会跳到另一个文件位置。一个只能从头逐字节解密的接口，会让随机定位变得很昂贵。

AES-CTR 适合讨论这类偏移读取。对于加密区域内的逻辑字节偏移 p，AES 块大小为 16 字节：

按照文件协议，从对应计数器位置生成密钥流，跳过块内前 skipBytes 个字节，就可以解密目标区间，而不必从文件开头处理所有内容。

这里的 p 必须相对明确的加密区域定义。计数器布局、字节序、跨块进位和溢出规则都属于协议的一部分；同一密钥下不得复用相同的 nonce/计数器范围。

这些要求也说明，加密不能只是导出脚本里多加一个开关。文件格式、导出器和各平台读取器必须采用完全一致的定义。

4. 只有 CTR 还不足以形成完整保护方案

CTR 提供机密性，不提供篡改检测。对密文进行修改可能使明文发生可控变化，因而不应把它作为完整的文件认证方案。

流式读取可以使用独立认证的分块设计，例如经过正确设计的分块 AEAD，或 CTR 配合每块独立 MAC。格式需要记录版本、逻辑明文长度、块尺寸、密钥标识和 nonce 等信息，并将文件身份、块序号、长度及关键头部字段纳入认证，防止区块替换、重排与截断。

读取某个范围时，先定位相关块，获取并验证完整认证块，再把所需明文字节交给解封装器。块过大会增加随机读取和首帧放大，块过小又会增加标签、请求和调度开销，需要按实际存储与网络条件选择。

对于本地随机读取，分块认证避免等待整文件校验才允许起播；对于网络路径，它也有利于把密文缓存与验证后的短期明文缓冲分开管理。

密钥如何交付、轮换、缓存和撤销，则是另一部分设计。客户端最终必须获得可播放内容，所以自定义加密能提高资源直接提取和篡改的门槛，但不等同于系统 DRM 或不可截取的显示链路。

八、这款软件的边界，来自每一步的具体需求

Pulse 的核心设计可以归纳为四个落点。

兼容性优先在离线制作与解码输入处收敛。 统一编码、位深、帧率、透明布局，并继续补齐设备分档，比把所有输入差异都留给运行时更容易测试。平台输出路径仍需有边界明确的回退，而不是宣称一种编码覆盖所有设备。

多线程安全在交接协议处收敛。 请求代次解决过期结果，解码线程解决读取与定位的访问顺序，GPU 完成查询解决表面和纹理的寿命。每一种机制只负责它能够证明的事情。

首帧优化在数据访问与准备关键路径处收敛。 当前已经减少本地整文件复制、托管内存加载和逐帧资源创建；网络渐进播放、尾部元数据获取和宿主准备并行化仍有具体工作要做。

流式加密在原生读取与解封装之间收敛。 它应该改变字节如何获得和验证，同时尽量保持后续解封装、解码与渲染链路不变。

这就是按播放步骤量身定做软件的含义：内容可以由工具约束的，就在离线阶段解决；平台必须分别实现的，就放入平台后端；跨线程必须共同遵守的，就定义清楚所有权和完成条件。自研的范围由这些具体需求决定，而不是由“做一个功能更多的播放器”决定。
