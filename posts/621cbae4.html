AlloyFramework的实现(六) - 音频系统

发表于2026-11-17|更新于2026-11-18
|总字数:6.6k|阅读时长:21分钟

前两篇分别介绍了 资源管理系统，以及业务代码准备、配置与数据模型。资源和配置就绪、Model 管理入口建立后，启动流程继续进入音频模块。音频系统除了加载资源，还要管理播放实例、空间位置、音量、结束通知，以及应用切后台时的行为。

例如，角色释放技能时，业务希望表达的是“在角色身上播放这个音效”；离开关卡时，希望本关卡的声音和预加载资源能够一起退出。业务不应该为此调用 AkUnitySoundEngine，也不应该持有 FMOD 的事件实例或直接管理 Wwise 的 Bank。

AlloyFramework 因此继续使用三层结构：业务层 → 框架层 → 实现层。当前音频实现层使用 Wwise，业务通过 AudioManager、AudioPlayOptions、AudioScope 等框架类型表达需求。

Wwise 是音频中间件，负责根据事件和制作规则组织声音，完成媒体读取、混音和输出。关于它生成的 .bnk、.wem，以及从制作到运行时播放的过程，可以先阅读 《Unity音频中间件Wwise的生成物与流程浅析》。本文重点介绍这些能力如何接入框架。

本文以当前源码为准。设计目标包含统一音频组、事件与参数建模，以及前后台和系统音频中断处理；当前已完成 Wwise 后端与主要生命周期管理，Loop 参数、调用级完成回调和 Android 音频焦点接入仍有待补齐，不将这些目标写成已有能力。

一、三层结构各自负责什么

业务只表达播放需求，框架管理请求与生命周期，实现层负责将框架契约转换为音频引擎调用。

这与资源模块的依赖倒置思路一致：运行时调用逐层向下，接口却由框架层定义，具体实现依赖并实现这些接口。框架通用播放流程通过 IAudioBackend 工作，不需要引用 AK 或 FMOD 的类型。

    graph TD
    Business["业务层：界面、角色、关卡"]
    Manager["框架层：AudioManager"]
    Contract["框架契约：IAudioBackend"]
    Backend["实现层：WwiseAudioBackend"]
    Engine["Wwise SDK：事件、Bank、原生播放实例"]
    Business -->|事件名称与框架参数| Manager
    Manager -->|通过接口调用| Contract
    Contract -->|当前实现| Backend
    Backend --> Engine

当前代码主要分布在两个目录：

位置 主要职责
Runtime/Framework/Audio 公共契约、播放请求、音频组、作用域、缓存与模块生命周期
Runtime/AudioWwise Wwise 初始化、Bank 加载、事件提交、回调、空间对象和平台适配

Alloy.Runtime 程序集没有引用 Wwise。Alloy.Audio.Wwise 则引用框架与 AK.Wwise.Unity.API，并关闭自动引用，让使用者显式选择是否依赖这个后端。

这里还需要区分业务逻辑与启动装配。当前项目的 GameAudioInstaller 位于 Bootstrap，它知道并调用 WwiseAudioInstaller，负责选择具体实现。日常业务播放不需要知道这个选择。如果要求整个 Game 工程都不能出现实现层类型，就还需要把这段装配代码移到独立的集成程序集。

隔离也不止是方法名称：返回值、回调参数和停止方式都应该使用框架类型。当前业务持有的是框架生成的 long 播放标识，Wwise 的 Playing ID 保存在后端内部，不会作为业务播放句柄交付。

二、先定义音频资源组与播放契约

1. AudioGroup：用逻辑组表达一份音频资源的使用权

不同方案的资源载体不同：Wwise 常见的是 .bnk 及其关联媒体，FMOD 使用 .bank，Unity 原生音频可以通过 AssetBundle 交付 AudioClip。

框架需要提供统一的 audioGroup 概念，让业务只关心“准备哪个组、何时归还”，由具体后端解释组内资源。一个逻辑组可以包含多个文件和共享依赖，不必与一个物理文件一一对应。

当前对应的类型是 AudioContentGroup，事件通过 AudioEventDependency 关联到一个或多个组：

    graph TD
    Event["事件 Key"] --> Mapping["AudioEventDependency"]
    Mapping --> Group["一个或多个 AudioContentGroup"]
    Group --> Dependency["共享依赖组"]
    Group --> Files["资源文件与后端加载描述"]
    Files --> Lease["AudioContentLease：保持文件可用"]
    Lease --> Native["后端加载原生音频资源"]

当前组描述中仍包含 Banks、PreparedEvents，以及 User / Event / Bus 等 Bank 类型。这些设计适合现有 Wwise 接入，但还带有具体后端的资源结构。未来接入 FMOD 和 Unity 原生后端时，需要将这部分描述进一步下沉，让公共层主要保留组标识、依赖关系和生命周期约定。

接口覆盖初始化、组加载与卸载、播放、停止、暂停、参数、状态、切换和监听器设置。下面节选其中与播放最直接相关的部分：

所谓“三家能力的超集”，应当是业务可以用统一模型表达需求，同时能够知道当前后端是否支持。不能因为统一了方法名称，就假定所有后端都能执行相同语义；无法支持的请求应明确失败，避免悄悄忽略参数。

四、一次播放如何经过三层

业务调用之后，框架不会立刻假定事件已经能够播放，而是先解决内容依赖：

    graph TD
    Request["业务提交事件与参数"] --> Validate["校验参数、作用域与后端能力"]
    Validate --> Lookup["查找事件依赖的音频组"]
    Lookup --> Ready{"所需内容是否已就绪"}
    Ready -->|是| Hold["播放实例持有组引用"]
    Ready -->|否且允许加载| Load["准备文件并加载原生组"]
    Ready -->|否且要求就绪| Fail["返回未就绪结果"]
    Load --> Hold
    Hold --> Recheck["再次检查取消与会话有效性"]
    Recheck --> Submit["通过后端提交事件并应用音量"]
    Submit --> Started["发送开始通知"]
    Started --> Ended["等待真实结束通知"]
    Ended --> Release["结束播放记录并归还组引用"]

1. 框架先准备依赖，再提交播放

AudioManager 为请求创建独立的播放记录，关联调用者取消令牌、音频会话令牌和可选作用域令牌。随后根据清单找到事件对应的组，为本次播放取得组租约。

默认的 LoadIfNeeded 会按需加载；RequireReady 则要求资源已经准备好，否则报告未就绪。对时机敏感的技能音效，可以在进入战斗时预加载，再使用后者避免把第一次加载延迟带入播放时刻。

等待资源完成后还要再次检查取消、会话与作用域。如果界面已经关闭，或者上一轮音频会话已经退出，不能因为加载现在才完成就补播旧声音。

2. 内容提供者与 Wwise 后端分别负责什么

ResourceAudioContentProvider 通过框架资源系统取得原始文件并保持租约；Wwise 后端再加载 Bank、准备需要的事件媒体。前者保证文件可用，后者保证引擎能够使用这些内容，两者的生命周期不能混为一谈。

Wwise 还可能在播放过程中继续读取流式媒体，因此不能在 PostEvent 返回后立刻释放原始文件。当前实现会保留内容引用，并通过 WwiseReadFile 处理资源缓存文件名与 Wwise 查找文件名之间的关系；特定流式内容还支持原生文件包交付。

文件链接方式与平台文件系统有关，不是业务层应承担的细节。真机接入时仍需要验证文件路径、可写权限和实际流式读取行为。

五、播放实例与资源释放必须成对设计

1. 预加载引用和播放引用分别持有

预加载表示“接下来可能用到”，播放表示“现在正在使用”。两者分别持有组引用。

例如，关卡预加载了 Battle 组，之后两个角色分别播放其中的事件。即使关卡提前归还预加载引用，两个播放实例仍然保留各自引用；待声音退出，框架才归还播放引用。

因此，释放 AudioGroupLease 不等于停止声音；停止声音也不等于立即卸载全部 Bank。引用归零后，组还可以按配置进入闲置缓存，以减少短时间内重复加载的开销。

当前缓存使用文件大小估算和保留时长进行管理，不能将它理解为 Wwise 实际内存占用的硬上限。

使用 AudioEmitter 跟随 Transform 时，同样要明确所有者；目标销毁或 Emitter 释放后，后端更新会处理对应声音与原生对象。业务无需为角色添加 AK 发声组件。

3. 开始、结束和失败是三种通知

当前框架通过事件系统发送：

消息 含义
Audio.Started 后端已接受播放并完成当前开始流程
Audio.Ended 播放进入结束状态，包括自然结束和主动停止等路径
Audio.Failed 请求失败

业务处理结束消息时，应根据 AudioPlaybackNotification.Playback.PlayID 匹配具体实例，并在业务退出时解除订阅。不能只按事件名称匹配，因为相同事件可以并发播放。

当前 PlayAudio 的 onStarted 不是完成回调。要达到“Event + 参数 + 完成回调”的目标，还需要为单次请求增加结束回调，并明确它是否覆盖主动停止、取消、作用域释放和失败。

源码还有一处需要修正的语义：虽然定义了 EAudioEndReason.Completed，自然结束路径当前没有将初始的 Unknown 更新为 Completed。因此现阶段不能依赖这个枚举值准确识别自然播完；这属于当前实现的待完善项。

六、统一音量与循环行为

例如，线性增益 0.5 约为 -6.02 dB；它不代表人的主观听感一定减少一半。业务使用统一数值，后端处理具体引擎的单位差异。

当前 Wwise 工程需要配置 AlloyMasterVolume、AlloyBGMVolume、AlloySFXVolume 和 AlloyInstanceVolume，并让参数曲线正确作用到对应音量。仅在 C# 中调用 RTPC，不足以保证制作侧产生预期效果。

2. Loop 需要明确跨后端语义

当前 AudioPlayOptions 没有 Loop 字段，后端也没有统一循环接口，循环由 Wwise 事件制作规则决定。因此不能在业务示例里写一个当前不存在的 Loop = true。

后续增加循环能力时，首先要约定“循环什么”：是单个音频片段，还是整个可能包含多个声音、延迟与随机容器的事件？还要区分沿用制作设置、强制单次和强制循环。

Unity 的 AudioSource.loop、FMOD 事件时间轴与 Wwise 事件并不天然具有完全相同的循环语义。可以通过制作规范、参数或配套事件实现统一行为；不支持的情况应由后端明确拒绝。简单在每次结束回调里重新播放，不保证无缝衔接，也会影响实例标识和完成通知。

七、前后台与系统音频中断如何处理

音频生命周期至少涉及三类来源：App 进入后台、iOS 音频会话中断、Android 音频焦点变化。它们可能同时发生，不能只用“窗口有没有焦点”解释全部情况。

1. App 切后台：接入 Unity 生命周期

当前 WwiseAudioHost 接收 Unity 回调：

后端分别保存暂停状态与窗口焦点。非 iOS 真机分支在任一条件要求暂停时调用 Suspend()，两个条件都恢复后调用 WakeupFromSuspend()。

这比只在收到 Focus 恢复时直接唤醒更稳妥，因为应用可能仍处于 Pause 状态。不过，挂起整个引擎与业务暂停某个播放实例属于不同层次，业务不应通过结束通知推断应用是否进入后台。

2. iOS 来电和闹钟：由原生音频会话处理

当前后端在 iOS 真机上跳过上述手动挂起逻辑，交由 Wwise 原生音频会话处理。已安装 SDK 的 AkSoundEngineController 也注明，iOS 应用中断由声音引擎处理，因此这里有对应的集成依据。

但“交给 SDK”不等于已经验证所有场景。音频会话类别、与其他应用的混音策略、输出路由和中断后的恢复行为仍需要结合项目设置确认。来电接听与拒接、闹钟结束、锁屏及返回前台，都应该在目标设备上验证。

当前框架还没有把这些原生中断原因统一通知给业务。如果视频、字幕或节奏逻辑也需要同步暂停，还需要单独定义跨系统的协调方式。

3. Android 音频焦点：当前仍需补齐

Unity 的 OnApplicationFocus 表示窗口焦点，不是 Android 系统的 Audio Focus。其他应用请求音频播放时，本应用不一定失去窗口焦点。

当前检查到的框架源码没有完整的音频焦点请求与变化监听，不能仅凭 OnApplicationFocus 就认定已经覆盖这个需求。后续应在平台适配中接入音频焦点，并区分暂时丢失、永久丢失、允许降低音量继续播放以及重新获得焦点等情况。具体申请方式还需要匹配项目目标 Android 版本。

框架层可以维护多个独立的暂停原因：后台、系统中断、音频焦点丢失。只有所有需要暂停的原因都解除后，才允许恢复系统音频；业务主动暂停的实例也不应被系统恢复流程误恢复。这是后续统一生命周期策略的方向，当前实现尚未覆盖完整状态集合。

八、退出与更换实现层

1. 先关闭音频，再关闭它依赖的资源服务

正常关闭时，AudioLifecycleManager 等待 AudioManager.ShutdownAsync，让未完成请求和内容持有得到清理，再解除更新与低内存订阅。Wwise 后端负责终止自己拥有的引擎、原生对象和文件访问关系。

应用强制退出不能依赖异步流程完整执行，因此还提供 ShutdownImmediately 作为兜底。正常业务退出仍应优先释放自己的作用域、Emitter 和预加载租约。

资源服务必须保持到音频清理完成，因为音频还持有初始化设置与原始文件租约。这与第四篇资源系统中“先结束资源使用，再关闭资源服务”的原则一致。

2. 新后端需要同时适配播放与内容

如果将 Wwise 更换为 FMOD 或 Unity 原生音频，接入工作包括：

  1. 实现 IAudioBackend，将初始化、组加载、播放、停止和真实结束通知映射到新后端。
  2. 按实际能力实现音量、时间轴等扩展接口，明确无法支持的请求。
  3. 调整内容描述与提供者，让逻辑组映射到新后端的 Bank、AB 或 AudioClip 集合。
  4. 在启动装配处切换实现，配套修改制作、构建与资源发布流程。
  5. 验证并发播放、取消、作用域释放、自然结束、资源卸载和移动平台中断恢复。

业务事件名称也需要稳定的映射约定。当前 Key 直接交给 Wwise 作为事件名称；未来 FMOD 使用事件路径、Unity 使用配置索引时，可以在后端或内容映射中转换，避免让业务改写所有播放字符串。

当前仓库的运行时音频后端只有 Wwise，还没有通过另外两套实现验证全部契约。更换后端的目标是保持业务表达稳定，但仍需要适配资源模型、制作规则和能力差异。

九、总结

AlloyFramework 的音频系统延续了资源模块的三层设计：业务通过事件与框架参数表达播放需求，框架管理音频组、播放实例和作用域，Wwise 后端负责原生引擎与资源操作。

这套实现的关键是把资源可用、播放已提交和声音已结束分开管理。预加载与播放分别持有引用，真正结束后才归还播放资源，业务退出通过作用域统一收口。

目前主要播放链路、线性音量、组管理和 Wwise 生命周期接入已经具备；统一循环、调用级结束回调、自然结束原因标记，以及 Android 音频焦点仍需要完善。后续扩展 FMOD 和 Unity 原生音频时，也应继续检验公共契约是否真正独立于具体后端。
