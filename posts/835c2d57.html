Unity UI的粒子特效的层级处理

发表于2026-10-31|更新于2026-10-31
|总字数:6k|阅读时长:18分钟

在 Unity 中，给背包里的高品质装备加一圈粒子光效，看起来是一件很简单的事：创建一个 Particle System，把它放在物品图标下面，调整位置和大小。

但实际操作时，经常会遇到几个问题：

  • 粒子在 Scene 窗口中正常显示，到了 Game 窗口却看不到。
  • 粒子可以显示，却无法稳定地放在 UI 背景和物品图标之间。
  • 背包滚动时，粒子会跑出列表区域，无法跟随 UI 一起被 Mask 或 RectMask2D 裁剪。

这些问题的共同原因，是普通粒子和 UGUI 使用了不同的渲染路径。要理解 UIParticle 为什么能解决它们，需要先从这两条路径说起。

Scene 中可见，Game 中不可见

一、为什么粒子放到 Canvas 下，仍然不能像 UI 一样显示？

普通粒子系统通过 ParticleSystemRenderer 参与场景渲染；UGUI 的 Image、Text 等元素则通过 CanvasRenderer 参与 Canvas 渲染。

把 Particle System 设为 UI 节点的子物体，只是改变了 Transform 层级，不会把 ParticleSystemRenderer 变成 CanvasRenderer。

这里经常有一种简化说法：

粒子在世界空间，UI 在屏幕空间，所以两者无法正确叠加。

这可以帮助建立直觉，但并不完全准确。

粒子的模拟空间可以是 Local、World 或 Custom；Canvas 也可以使用 Screen Space - Overlay、Screen Space - Camera 或 World Space。即使是屏幕空间 UI，其网格也有局部坐标和对应的变换。

真正影响层级与裁剪的，是它们是否进入了同一套 UI 渲染流程。

以 Screen Space - Overlay 为例，Canvas 通常绘制在场景相机输出之上。粒子即使被相机正常渲染，也可能被后绘制的不透明 UI 遮住，因此看起来像是“粒子消失了”。

而对于 UI 夹层，我们想要的是：

普通 Particle System 并不会因为在 Hierarchy 中位于背景与图标之间，就自动插入这两个 UI 元素的绘制顺序。

普通粒子无法通过兄弟节点顺序实现 UI 夹层

裁剪也有相同的问题。Mask 依赖 UI 的模板缓冲机制及对应材质处理；RectMask2D 则通过 UI 裁剪流程约束可裁剪元素。普通 ParticleSystemRenderer 不会自动接入这些机制。

普通粒子溢出 UI 裁剪范围

二、方案一：用相机与排序设置控制显示顺序

一种常见处理方式，是继续使用原生 ParticleSystemRenderer，通过相机和排序设置，让粒子显示在指定位置。

例如将 UI 拆成背景层与前景层：

然后结合 Canvas 的排序设置、粒子的 Sorting Layer 和 Order in Layer，或多相机的绘制顺序控制叠加关系。

需要注意，这些设置并不是一个可以任意互相覆盖的全局优先级：

  • Camera Depth 控制相机的先后关系，具体行为也与渲染管线有关；URP 中通常还需要考虑 Camera Stack。
  • Sorting Layer 和 Order in Layer 控制适用渲染对象的排序。
  • Screen Space - Overlay UI 并不能简单地通过提高场景相机 Depth，让普通粒子任意插入其中。

因此，为了实现夹层，往往需要调整 Canvas 模式、拆分 Canvas，甚至增加专用相机。

以 Screen Space - Camera 为例，Image、Text 本身没有供我们独立设置的 Sorting Layer 和 Order in Layer。要让某个 UI 节点或一组节点独立参与这类排序，就需要为它们配置单独的 Canvas；如果是嵌套 Canvas，还需要开启 Override Sorting。这里并不是要求每个 Image、Text 都添加 Canvas，而是每个需要独立排序的 UI 层都要有对应的 Canvas。

普通粒子则不同：它使用 Particle System 的 Renderer 模块中的 Sorting Layer 和 Order in Layer。给普通粒子节点添加 Canvas，并不会让 ParticleSystemRenderer 服从这个 Canvas 的排序。

拆分 Canvas 的代价，是打断原本可能成立的 UI 合批。UGUI 以 Canvas 为批处理边界，不同 Canvas 中的 UI 元素不能跨 Canvas 合批。 即使图片使用相同材质和图集，一旦被拆进不同 Canvas，也无法再作为同一个 UI 批次提交，因此会增加 Draw Call（DC）的风险。

例如，多张原本满足合批条件的图片，在同一个 Canvas 中可能只需要一个绘制批次；如果为了与粒子穿插，将它们拆成多个独立 Canvas，这些图片就需要分别提交。对于背包，如果每个格子都拆出背景 Canvas 和前景 Canvas，批次数量便可能随可见格子数增加。

这并不意味着“一个 Canvas 永远对应一个 Draw Call”：同一个 Canvas 内部仍可能因材质、纹理、遮罩和重叠顺序不同而产生多个批次；如果这些元素原本就不能合批，拆分后的 DC 增幅也不一定明显。这里的核心代价，是丢失跨这些节点合批的机会，最终应通过 Frame Debugger 确认。

这种方案的优势，是保留了粒子原有的渲染流程，不需要每帧额外把粒子烘焙成 UGUI 网格。与后面介绍的 UIParticle 相比，它通常能避免这部分 CPU 开销。

但它省去的是额外的网格烘焙开销，并不保证整体性能更好。新增相机、拆分 Canvas 导致的合批中断，以及额外的渲染批次，都需要一起纳入评估。

更大的问题是维护复杂度：界面越复杂，需要控制的夹层越多，Canvas 和排序配置也越容易失控。对于 Scroll View 中每个物品都需要独立夹层的情况，这种方式尤其不方便。

而且，调整渲染顺序本身，并不能让普通粒子自动支持 Mask 和 RectMask2D。

使用 10、15、20 三个排序值，依次排列图片、粒子、图片。

五、解决了层级，也引入了每帧网格开销

粒子的位置、大小、颜色和数量会变化，因此当前实现需要持续更新网格。

可以看到，烘焙和网格后处理占据了主要开销。

其中 Combine Mesh 的采样范围不只是矩阵变换，还包含：

  • CombineMeshes。
  • 包围盒重新计算。
  • 条件性的顶点颜色空间转换。
  • IMeshModifier 网格修改器处理。

因此，单纯把坐标变换移到 Shader，并不等于可以消除整个阶段的成本。

六、背包里每个物品都有特效，如何避免重复计算？

假设一个背包显示了：

  • 20 个蓝色物品，使用同一种光点特效。
  • 15 个紫色物品，使用同一种环绕特效。
  • 5 个金色物品，使用同一种火焰特效。

如果每个格子都独立运行，便需要处理 40 份粒子特效。即使其中许多外观相同，它们仍各自模拟、烘焙和转换网格。

这正是 Mesh Sharing 适合解决的问题。

它的思路是：

同一种特效只计算一份网格，再交给多个 UI 节点显示。

共享后的组织方式可以是：

特效模板 实例数量 Group ID 每帧更新的实例数量
蓝色光点 20 100 1
紫色环绕 15 200 1
金色火焰 5 300 1

这时，主要模拟和网格生成工作就从 40 份缩减为 3 份。每份特效内部包含的多个粒子系统，仍然需要分别处理。

对于频繁创建和回收的背包格子，可以使用 Auto 模式，为同模板设置相同的固定 Group ID，不同模板设置不同 ID。如果 Inspector 配置的是 Group ID 范围，应将最小值和最大值设为一致，避免同模板被随机分配到不同组。

不过，共享也意味着一些约束：

  • 同组应有匹配的粒子系统结构和 Renderer 顺序。
  • 同组显示相同的粒子形态和动画进度。
  • 当前实现会同时向副本设置主实例的渲染材质，不能简单依靠副本上的不同材质保留品质差异。
  • 不同效果不能仅因为想省性能，就放进同一个组。

如果全部同步显得机械，可以将同模板分成少量共享组，用多几份计算换取一定的视觉差异；要产生不同相位，还需让各组采用不同的启动时机或初始状态。

七、Mesh Sharing 不等于 Draw Call 合批

Mesh Sharing 主要减少的是重复模拟、烘焙和网格处理。

Canvas 合批主要减少的是渲染批次，它与材质、纹理、裁剪状态和绘制顺序等因素有关。

因此：

不同 Mesh 可以被 Canvas 合批，共享同一个 Mesh 也不保证只有一个 Draw Call。

即使共享成功，每个可见物品仍有自己的 UI 渲染节点，网格提交、Canvas 处理和 GPU 像素绘制依然有成本。特别是透明粒子覆盖面积较大时，重复叠加带来的 GPU 开销不会因为共享网格而消失。

八、图片、文字与粒子穿插：为什么层级正确了，Draw Call 却上升了？

UIParticle 让粒子进入了 UI 渲染流程，但这不意味着它能与所有 UI 元素合成一次绘制。背包里更常见的情况，是图片、文字和粒子交替出现：

图片可能使用 UI 图集，文字使用字体图集，粒子又使用自己的纹理、Shader 或混合模式。当这些元素的渲染状态不兼容，且相互遮挡要求保留绘制顺序时，就容易形成多个批次。

例如，假设两张图片使用相同材质和图集，它们之间夹着一段使用字体材质的文字：

如果三者相互覆盖，而且必须保留上述叠加效果，就不能简单把两张图片提前合并绘制，再统一画文字。因为这样会把原本位于文字上方的图片 B 移到文字下方，改变最终画面。

透明 UI 的绘制顺序本身就是视觉效果的一部分。合批必须尊重这种关系。

不过，不能把“Hierarchy 中图片和文字交错”直接等同于“一定增加相同数量的 Draw Call”。UGUI 会结合元素的重叠关系和渲染状态构建批次；互不重叠的元素可能有更多合批空间。实际结果应通过 Frame Debugger 检查，不能只数节点或材质切换次数。粒子的可见范围和网格包围盒较大时，也更容易与周围元素产生重叠约束。

在滑动列表中，这个问题尤其容易被忽略：两个 Item 来自同一个 Prefab，图片、文字和特效配置几乎一样，我们自然希望它们能复用相同的渲染状态，增加可见 Item 时尽量不增加绘制批次。

这里的目标需要说准确：多个相同 Item 尽量维持与一个 Item 接近的批次数量，不等于多个 Item 只有一个 Item 的总性能消耗。 即使成功合批，更多 Item 仍然意味着更多顶点、像素绘制，以及可能增加的布局、网格更新和粒子处理。Mesh Sharing 可以减少重复粒子计算，也不能消除所有随数量增长的成本。

不过，Item 或 Prefab 本身不是 UGUI 的合批边界。要判断是不是穿插造成的，需要在 Frame Debugger 中逐项比较实际提交的材质、纹理和裁剪状态，同时检查 Canvas 归属以及元素的重叠关系。即使两个 Item 视觉上分开，较大的文字矩形、透明图片区域或粒子包围盒，也可能让参与批处理判断的范围产生重叠，从而限制跨 Item 重排。若每个 Item 还有独立 Canvas、Mask 或不同材质实例，也会出现类似结果。

因此，排查时既要看“两个 Item 是否使用相同资源”，也要看“这些资源能否在保持正确遮挡关系的前提下连续绘制”。当断批确实来自必须保留的穿插顺序时，仅仅统一图集或开启 Mesh Sharing 无法解决，需要回到制作阶段约定分层和效果范围。

1. 为什么不能等做完后，再统一调整顺序？

为了减少材质切换，很容易想到把所有图片放一起、所有粒子放一起、所有文字放一起。但这只在视觉设计允许时成立。

例如，某个品质光效原本要求在物品图标背后旋转，另一个光效要求覆盖图标边缘，还有一个要求从数量文字前方掠过。此时把它们全部搬到同一层，就会破坏已经确定的显示效果。

这类问题到了开发后期，往往只能在视觉还原与渲染成本之间取舍。因此，更合理的做法是在 UI 和特效制作阶段就确定分层规范，让视觉设计与批处理需求共同约束资源制作。

2. 为重复列表约定固定的视觉层

以背包为例，可以先约定从后向前的层级：

视觉层 内容 制作约束
背景层 槽位底图、底色 尽量使用统一 UI 图集和共享材质
底层特效 品质光晕、背景流光 保持在物品图标后方，不越过数量文字
物品层 物品图标、品质边框 明确边框与图标的先后关系，避免任意穿插
前景特效 少量闪光、选中特效 统一显示在图标上方、文字下方，限制覆盖范围
信息层 数量、等级、状态标识 保持信息可读，字体和材质尽量统一

这里约定的是视觉关系，不是要求每一层都创建一个 Canvas。额外拆分 Canvas 会形成批处理边界，也会引入管理成本，需要根据更新频率和实际采样决定。

如果不同格子之间不会相互遮挡、不会各自使用不同的遮罩，而且上述视觉关系允许，可以进一步将同一视觉层集中组织，例如统一管理可见格子的底层特效。这能为相同材质的元素创造更多合批机会，但需要同步滚动位置、格子复用和裁剪关系，不能仅靠修改兄弟节点顺序完成。

如果界面有重叠卡片、拖拽置顶，或要求某个格子的全部内容覆盖另一个格子，则需要保留对应的整体前后关系，不能强行按全局视觉层拆散。

3. 把资源规范和效果预算一起确定

分层约定还需要配合资源规范：

  • 图片与字体： 能共用图集和材质的资源尽量复用；文字尽量统一字体资源，关注字体回退、额外材质和子网格带来的批次。
  • 粒子材质： 同类品质特效尽量统一 Shader、纹理和混合模式，避免每个格子创建独立材质。使用同一图集只是合批条件之一，Shader、裁剪和其他渲染状态仍需兼容。
  • 特效范围： 明确光晕和拖尾能否越过格子边界，限制无必要的大范围覆盖，减少相邻格子之间的叠加与透明像素开销。
  • 遮罩与 Canvas： 同一列表优先复用统一的 Viewport 裁剪，避免无必要的逐格遮罩和独立 Canvas。确实需要不同裁剪效果时，应接受相应成本。
  • 复杂效果： 常驻品质效果保持简单，将复杂粒子集中到选中、获得奖励或展开详情等少量重点状态。

制作验收应使用实际规模的背包界面，同时放入图片、文字和多种品质特效。CPU Profiler 用于观察模拟和网格更新开销，Frame Debugger 用于检查实际绘制批次、材质与裁剪状态，并结合 GPU 耗时判断透明叠加的影响。

目标不是不惜代价把 Draw Call 压到最低，而是在保持正确显示效果的前提下，避免本可通过制作规范消除的渲染开销。 Mesh Sharing 解决重复计算，分层与资源规范减少不必要的批次，两者需要配合使用。

九、控制背包特效的整体成本

背包还需要注意屏幕外特效。被 RectMask2D 裁掉，只意味着不可见，并不必然停止粒子模拟和网格烘焙。当前 UpdateMesh 的提前退出条件没有检查 canvasRenderer.cull，因此最好结合列表虚拟化，只激活可见格子的特效。

对于实际项目，可以优先采用这样的组合：

  • 按特效模板开启 Mesh Sharing。
  • 回收或停用不可见格子的特效。
  • 控制每种特效的粒子数量、拖尾复杂度和透明覆盖面积。
  • 用 UI Shader 或序列帧承担常驻光圈、流光，将复杂粒子留给选中状态或重点物品。

UIParticle 解决层级问题的关键，是将粒子生成的几何转换为 UI 局部网格，让它进入 Canvas 渲染流程。理解这条路径，也就能理解它的性能代价来自哪里，以及为什么背包这类重复特效场景需要 Mesh Sharing。
