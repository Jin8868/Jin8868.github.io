AssetBundle 的加载与卸载：从内存增长到生命周期管理

上一篇《Unity-AssetBundle结构解析》已经介绍了 UnityFS 容器、SerializedFile、清单与跨包引用，以及压缩方式对读取行为的影响。本文接着讨论资源进入内存以后的事情：C# 引用、引擎对象和 GPU 数据各由谁持有，界面关闭后又该如何释放。

下面以反复打开、关闭角色预览界面为例，按照问题背景、管理目标、处理过程和结果验证的顺序，梳理加载与卸载之间的关系。

一、问题背景：界面关了，资源为什么还在

角色预览界面的逻辑很直观：打开时加载角色包，读取 Prefab 并创建实例；关闭时销毁角色，再卸载 AB 包。

但只要卸载时机或资源归属处理不当，就可能出现两种现象：使用 Unload(false) 后，角色还能正常显示，但反复开关界面，内存中逐渐出现多份相同纹理；改为 Unload(true) 后，资源被释放了，仍在使用这些资源的角色却丢失了 Mesh 或材质。

这两个现象指向同一个问题：界面实例、AB 包和资源对象，并不共享同一个生命周期。 销毁实例，不等于已经释放它用过的全部资源；卸载包，也不一定会销毁此前加载的对象。

二、管理目标：明确谁在使用，什么时候能释放

这个场景需要解决的，不只是让内存下降，还包括保证资源在使用期间有效，以及避免下次打开界面时无意间再加载一份。

具体可以归纳为三个目标：

  1. 使用期间保持有效。 界面实例、对象池或其他系统仍在引用资源时，不能提前销毁资源。
  2. 重复进入时可复用。 同一份逻辑资源仍然存活时，应有明确的复用或释放策略。
  3. 退出后能够验证。 能够确认引用已经解除、对象得到回收，而不只是观察进程内存有没有立刻下降。

要做到这些，需要先分清各个 API 实际处理的是哪一部分。

三、处理过程：把加载、使用和回收串起来

1. 先确定内存在哪里

以本地 AB 包为例，加载过程及各部分的关系如下：

清理时也要分别处理：资源卸载负责 Native 对象及相关 GPU 资源，GC 负责不可达的托管包装和业务对象。 图中表示逻辑归属，统一内存设备上的 CPU 与 GPU 可能共享物理内存。

如果包已经在本地，通常优先使用 LoadFromFile 或 LoadFromFileAsync，省去先读取整个托管数组的过程。

前文已经解释了包的按需读取与解压机制，这里只保留一个与内存管理有关的区别：LoadFromFile 返回的是包的访问入口，LoadAsset 返回的是具体资源对象。打开包不代表包内所有资源都已加载；卸载入口，也不必然销毁已经加载的对象。[1]

3. 确认资源对象和 GPU 数据的加载过程

调用 LoadAsset 后，Unity 会创建对应的底层资源对象，并向 C# 返回 Texture2D 包装对象。下文默认相关依赖包已经准备好，依赖解析过程沿用前文，不再展开。

纹理和 Mesh 还涉及 GPU 数据的上传。这里容易产生一个误解：认为 LoadAsset 只准备 CPU 数据，直到第一次渲染时才上传显存。

实际并没有这样统一的时间界限。Unity 有同步和异步上传管线，数据可能在加载过程中就上传到 GPU，也可能通过缓冲区分帧传输。具体行为取决于资源设置、加载路径及平台，不能仅凭“还没有渲染过”判断显存占用。[2]

Mesh.UploadMeshData(true) 可以提交 Mesh 数据，并释放脚本读取所需的 CPU 数据副本；这里释放的是 Native 侧的 CPU 数据，不是 C# 包装，GPU 数据仍然保留。它主要用于明确管理 Mesh 数据，并不是加载 AB 资源时必须补上的步骤。

Read/Write 保留的是什么

纹理开启 Read/Write Enabled 后，Unity 会保留可供 CPU 访问的像素数据，以支持 GetPixels 等操作。这份数据会增加常驻内存开销。[3]

如果纹理只用于渲染，通常应关闭该选项；如果运行时确实需要读取或修改像素，则需要保留。UI 图集、大尺寸贴图尤其值得检查。

关闭 Read/Write 能减少 CPU 副本的占用，但不宜把收益一概写成“总内存减半”。纹理格式、MipMap、流送设置、平台，以及对象自身的开销都会影响最终结果。

4. 根据使用情况选择卸载方式

两种调用都会卸载包本身，使这个 AssetBundle 无法继续用于加载资源。区别在于，是否同时销毁此前从包中加载出来的对象。[4]

Unload(true)：包和已加载资源一起卸载

Unload(true) 会释放包自身的 Native 管理数据，并销毁属于这个包的已加载资源对象，释放它们的 Native 数据；纹理、Mesh 等对象对应的 GPU 资源也会进入图形系统的释放流程，即使场景中的其他对象仍在引用它们。

这里的销毁主要针对引擎对象，不意味着 C# 托管包装已经被回收。包装对象仍由 GC 管理；只要业务代码还持有引用，它就可能继续占用托管堆空间。GPU 资源的实际释放也可能等待渲染任务或驱动处理完成。

例如，从包里加载 Prefab 后调用 Instantiate，场景中的实例通常还在，但它引用的共享 Mesh、材质、纹理可能已被卸载，导致模型无法正常显示。粉红色通常指向 Shader 缺失、错误或不受支持，不能直接归因于“少了一张纹理”。

底层对象销毁后，已有的 C# 变量不会自动被重新赋值。Unity 重载了 ==，会将底层对象已经失效的包装对象判为空：[5]

这也是判断 Unity 对象时，== null 与普通 C# 引用判空可能不一致的原因。对象失效后，访问需要底层对象的成员可能报错，并不意味着每次访问都会导致程序崩溃。

Unload(false)：卸载包，保留已加载资源

Unload(false) 释放的是包自身的 Native 管理数据和相关读取资源。已加载纹理、Mesh、材质的 Native 对象与数据，以及它们对应的 GPU 资源仍然保留，可以继续使用。

它不会直接回收 AssetBundle、Texture2D 等 C# 包装，也不会释放调用方传给 LoadFromMemory 的托管 byte[]。这些托管对象都需要在不再可达后，由 GC 回收。

但这些资源也不再由原来的包实例管理。后续重新打开同一个包，不会自动把旧资源重新关联回来。

不过，重复副本不一定就是永久泄漏。能否回收，要看资源是否还有使用者，以及是否执行了合适的卸载操作：

  • 对不再需要、且符合 API 限制的单个资源，可以使用 Resources.UnloadAsset。该接口不适用于 GameObject 或 Component。[6]
  • 清除相关引用后，可以在合适的时机调用 Resources.UnloadUnusedAssets()，清理 Unity 判断为未使用的资源。它有全局检查成本，通常安排在加载界面等能够接受开销的位置。

重新加载包，再对新包调用 Unload(true)，并不能顺带销毁上一次 Unload(false) 留下的旧资源。

6. 使用 UnloadUnusedAssets 做阶段性清理

前面提到，Unload(false) 会留下已加载的资源。等使用者退出后，可以通过 Resources.UnloadUnusedAssets() 清理其中不再使用的部分。它也能处理其他加载路径留下的未使用资源，并不局限于 AB 包。

这个接口清理的重点是未使用资源的 Native 对象及其数据，并让相应 GPU 资源进入释放流程。 它与 C# GC 是不同的回收机制：即使具体版本的执行过程中伴随托管 GC，也不能据此认为所有托管包装、数组和缓存容器都已回收。仍然可达的托管对象依然会保留。[8]

“未使用”由谁判断

这个接口不接收包名或资源列表。Unity 会检查 GameObject 层级、脚本组件及静态变量中的引用，判断哪些资源仍然可达。[7]

从行为上，可以把这次清理理解成三个步骤：

  1. 查找仍在使用的资源。 从上述引用入口出发，沿对象之间的引用关系，确定需要保留的资源。
  2. 识别未使用资源。 将没有被这些引用关系保留的资源列入清理范围；它不是只检查刚关闭的界面或刚卸载的包。
  3. 卸载资源。 销毁符合条件的 Native 资源对象、释放相关数据，并让对应 GPU 资源进入释放流程。

这是便于理解的概括，并非对引擎内部具体算法和线程分工的保证。开销不仅来自最终释放了多少资源，也来自查找、遍历引用关系以及销毁对象的过程。 即使最后只回收少量内存，也可能已经付出了明显的检查成本。

因此，界面关闭了，不代表界面用过的纹理就能回收。隐藏的 UI、对象池中的角色、静态字典里的资源缓存，都可能继续持有引用。调用这个接口不会替你清空这些缓存。

还有一个细节：它不会像 C# GC 那样检查脚本执行栈。 仅被普通方法局部变量引用的资源，不能据此保证保留。需要跨越清理过程继续使用的资源，应由明确的持有者保存，例如存活组件的字段；协程局部变量可能被编译成状态机字段，也不宜一概当作普通栈变量理解。[7]

表中的 GPU 释放指生命周期上的释放请求，不保证调用返回时驱动已归还物理显存；没有 GPU 数据的资源自然不涉及这一列。上述卸载操作也不会删除磁盘上的 AB 文件或下载缓存。

例如，LoadFromMemory(data) 使用的 data 是托管数组。卸载包负责释放 Unity 侧的包数据；调用方不再持有 data 后，数组才具备被 GC 回收的条件。这是两笔独立的内存，不能只调用一次 Unload 就认为全部清完。

因此，清理通常分成两个责任：先按资源生命周期释放 Native 对象及相关 GPU 资源，再解除不需要的托管持有关系，让 GC 回收包装和业务对象。解除引用可以先做，但解除引用本身不等于已经释放 Native 或 GPU 数据。

将清理安排在场景切换的 Loading 阶段

UnloadUnusedAssets() 属于开销可能较大的集中清理操作，建议安排在场景切换的 Loading 界面中执行。 它虽然返回 AsyncOperation，但不意味着所有工作都在后台执行，也不保证每帧的耗时足够小。在正常游玩、镜头运动或 UI 动画期间调用，可能让主线程超过单帧预算，造成掉帧或明显卡顿。

推荐顺序是：先显示 Loading 界面并让它至少完成一帧显示，再卸载旧场景或销毁旧实例、清除不需要的缓存引用，等待销毁完成后执行清理，最后继续新场景的加载流程。若新旧场景共享资源，应先确定需要保留的资源由常驻持有者引用，避免刚清理完又重新加载。

Loading 界面用于承接这段等待，并不能消除清理成本；其中的转圈动画或进度条也可能短暂停顿。不要在每次 Release、关闭小弹窗或每隔几秒时调用，实际耗时应在目标设备上通过 Profiler 确认。

工程上常见的做法，是统一管理包及其依赖，复用已打开的包，在确认没有使用者后调用 Unload(true)。

实际管理器还需要处理几个问题：

  • 依赖包的持有关系。 依赖链沿用前文的加载流程；这里还需要让每个使用者持有相应依赖，直到使用结束，防止共享材质、Shader 或纹理被提前卸载。
  • 异步请求合并。 多个请求同时加载同一个包时，应共享进行中的任务；加载失败或取消时，要正确回滚计数。
  • 资源缓存与包状态一致。 缓存中的资源不能在所属包已经 Unload(true) 后继续被当作有效对象返回。

引用计数不是唯一方案。生命周期边界清晰的项目，也可以在关卡退出后统一卸载该关卡独占的包。无论采用哪种方式，最终都需要能回答同一个问题：这个包里的资源，现在还有谁在用？

四、结果验证：确认副本不再累积，使用中的资源仍有效

管理策略调整后，需要验证的是资源生命周期是否符合预期，而不只是某一帧的进程内存数值。

对于角色预览界面，可以在目标设备的 Player 中，记录打开前、打开后、关闭清理后的 Memory Profiler 快照，再重复若干次相同操作。

验证场景 应观察到的结果
同时存在多个使用者 释放其中一个后，其余对象仍能正常显示，共享资源保持有效
最后一个使用者退出 确认销毁完成、缓存清除后，相关资源能够按策略卸载
反复打开和关闭界面 同名纹理、Mesh、材质的实例数不持续逐轮增加；允许策略明确的缓存保留
执行 UnloadUnusedAssets() 未使用资源得到清理，仍被有效使用者持有的资源保留
主包释放、其他对象仍使用依赖包 共享依赖保持有效，直到最后一个持有者退出

这里列出的是验证标准，并非项目实测数据。具体节省多少内存、清理耗时多长，需要结合资源规模、Unity 版本与目标设备测量。

验证时也应分开看 Native 资源数量与占用、Managed 包装及业务容器的占用，以及图形内存。Native 资源已释放但包装仍被静态集合引用，和包装已经回收但共享资源仍在使用，是两种不同情况。

如果资源实例数仍然上涨，优先检查重复加载与旧缓存；如果资源无法回收，检查对象池、静态字段和存活组件的引用。如果对象数量已经恢复，而进程内存没有立即下降，再分析 Unity 分配器保留内存、尚未回收的托管包装，以及 GPU 侧延迟释放等因素。

回到最初的预览界面：打开包、加载 Prefab、创建角色、销毁角色、卸载资源，是需要衔接的几个步骤。明确每一步的持有者和结束条件，才能同时避免提前卸载与重复副本。Unload(true)、Unload(false) 和 UnloadUnusedAssets() 也就各自有了明确的使用位置。
