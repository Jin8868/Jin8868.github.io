AlloyFramework(四)：资源管理系统

发表于2026-11-11|更新于2026-11-13
|总字数:5k|阅读时长:17分钟

游戏业务中，打开界面需要加载预制体，展示道具需要加载图标，进入关卡需要加载场景。这些功能都需要资源系统，但业务真正关心的是“加载什么、什么时候可用、用完怎么释放”。

先简单介绍一下当前使用的资源方案。YooAsset 是面向 Unity 的资源管理框架，提供资源收集与打包、资源包管理、异步加载、依赖资源管理，以及基于版本清单的资源更新等能力。它支持编辑器模拟、离线和联机运行模式，让开发阶段与发布后的资源加载使用同一套方案。

例如，业务要加载一个界面预制体，YooAsset 可以负责定位它所在的资源包、加载依赖，并返回加载句柄；发布新资源时，则通过版本清单确定需要下载的文件。项目中常见的 YooAssets 是它提供的静态入口类名，本文使用 YooAsset 指代这套资源方案。

AlloyFramework 在这些能力之上封装业务接口与生命周期管理，将 YooAsset 接入整个框架的启动和退出流程。
如果业务直接调用 YooAsset 的接口，界面、战斗和场景逻辑中就会出现具体资源库的类型与调用方式。以后更换资源方案时，需要修改的地方也会散落在这些业务模块中。

AlloyFramework 因此将资源系统分成三层：业务层 → 框架层 → 具体实现层。当前实现层使用 YooAsset，业务只调用框架接口，并使用框架定义的资源句柄。

本文从这三层的职责出发，介绍接口、初始化、资源加载与释放，以及后续如何更换实现。异步接口使用 Cysharp.Threading.Tasks 提供的 UniTask，取消令牌使用 System.Threading.CancellationToken。

一、三层结构各自负责什么

最关键的一点是：框架层不知道实现层的加载细节。业务层只调用框架接口，框架通过抽象接口使用资源服务，具体实现通过工厂创建。

这是**依赖倒置原则（Dependency Inversion Principle）**的直接应用：高层模块依赖抽象契约，具体资源实现也遵循这份契约。业务不直接依赖 YooAsset API，框架的通用请求处理逻辑也不需要知道 YooAsset 如何加载资源。

这里要区分调用方向与代码依赖方向：运行时调用按“业务层 → 框架层 → 实现层”逐层向下；接口由框架定义，具体实现反过来依赖并实现这些接口。实现层不会反向调用具体游戏业务。

将来换成 Addressables 或自研方案，只需提供满足相同接口与行为约定的实现，并切换创建它的工厂，框架的通用处理逻辑和业务调用代码都可以保持不变。

工厂负责决定“创建哪一种资源服务”，框架负责决定“何时初始化、如何调用和何时退出”。这样，具体类型的选择就集中在启动接入位置。

整体调用关系分为三层，每一层承担不同的职责：

    Business["业务层：界面、角色、关卡等业务逻辑"]
    Framework["框架层：封装统一加载接口与资源生命周期"]

业务层通过 ResourceManager 调用 LoadAssetAsync、LoadSceneAsync 等加载接口。框架层统一封装这些操作及资源生命周期，通过 IAssetService 使用具体实现。当前实现层由 YooAssetService 接入 YooAsset，将框架接口转换为实际的资源加载与释放操作。

图中的箭头表示逐层调用关系。具体实现由启动工厂创建，业务无需知道底层使用哪一种资源方案。

业务层表达加载需求，并负责自己持有资源的使用周期。框架层提供稳定的接口，统一处理请求的生命周期。实现层将这些接口映射为具体资源库的调用。

在当前代码中，框架层包含两个主要对象：ResourceManager 是业务使用的统一入口，ResourceServiceManager 则作为 FrameworkSystem 接入启动管线，并管理底层服务。

YooAssetService 实现 IAssetService，内部才会使用 ResourcePackage、YooAsset 的加载操作和原生句柄。业务得到的结果仍然是框架接口，不需要知道底层使用的是哪一个资源库。

这层隔离既要覆盖加载方法，也要覆盖返回值和释放方式。如果加载入口封装了，返回的却仍是 YooAsset 原生句柄，业务与实现层之间的依赖就还存在。

2. 句柄接口：统一资源的使用与释放

IAssetHandle<T> 表示调用者持有的一份资源使用权，通过 Asset 访问资源，用完调用 Dispose。IInstanceHandle 同时持有实例和它依赖的预制体引用，释放时会销毁实例并归还引用。场景卸载是异步操作，因此 ISceneHandle 提供 UnloadAsync。

YooAssetService 需要准备什么

当前实现先执行配置中的发布准备逻辑，随后调用 YooAssets.Initialize 并初始化默认包 DefaultPackage。

资源包初始化按以下顺序进行：

  1. 根据运行模式创建 YooAsset 初始化参数。
  2. 初始化资源包。
  3. 取得本次使用的包版本。
  4. 激活该版本的资源清单。
  5. Host 模式下下载清单中缺失的文件。
  6. 将资源包登记为可用，默认包同时设置给 YooAsset。

运行模式包括编辑器模拟、离线和 Host 模式。Host 模式可以使用启动阶段固定的发布信息与包版本，使资源、业务 DLL 等文件按同一次发布准备。

业务只需要等待资源服务就绪。需要使用其他资源包时，通过框架的 EnsurePackageAsync 提前准备，具体模式和 YooAsset 参数由实现层处理。

YooAsset 实现如何复用加载结果

YooAssetService 使用“资源包名称、资源地址、资源类型”作为资源索引。同一索引的请求共享底层加载操作，每个请求分别取得自己的框架句柄。

第一次加载时，实际调用 package.LoadAssetAsync<T>(location)。后续相同请求复用这份共享记录，并分别增加引用。加载完成后，各自得到一个 AssetLease<T>，对外只暴露 IAssetHandle<T>。

A 释放句柄时只归还 A 的引用，B 仍然可以继续使用。最后一个引用归还后，实现层才移除共享记录并释放 YooAsset 原生句柄。一个等待者取消，也只归还自己的引用，不会直接取消其他等待者使用的共享加载。

这套实现让业务能够独立管理自己的使用周期，而不必判断另一个界面是否还在使用同一张图。

五、加载与释放必须成对设计

1. 普通资源：保存句柄，用完归还

业务拿到资源后，需要让句柄存活到资源不再使用。下面以界面图标为例，展示加载与清理的核心过程：

Image 来自 UnityEngine.UI。界面关闭时，需要先取消尚未完成的加载，并调用清理逻辑。资源一旦交付，业务就应保存并最终释放句柄，不能只取出 Sprite 后遗失句柄，也不能在图片仍显示时提前归还。

2. 预制体实例：实例与资源引用一起管理

业务通过 InstantiateAsync 可以取得 IInstanceHandle。当前实现先加载预制体，再调用 Unity 的实例化方法，将实例与预制体引用一起放入返回句柄。

如果业务只调用 Destroy(instanceHandle.Instance)，实例虽然被销毁，但仍需要调用句柄的 Dispose 归还预制体引用。统一通过句柄释放，更容易保持完整的生命周期。

3. 场景：等待卸载完成

场景通过 LoadSceneAsync 返回 ISceneHandle，用 UnloadAsync 等待卸载完成。框架管理层也会跟踪场景卸载操作，正常关闭资源服务时等待已经开始的卸载退出。

资源句柄释放和闲置资源清理是两个不同动作。Dispose 归还调用者的资源引用；TryUnloadUnusedAsset 和 UnloadUnusedAsync 则请求底层清理可卸载的资源。清理闲置资源不会替业务归还仍持有的句柄，也不保证内存立即下降。

六、框架关闭时如何处理尚未完成的请求

资源请求可能仍在等待文件或场景加载，框架关闭时需要先协调这些操作，再释放底层实现。

ResourceServiceManager 正常退出时，会先解除业务入口绑定并拒绝新请求，取消资源服务的生命周期令牌，等待已经开始的请求及回滚处理结束，最后调用实现层的 ShutdownAsync。

这也解释了框架层为什么需要一个管理对象：它除了转发接口，还要确保请求在服务退出时得到一致的处理。具体实现负责底层资源的释放，框架管理层负责调用时机和请求生命周期。

应用退出时无法依赖异步操作全部完成，因此还提供同步 Shutdown 作为兜底。业务正常退出仍应先释放自己持有的资源，再让框架关闭整个服务。

七、更换实现层需要做什么

如果要将 YooAsset 换成 Addressables 或自研资源方案，需要完成以下接入工作。

1. 实现资源服务接口

创建新的资源服务类，例如 ProjectAssetService，实现 IAssetService，完成初始化、资源包准备、资源加载、实例化、场景加载、闲置资源清理和退出逻辑。

如果项目还需要资源更新或原始文件读取，则同时实现 IHotUpdateService、IRawFileService，提供对应能力。

2. 适配框架句柄

将新方案的加载结果包装为 IAssetHandle<T>、IInstanceHandle 和 ISceneHandle。资源释放时归还当前持有者的引用，实例释放时同时清理实例与预制体引用，场景卸载则等待底层操作完成。

同时处理取消和失败时的资源回收，保证未交付的结果能够清理，多个调用者持有同一资源时不会互相影响。

3. 在启动阶段替换工厂

4. 配套调整资源构建与发布

当前资源实现位于主包侧，更换实现后需要重新构建并发布主包。

游戏业务中，经常需要“等一会儿，再执行一段逻辑”：提示显示两秒后关闭，角色死亡后延迟复活，或者等下一帧再刷新界面布局。 因此，框架需要提供一种方便的延迟写法，让业务能够直接表达“多久之后做什么”。例如，让提示两秒后关闭： 12345// 两秒后关闭提示，使用不受游戏时间缩放影响的计时。long closeTimerID = AlloyTimer.DelaySeconds( 2.0, CloseTip, useTimeScale: false); 这里的 CloseTip 是业务自己的关闭方法，计时器负责等待并在到期后调用。返回的任务 ID 则用于提前取消：如果提示已经被玩家手动关闭，就可以取消原来的延迟任务。 12// 提示提前关闭时，取消尚未执行的延迟回调。AlloyTimer.Remove(closeTimerID); 从一次延迟继续往下看，还会遇到每秒刷新一次倒计时、每隔几帧检查一次状态、重复执行指定次数等需求。游戏暂停时，有的任务需要一起暂停，有的界面刷新则需要继续。这些都是同一类计时需求的不同用法。 Unity 的协程和 UniTask 都可以表达...
